# 요청 단위 보호와 안전한 종료 개선 — 최종 결과 (2026-10-23)

범위: 현재 감지·전환 정책은 그대로 두고, ① 전환이 이후 요청을 실제로 보호했는지 요청 단위로 확인하고 ② 전환 때 진행 중이던 답변이 끊기는 문제를 원인 확인 → 개선 → 검증했다. 새 감지기·SLO 기반 확장·생성 상태 이전은 하지 않았다. Git·Calico·안전검사는 건드리지 않았다. 모든 실험은 한 번(또는 사전 등록한 횟수)씩이며 **사례 검증**이다(통계적 결론 아님).

## 쉬운 설명 (먼저 읽기)
- **좋아진 것**: 전환할 때 서버가 "종료 신호를 받자마자 하던 답변을 버리던" 설정을 "최대 90초 동안 하던 답변을 끝내고 종료"하도록 바꿨다(vLLM이 이미 가진 옵션 `--shutdown-timeout` 사용, 새 프로그램 추가 없음). 같은 조건에서 진행 중이던 답변 4개 중 **정상 완료가 1개 → 3개**가 됐다(장애 없음). 네트워크 지연을 건 조건에서도 1개 → 3개.
- **여전히 끊기는 경우**: 구 Pod가 정해진 최대 대기(90초) 안에 못 끝내는 긴 답변(1024토큰 요청)은 끊긴다. 끊기기 전 30초 동안 연결만 열려 있다가 오류로 끝난다. 그리고 **연결을 재사용하는(keepalive) 클라이언트**는 전환 뒤에도 약 30초간 구 Pod로 요청이 가고, 구 Pod가 종료를 시작하면 500 오류를 받는다(개선 구성에서 5건, 기존에는 1건).
- **비용**: 구 Pod를 더 오래 켜 둔다. 구 Pod 유지 시간이 37초(기존) → 98.5초(모든 답변이 90초 안에 끝난 경우) ~ 157.8초(상한까지 간 경우)로 늘었다. 구 Pod 하나는 CPU 2·메모리 4Gi를 예약하므로 같은 조건의 기존 구성 대비 추가 Pod-초 61.6~120.9초(장애 없음)·99.5초(네트워크 지연)에 비례한 예약 비용이 든다.
- **'예방'이 아니라 '피해 감소'**: 장애 주입 후 약 2초 안에 느린 요청이 이미 나왔고, 전환은 그 뒤(약 49초)였다. 전환 뒤의 요청은 정상으로 돌아왔다.

## 2. 답변 중단의 확인된 원인 (로그·설정으로 확인)
시간순(장애 없는 전환, 기존 구성 F):
1. 승격 호출 → Service 선택자 변경(새 요청은 새 Pod로).
2. 선택자 변경 +30초: Argo Rollouts `scaleDownDelaySeconds: 30`이 지난 뒤 구 ReplicaSet을 0으로 줄여 Pod 삭제 요청 → kubelet이 SIGTERM.
3. 구 Pod의 vLLM 로그: `stopping engine client mode=abort timeout=0s` → **진행 중 요청을 즉시 중단**(vLLM `--shutdown-timeout` 기본값 0 = abort).
4. 이어서 두 가지 모양으로 나타났다: (a) 첫 실행: 토큰이 멈춘 채 연결이 열려 있다가 유예(`terminationGracePeriodSeconds` 기본 30초) 만료 SIGKILL 때 `ClientPayloadError`로 끊김(4개 모두). (b) F 재실행: 종료 신호 16ms 뒤 `[DONE]`만 받고 `finish_reason` 없이 끝남 — **정상 종료 표시를 받았지만 답변이 잘림(조용한 절단, 72~74청크)**. 그래서 '정상 완료'는 `finish_reason`이 있을 때만 인정한다.

- Argo의 30초 지연은 새 요청 경로 변경 뒤의 고정 지연일 뿐 요청 완료를 확인하지 않는다.
- 현재 vLLM(0.28.1rc1.dev133)은 `--shutdown-timeout`(0=abort, >0=대기)을 지원하고, 종료 로그에 `draining in-flight requests count=N`을 남긴다.
- 처리 중 요청 수: `vllm:num_requests_running`(/metrics)은 관측에서 엔진 로그와 일치했다(D2: 0이 되는 시각 05:33:27.6, 엔진 `processing complete` 05:33:26.6). 다만 이번 개선은 이 지표를 제어에 쓰지 않는다(vLLM 내부 대기에 맡김).
- keepalive: 연결을 재사용하는 클라이언트는 선택자 변경 뒤에도 구 Pod로 계속 간다(29~35건, 구 Pod 삭제 시작까지 약 30초). 새 연결은 즉시 새 Pod로 간다. **오류 경로·설정 점검·보호되는/안 되는 요청 정리는 `RESULT-SUMMARY-KEEPALIVE-20261023.md`가 최종본이며, 이 문서의 keepalive 연결 포트 표기(직전 연결 포트 가정)는 그 문서의 서버 로그 기준 집계로 정정된다.**

## 3. 개선 구현과 동작 (새 제어 로직 없음)
- 파일: `gitops/apps/vllm-serving/overlays/graceful-drain/{kustomization.yaml, drain-patch.yaml}` — 기본 `rollout.yaml`·`network-tolerant` 무변경. 값(검증 전 고정): `--shutdown-timeout=90`, `terminationGracePeriodSeconds: 120`, `scaleDownDelaySeconds: 30` 유지.
- 동작: 선택자 변경 +30초에 구 Pod에 SIGTERM → vLLM이 `mode=drain timeout=90s`로 전환해 진행 중 요청을 최대 90초 기다림 → 모두 끝나면 정리 후 종료(조기 종료), 아니면 90초에 엔진 강제 종료 → 연결은 유예(120초)까지 열려 있다 종료.
- **'요청 완료를 확인하는 종료'로 표현할 수 있는 이유(사전 등록 (가)(나))**: (가) D2에서 3개 요청이 끝나자 SIGTERM 후 37.4초에 `request processing complete`가 기록됐다(상한 90초보다 훨씬 이른 종료). (나) D에서 끝나지 않은 요청은 정확히 90.0초(05:20:29.64)에 엔진이 강제 종료됐다. 완료 판정과 대기는 vLLM 내부 기능이며 우리 쪽 지표·제어를 추가하지 않았다. 고정 지연만 늘린 것이 아니다.
- 지표 누락·낡음 규칙은 제어에 지표를 쓰지 않으므로 해당 없음. 무한 대기 없음(90초 상한 + 120초 유예). 반복 승격 없음. 이미 보낸 스트림의 자동 재시도·이어붙이기 없음.
- 새 요청 유입 차단과 기존 응답 완료는 별개로 확인: 새 연결 요청은 선택자 변경 뒤 구 Pod 0건(D 158, D2 99, 네트워크 지연 165건 모두 새 Pod), 기존 응답은 아래 표.

## 7. 발표에서 주장할 수 있는 것 / 아직 입증하지 못한 것
주장 가능(근거 있음, 사례 검증):
- 전환 뒤 새 연결 요청은 모두 새 Pod가 처리했고 요청 지연이 정상 수준으로 돌아왔다(C 대 G 한 쌍, 선택자 변경 뒤 중앙값 1.32초 → 0.30초). 처리 Pod는 접속 로그 대조로 요청마다 특정했다.
- 기존 구성은 전환 시 진행 중이던 긴 답변을 잘랐다(종료 신호 즉시 중단 + 조용한 절단 가능). 원인은 vLLM 기본 종료 모드(abort)와 짧은 종료 유예다.
- 기존 vLLM 옵션만으로(새 제어 로직 없이) 진행 중 답변을 상한 90초 안에서 끝까지 전달할 수 있었고, 모두 끝나면 일찍 종료했다. 대가는 구 Pod 유지 시간 증가다.

입증하지 못했거나 말하면 안 되는 것:
- '사용자 불편 전 예방'(느린 요청이 먼저 나왔다), 진행 중 생성 상태를 새 Pod로 옮김, 모든 답변 보존, 심하게 손상된 Pod·1초 이상 지연에서의 보존, 통계적 일반화(각 구성 1회).
- keepalive 클라이언트 보호(오히려 종료 때 500 오류 5건, 클라이언트 재연결·재시도는 구현하지 않음).
- 90초가 최적 값(검증 전 고정값, 튜닝하지 않음), 유예 여유 30초의 최적성(상한 뒤 약 30초 연결만 열려 있음 — 줄이면 개선될 수 있으나 이번엔 바꾸지 않음).

## 8. 기존 구현에서 발견된 문제
- 저장소 `probe.py`에 없는 `force_close`가 이미지 프로브에만 있다(재현성). 사본 `notes/image-probe-forceclose-20261002.py`.
- `analyze.first_success_after()`가 첫 카운터 증가를 건너뜀(정정 별도 보존).
- 기본 종료 설정에서 SIGTERM 시 진행 중 요청이 즉시 중단되고 `[DONE]`만 받는 조용한 절단이 가능하다.
- 엔드포인트 감시가 승격 뒤 변경을 기록하지 못했다(선택자 변경은 기록됨).
- 종료 중 keepalive 요청이 500을 받는다(vLLM `cannot schedule new futures after shutdown`).
