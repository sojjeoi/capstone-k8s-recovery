# keepalive 오류 한정 점검 — 최종 결과 (2026-10-23)

범위: 전환 때 연결을 재사용(keepalive)하는 클라이언트가 받는 오류에 한정했다. 기존 로그·코드로 경로를 확인하고, 현재 구성의 작은 설정 변경으로 완화되는지 **한 번만** 점검했다. 프록시·구조 변경·클라이언트 변경은 하지 않았다. 점검 뒤 새 실험은 시작하지 않았고 기본 상태로 복원했다. 각 실행은 1회이며 사례 검증이다.

## 쉬운 설명 (먼저 읽기)
- **왜 오류가 나나**: 서비스 주소 규칙(Service)을 바꿔도 **이미 열려 있는 연결은 옛 Pod에 그대로 붙어 있다.** 옛 Pod가 종료를 시작하면, 서버가 새 요청을 처리할 준비를 이미 닫아 버려서 그 열린 연결로 들어온 요청은 곧바로(약 10ms) 500 오류를 받는다. 오류를 받은 연결은 닫히고, 클라이언트의 다음 요청은 새 연결로 새 Pod에 간다. 그래서 오류 수 = 종료 시점에 옛 Pod에 붙어 있던 연결 수였다(개선 구성에서 5개 연결 → 5건, 연결당 정확히 1건).
- **설정으로 어디까지 되나**: 서버가 한동안 쓰이지 않은 연결을 일찍 닫도록 하면(`VLLM_HTTP_TIMEOUT_KEEP_ALIVE` 5초 → 1초) 이 점검에서는 종료 시점에 붙어 있던 재사용 연결이 0개가 되어 500이 0건이었다. **하지만 이것은 "연결이 자주 정리되어 옛 Pod에 오래 안 붙어 있게 된 것"이지, 열린 연결의 요청을 서버가 정상 처리하게 만든 것이 아니다.** 연결을 쉬지 않고 계속 쓰는 클라이언트는 여전히 같은 500을 받는다고 보는 것이 맞다(이번 점검에서는 재현하지 못함). 그리고 부작용으로 "서버가 막 닫은 연결을 클라이언트가 재사용하다 실패"하는 오류가 새로 생겼다(189건 중 2건).
- **결론**: keepalive 오류는 **부분 완화만 가능, 완전 해결은 불가능(코드 동작이라 설정으로 막을 수 없음)**으로 확정한다.

## 1. 오류 경로 (기존 로그로 확인, 실험 아님)
(`analysis/ka-path-20261023/ka-path.json`, 구 Pod 접속 로그의 연결별 집계)
1. 선택자 변경은 열린 TCP 연결을 옮기지 못한다. 종료 신호 직전 10초 안에 쓰인 재사용 연결이 모든 실행에서 5개였고, 이 연결들은 전환 전부터 9~19회 재사용된 연결이다.
2. 구 Pod가 종료 신호를 받으면 vLLM이 요청 전처리용 실행기를 닫는다. 열린 연결로 새 요청이 오면 `RuntimeError: cannot schedule new futures after shutdown`(HTTP 500)이 즉시 난다(위치: `vllm/utils/async_utils.py`의 `run_in_executor`, 호출 경로 `completion/serving.py: render_completion_request`). 엔진은 drain 모드라 **진행 중 요청은 계속 처리**된다.
3. 500을 받은 연결은 닫히고 다음 요청은 새 연결 → 새 Pod. 연결당 500은 1건이었다.

| 실행 | 종료 시점 재사용 연결 | 500을 받은 연결 | 500 건수 |
|---|---|---|---|
| F 기존(장애 없음) | 5 | 1 | 1 (프로세스가 바로 종료되어 나머지는 연결 끊김) |
| D 개선(장애 없음) | 5 | 5 | 5 |
| D2 개선(조기 종료 확인) | 5 | 5 | 5 |
| F 기존(네트워크 지연) | 5 | 0 | 0 (`ServerDisconnectedError` 1건) |
| D 개선(네트워크 지연) | 5 | 5 | 5 |
| **DKA1 개선 + 유휴 제한 1초** | **0** | **0** | **0** |

- 정정: 이전 표에서 keepalive 요청의 포트를 "직전 연결 포트로 가정"한 값은 부정확했다. 위 표는 서버 로그의 연결별 기록이라 정확하다. 이전 보고서의 keepalive 실패 건수(D 5, D2 5, 지연 D 5, F 1)와는 일치한다.

## 2. 작은 설정 변경의 점검 (1회, DKA1)
- 변경: overlay `gitops/apps/vllm-serving/overlays/graceful-drain-ka1/` = D 구성 + 환경변수 `VLLM_HTTP_TIMEOUT_KEEP_ALIVE=1`(정수 최소값, 검증 전 고정). 프록시·구조 변경 없음. 사전 등록: `docs/design/GRACEFUL-DRAIN-VERIFICATION-DRAFT-20261023.md` §5c.
- 같은 계획·같은 probe로 D와 비교(장애 없음, `trace/drain-DKA1-2026-10-23T120458/`):

| 항목 | D (유휴 5초) | DKA1 (유휴 1초) |
|---|---|---|
| 종료 시점 재사용 연결 / 종료 중 500 | 5 / 5건 | **0 / 0건** |
| keepalive 요청이 구 Pod로 가던 기간(선택자 변경 후) | 약 30초(35건) | **약 1.7초(2건)** 후 새 Pod |
| keepalive 요청 실패 | 5건(500) | **2건(`ServerDisconnectedError`, 1건은 전환 전 평상시)** |
| keepalive 클라이언트의 새 연결 수(전체 요청 중) | 7 (181건) | 18 (189건) |
| 스트리밍 정상 완료 / 중단 | 3 / 1 | 3 / 1 (같음; 1024토큰은 90초 상한에서 중단, 295청크) |
| 새 연결 요청(전환 후) | 새 Pod 158, 구 Pod 0, 실패 0 | 새 Pod 164, 구 Pod 0, 실패 0 |
| 구 Pod 유지(선택자 변경→사라짐) | 157.8초 | 164.2초 |

- 해석: 이 클라이언트(1 RPS, 요청 사이에 연결이 1초 넘게 쉬는 경우가 있음)는 서버가 유휴 연결을 일찍 닫아서 전환 직후 새 Pod로 갈아탔고, 종료 시점에 옛 Pod에 붙은 연결이 없어 500이 나지 않았다. 드레인(스트리밍 완료·90초 상한)에는 영향이 없었다.
- **이것을 'keepalive 문제 해결'이라고 쓰지 않는다**: (가) 연결을 계속 쓰는(쉬는 간격이 1초 미만인) 클라이언트는 종료 중 500을 받는다고 코드 동작상 예상되지만 이번 점검에서는 재현하지 못했다(추정). (나) 유휴 제한 1초는 "서버가 막 닫은 연결을 클라이언트가 재사용하다 실패"하는 경합을 만든다(2/189건, 약 1%). (다) 재연결 증가의 지연 비용은 측정하지 않았다. (라) 1회 결과이다. 클라이언트를 새 연결 방식으로 바꾼 것은 해결로 세지 않았고, 고정(새 연결) probe는 별개 지표다.
