# 통일 비교 최종 결과 (2026-11-06)

> 장애 3종 × 비교 방식 4개를 같은 규칙으로 칸마다 유효 10회 반복한 결과다. 사전 등록: [UNIFIED-COMPARISON-PREREG-20261104.md](../design/UNIFIED-COMPARISON-PREREG-20261104.md). 표 원본: `experiments/results/hpa_compare/analysis/UNIFIED-TABLE-20261105T151043Z.md`(`.json`에 세션별 값).

## 1. 한 줄 결론

CPU 압박과 네트워크 지연에서는 우리 시스템(예비 Pod 자동 전환)의 품질 위반 시간이 다른 세 방식보다 짧았고 범위도 겹치지 않았다. **요청 폭주에서는 우리 시스템이 네 방식 중 가장 길었다.** 상황에 따라 확장과 전환이 맞는 경우가 다르다.

## 2. 왜 했나

지도교수 피드백(경진대회 후): ① CPU 압박과 네트워크 지연 실험의 비교군이 서로 달랐다 ② 반복 횟수가 적었다(6회, 13회 등). 그래서 모든 장애에 같은 4개 비교군을 두고 칸마다 10회씩 다시 쟀다.

## 3. 무엇을 비교했나

| 방식 | 구성 |
|---|---|
| 무전환 | 서비스 Pod 1개, 조치 없음 |
| 오토스케일링 | 서비스 Pod 1개 + CPU 기반 HPA(목표 100%, 최대 2개) |
| 계속 분산 | 준비된 Pod 2개에 요청을 계속 나눠 보냄 |
| 우리 시스템 | 서비스 Pod 1개 + 준비된 예비 Pod 1개, 감지 신호가 오면 새 요청을 예비 Pod로 전환 |

| 장애 | 내용 | 우리 시스템 감지기 |
|---|---|---|
| CPU 압박 | 서비스 Pod 1개에 CPU 일꾼 1→2→3→4개, 단계마다 90초 | CPU 임계값 규칙 |
| 네트워크 지연 | 서비스 Pod 1개에 지연 500→1000→2000→4000ms(지터 10%), 단계마다 90초 | 상태 확인 규칙(net_probe) |
| 요청 폭주 | 요청량을 단계적으로 늘림(`chaos/scenario-load-ramp.yaml`) | CPU 임계값 규칙 |

- **지표:** 주입 후 10분(600초) 동안 품질 기준을 어긴 시간의 합(초). 품질 기준은 최근 60초 응답 시간 P95가 0.648초를 넘는 상태가 30초 이상 이어지거나, 성공률이 99% 아래인 경우다.
- **측정:** 1초에 1번 짧은 확인 요청(max_tokens=1)을 보내 잰다. 네 방식 모두 같은 측정·같은 판정 규칙을 쓴다.
- **순서:** 한 장애에서 네 방식을 1회씩 묶어 한 블록으로 하고, 블록마다 방식 순서를 한 칸씩 돌렸다.

## 4. 결과

품질 기준을 어긴 시간의 합(초). 중앙값(최소~최대), 칸마다 유효 10회.

| 장애 | 무전환 | 오토스케일링 | 계속 분산 | 우리 시스템 |
|---|---|---|---|---|
| CPU 압박 | 269.7 (200.5~292.5) | 232.9 (191.5~291.8) | 247.0 (192.0~291.8) | **0.0** (10회 모두 0) |
| 네트워크 지연 | 389.1 (387.9~391.0) | 388.5 (378.9~393.0) | 386.6 (372.9~390.1) | **92.0** (47.1~129.1) |
| 요청 폭주 | 310.3 (131.6~475.0) | 267.8 (198.8~392.1) | 287.8 (84.4~339.0) | **365.5** (303.7~474.0) |

Mann-Whitney U 양측 p(우리 시스템 대 각 방식, 참고값):

| 장애 | 대 무전환 | 대 오토스케일링 | 대 계속 분산 | 방향 |
|---|---|---|---|---|
| CPU 압박 | < 0.0001 | < 0.0001 | < 0.0001 | 우리 시스템이 짧음 |
| 네트워크 지연 | < 0.0001 | < 0.0001 | < 0.0001 | 우리 시스템이 짧음 |
| 요청 폭주 | 0.0115 | 0.0011 | 0.0001 | **우리 시스템이 김** |

p값은 차이가 있다는 참고값일 뿐이며, 클러스터·모델이 하나라 일반화하지 않는다.

### 우리 시스템의 전환
- 유효 30회(장애 3종 × 10회) 모두 전환 뒤 새 Pod 요청 +60, 기존 Pod +0으로 요청 이동이 확인됐다.
- 장애 주입부터 전환까지: CPU 압박 60.2~89.5초(중앙값 68.9), 네트워크 지연 33.4~89.5초(68.7), 요청 폭주 69.0~164.9초(113.1).
- 감지 전의 저하는 막지 못하므로 네트워크 지연과 요청 폭주에서 위반 시간이 0이 아니다.

## 5. 해석 (확인된 사실과 추정 구분)

- **CPU 압박·네트워크 지연:** 특정 Pod 하나만 느려지는 상황이다. 새 요청을 건강한 Pod로 옮기면 피해가 줄었다(확인). 오토스케일링은 네트워크 지연에서 다른 방식과 거의 같았다(확인).
- **요청 폭주:** 전환이 10회 모두 완료됐는데도 위반 시간이 가장 길었다(확인). 전환은 같은 크기 Pod로 바꿀 뿐 용량이 늘지 않는다는 점이 이유로 보이지만, 원인은 측정하지 않았다(추정). 무전환보다도 길었던 이유는 모른다.
- **요청 폭주의 큰 편차:** 같은 방식 안에서도 값이 크게 흔들렸다(예: 계속 분산 84.4~339.0초). 원인은 확인하지 못했다.

## 6. 반드시 같이 밝힐 점

1. **무효 16회(수치 제외).** 사전 등록대로 하네스 오류만 무효로 하고 같은 칸을 1회 다시 했다.
   - CPU 압박 무전환 b1·b5, 네트워크 지연 오토스케일링 b23, 요청 폭주 무전환 b14·b14-r2·b15·b16·b16-r2, 요청 폭주 오토스케일링 b13, 요청 폭주 계속 분산 b12·b12-r2
   - 우리 시스템 n2s12·n2s22(주입 전 안전검사 중단, 10/22), n2s28(측정 시계 불일치, 10/30), n2s64(주입 전 사전검사에서 진입 거부, 주입 없음), n2s67(관찰 미완료)
   - 측정 시계 불일치(probe_clock_inconsistent)는 무전환과 오토스케일링 칸에서 났다.
2. **1회 재시도를 넘은 보충.** 요청 폭주 b16의 계속 분산·무전환과 b26 무전환은 칸을 채우려고 순서 끝에 보충했다.
3. **요청 폭주 무전환 민감도.** 값이 남은 무효 4회(264.5·185.8·153.6·166.7초)까지 넣으면 중앙값이 310.3 → 271.6초가 된다. 우리 시스템이 가장 길다는 결론은 같다.
4. **네트워크 지연의 우리 시스템 10회 중 3회(n2s13·n2s61·n2s63).** 주입 전 첫 평가값이 이미 기준(0.0064초)을 넘어 3번 연속 계산에 들어갔고, 전환이 33~40초로 빨랐다. 이 3회가 위반 시간이 가장 짧은 세 값(47.1·57.0·62.1초)이다. 빼면 중앙값 95.9초(84.9~129.1)이고, 다른 방식과 여전히 겹치지 않는다. 사전 등록대로 유효로 유지했다.
5. **실행 중 사고.** Pod 수를 줄일 때 Argo Rollouts 상태 기록이 실제와 다르게 멈춘 일이 두 번 있었다(11/04, 11/05). 두 번 모두 실험을 멈추고 사용자 승인 후 복구했으며, 원인은 확인하지 못했다. 노트북 대기 모드로 끊긴 세션은 무효로 처리했다. 사용자 요청으로 세션 경계에서 멈춘 적이 있고, 이때 n2s75는 주입 없이 빈 폴더만 남았다.
6. **기존 세션 포함.** 10/22~10/30에 같은 하네스로 잰 네트워크 지연·요청 폭주 세션은 사전 등록 §4대로 칸에 포함했다.
7. **CPU 압박의 이전 결과와 별개.** 경진대회 발표의 CPU 압박 8쌍은 IF(c1) 감지기로 잰 이전 결과라 이 표에 합치지 않았다.

## 7. 한계

- 클러스터 1개, 모델 1개(CPU vLLM, Qwen2.5-0.5B), Pod 2개 규모에서만 확인했다.
- 네트워크 장애는 지연(지터 포함)만 넣었다. 패킷 손실·대역폭 제한은 없다.
- 네트워크 감지 신호(net_probe)는 넣은 지연을 거의 직접 재는 값이라, 이 결과를 AI·다변량 감지의 우수성 근거로 쓰지 않는다.
- 감지기는 원인을 구분하지 않는다. 요청 폭주에서도 전환해 더 나빠졌다.
- 예비 Pod를 켜 두는 비용은 이번에 다시 재지 않았다(이전 비교: 우리 시스템 1,665~1,771, 오토스케일링 900~1,297 Pod·초).
