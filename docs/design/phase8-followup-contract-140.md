# Phase 8 — 후속 비교 분석 계약 동결 + 첫 쌍 포함 기준 사전 고정 (§140)

**이 문서는 다음 쌍(proposed→fixed_threshold)을 실행하기 전에 작성·커밋한다
- 결과를 본 뒤 여기 적힌 지표·창·포함기준을 바꾸지 않는다.** 목적은
결과가 좋아질 때까지 반복하는 게 아니라, 동일 조건에서 두 arm의 차이가
반복에서도 관측되는지 확인하는 것이다.

## 1. 현재 해석 확정(§139 재확인, 표현 규칙 고정)

- 첫 episode의 회복은 **두 arm 모두 탐지·전환보다 먼저** 일어났다
  (fixed: 5분29초 전, proposed: 3분6초 전).
- 탐지·전환은 **실제 두 번째 episode 내부**에 있었다(fixed: episode 2
  구간 09:23:07~09:27:27 안에 탐지 09:25:31/전환 09:25:43; proposed:
  09:46:53~09:51:22 안에 탐지 09:46:57/전환 09:47:03).
- **금지 표현**: "전환이 첫 회복을 만들었다"(첫 회복은 전환보다 먼저
  끝났으므로 사실과 다름), "전환이 모든 저하와 무관했다"(두 번째
  episode와는 시간적으로 겹침). 이 문서 이후 전부 다음 한 문장으로만
  기술한다: "두 번째 episode 구간 안에 탐지·전환이 있다는 시간적 대응
  관계가 있으나, 인과 효과는 확정하지 않는다."

**첫 쌍의 정정된 900초 cohort(§139, 원본 미변경 - 파생 분석만 사용)**:

| | fixed_threshold | proposed |
|---|---|---|
| 발신/완료 | 900/900 | 900/900 |
| cohort 내 미완료 | 0 | 0 |
| 실패 | 1 | 0 |
| latency>0.648s | 69 | 60 |

---

## 2. 분석 계약(결과를 보기 전에 동결)

**주 비교**(동일 900초 발신 cohort, `t_injection<=sent_at<t_injection+900`,
request_id 기준):
1. 실패율 = 실패 수 / cohort 발신 수(완료 기준·전체발신 기준 둘 다 표기)
2. latency 초과율(threshold=0.648s) = 초과 수 / cohort 발신 수(둘 다 표기)
3. 실패∪지연초과 합집합 비율 = request_id 기준 합집합(중복 계산 방지) / cohort 발신 수

**보조 비교**:
- 전체 관측구간(900초) 평가 가능한 raw SLO 위반시간(persistence 미적용,
  `slo_judge.evaluate()`의 point별 판정을 그대로 합산 - §137/§139와 동일
  정의, 재계산 안 함)
- episode별 시작(t_slo)·회복(t_recovery)·탐지(t_detection)·실제
  전환(t_switch) 시각 - **episode 1 하나만으로 "전체 복구 효과"를
  대표하지 않는다.** 900초 전체에서 발견되는 모든 episode를 함께
  보고한다.
- 재위반(2개 이상 episode) 여부, 관측종료 시 미회복(open episode) 여부
- 관측구간(900s) detector CPU 누적 사용·메모리(평균·최대) - 준비/정리
  구간은 경계 표본이 없으면 "계산 불가"로 남기고 추정하지 않는다(§139와
  동일 원칙)
- 실제 탐지 경로(`detection_source`/`detector`)·실제 전환 횟수(audit-log
  `executed_verified` 기준)

**금지 사항(명시)**:
- 두 번째 episode가 새로 중요해졌다고 첫 episode나 전체 900초 데이터를
  분석에서 빼지 않는다 - 전부 함께 보고한다.
- 전환 전후 중 유리한 쪽 구간만, 또는 유리한 episode만 골라 주 결과로
  쓰지 않는다 - 900초 전체와 모든 episode를 항상 함께 낸다.
- 반복이 여러 번 쌓여도, 각 반복(쌍)의 개별 결과를 먼저 보여주고,
  전체 요청을 합산한 하나의 비율만으로 결론 내리지 않는다(§7의
  최종보고 규칙과 동일).

**episode 재구성 방법(고정, §139에서 확립한 그대로 재사용 - 새 로직
없음)**:
- rolling 60초 P95/가용성 계산은 **주입 전 이력을 유지**한다(그래야
  주입 직후 첫 판정이 원본 실시간 판정과 일치 - §139에서 이걸 놓쳐서
  버그가 났었다).
- **집계 구간(cohort)만 주입 이후로 제한**한다 - `raw_violating_seconds()`
  등 지표 합산에는 in-window point만 쓴다.
- `sent_at`(발신 시각) vs `observed_at`(=sent_at+latency, 결과가 확정된
  시각)은 섞지 않는다 - streak 지속시간 판정은 `sent_at` 기준, 반환되는
  `t_slo`/`t_recovery`는 그 판정을 확정지은 표본의 `observed_at` 기준
  (기존 `slo_judge.py` 그대로).
- persistence: latency 위반은 30초 연속(`LATENCY_PERSIST_SEC`), 가용성
  위반은 즉시(지속조건 없음) - `slo_judge.py` 원본 정의 그대로.
- 재탐색 경계: 첫 episode는 `initial_not_before=t_injection`, 이후
  재위반 탐색은 직전 episode의 `t_recovery`를 `not_before`로 - 관측종료
  까지 미회복(`t_recovery=None`)이면 그 지점에서 탐색을 멈춘다
  (`correct_137_errors.find_all_episodes()`, §139에서 이미 검증됨,
  변경 없음).

**비용 표기 규칙**: 배수(倍數)와 절대 증가량을 항상 함께 보고한다.
평균 RSS를 단순히 더하거나 구간 길이를 곱해 "누적 메모리 비용"이라고
부르지 않는다 - RSS 평균/최대는 순간 스냅샷의 평균일 뿐 CPU 누적
사용시간(초)과 같은 종류의 "누적" 양이 아니다. 메모리는 항상 "평균
RSS(MB), 최대 RSS(MB)"로만 표기한다.

## 3. 첫 쌍(fixed→proposed, rep01)의 포함 기준 사전 고정

다음 쌍 실행 **전**에 아래 기준을 정한다 - 결과의 좋고 나쁨은 포함·
제외 판단에 쓰지 않는다.

**질문별 사전 판정**:

| 질문 | 판정 | 근거 |
|---|---|---|
| 동일한 900초 cohort와 완전한 요청 결과가 복원됐는가? | **예** | §139에서 evidence 기준 900/900/900/900 완전 복원, 독립 재계산값과 정확히 일치 확인됨 |
| 비용 구간·계산 방법이 다음 실행과 비교 가능한가? | **관측(900s) 구간만 예, 준비/정리는 첫 쌍부터 이미 불가** | 관측구간 계산법(phase_marks 기준 CPU 누적차/RSS 평균)은 코드 변경 없이 동일하게 재사용 - 준비/정리는 첫 쌍에서도 경계 표본 부족으로 계산 불가였고 이번에도 동일 조건(§4 참고) |
| stop-file 수정이 관측 구간 내 부하·요청·판정·정책 동작을 바꾸는가? | **아니오(코드로 확정, 라이브 재확인 불필요)** | `load_ramp_followup_adapter.py`의 `stop()`은 `run_once()`의 OBSERVING 루프가 끝난(=t_injection+900s 경과) **뒤**에만 호출된다 - stop-file도 그 시점에만 touch됨. `probe_followup.py`의 발신 루프는 900초 동안 stop-file의 존재 자체를 볼 수 없다(그 전엔 파일이 없음) - 900초 안의 발신 주기·payload·timeout·연결정책은 코드상 한 글자도 안 바뀌었다 |
| 아니면 관측 종료 이후의 drain·증거 회수만 보완하는가? | **예, 그것만** | 위와 동일 근거 - 변경 범위는 t_injection+900s **이후**의 종료 절차뿐 |

**결론(사전 고정)**: 900초 cohort 기반 주·보조 지표(§2의 모든 항목,
detector 비용의 관측구간 부분 포함)는 **포함 후보로 확정**한다 -
stop-file 수정이 in-window 동작에 영향을 주지 않는다는 게 코드로
이미 확정됐고, 관측 데이터 자체도 §139에서 완전 복원이 확인됐기
때문이다. 준비/정리 구간 비용은 **첫 쌍·다음 쌍 모두 별도 기술통계로만
남긴다**(비교 대상에서 제외, 폐기 아님 - 표본이 부족하다는 사실 자체를
계속 보고).

**기술적 통과 조건(다음 쌍 실행 뒤 기계적으로 확인)**: 아래 둘 다
충족해야 "stop-file 수정이 실제로 의도대로 동작한다"고 확정하고, 이후
반복에도 같은 계측 프로토콜을 계속 쓴다 - 하나라도 실패하면 계측 코드를
추가로 고치기 전까지 더 반복하지 않는다:
1. 다음 쌍의 두 trial 모두 `load_ramp_followup_adapter.stop()`의
   `drained` 플래그가 True(90초 안에 probe가 자체 grace를 끝내고
   `/probe.exit`를 씀 - 강제종료 아님).
2. 다음 쌍의 두 trial 모두 cohort 재구성에서 terminal-only/duplicate-sent
   같은 "원인불명 이상"이 0건(계측 자체의 무결성 확인).
