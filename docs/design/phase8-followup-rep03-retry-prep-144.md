§140~§143 그대로 보존한다(수정 0건). 이번 턴에 한 일: (1) 사용자가
명시적으로 승인한 최소 코드(재시도 provenance + 예외 진단 로그) 구현,
(2) 가능한 범위에서 오프라인 검증, (3) 검증 도중 **로컬 자원이 §143
시점보다 훨씬 심각하게, 실시간으로 악화되고 있음을 직접 관측**. 라이브
실행은 하지 않았다 - NO-GO 유지, 오히려 근거가 더 명확해졌다.

## 0. 가장 급한 것 먼저

이번 턴 오프라인 검증 도중 **`import numpy`조차 실패**하는 것을 직접
확인했다:
```
OpenBLAS error: Memory allocation still failed after 10 retries, giving up.
```
이건 코드 결함이 아니라 **지금 이 순간 로컬 머신에서 실제 메모리 할당이
실패하고 있다는 직접 증거**다(bare `import numpy` 단독 실행으로 재현 -
내 코드의 특정 로직과 무관함을 확인). Commit headroom은 22:09(1,911MB)
→ 22:27(370MB) → 22:30(109MB)로 21분 사이 계속 하락했다 - **§143의
중단기준(1.5GB)을 이미 한참 하회했고, 지금도 계속 나빠지는 추세다.**
이 관찰 자체가 이번 진단·테스트 실행이 일부 소모했을 가능성을 배제하지
않는다(6절) - 그래도 방향과 속도는 사용자가 지금 알아야 할 정보라
가장 먼저 적는다.

## 1. 구현한 최소 변경 + 오프라인 검증

**A. 후속 재시도 provenance** (`run_load_ramp_followup_trial.py`):
`--attempt-of`/`--attempt-suffix`/`--replacement-reason` 인자 추가.
지정 시 `run_id`에 접미사를 삽입하고(main experiment의 `-retry1-` 관례와
동일 패턴), `contract-{run_id}.json`에 `contract_schema_version`과
`replacement`(원본 run_id·경로·sha256·대체사유·논리적 rep 연결) 필드를
추가한다. 원본 파일은 절대 열어서 쓰지 않는다(읽기+해시만). 동일 run_id
결과가 이미 있으면(계약/trial/cost 셋 중 하나라도) `SystemExit`로 즉시
중단 - 자동 접미사 증가 없음.

**B. 예외 진단 로그** (`run_once.py`): 신규 `_write_exception_diagnostic()`
- 일반 `except Exception` 경로에서만 `results_dir/diagnostics/exception-
{run_id}-{시각}.log`에 run_id·예외타입·발생시각·전체 traceback을 남긴다.
env var·요청 원문·지역변수는 담지 않는다(`traceback.format_exc()` 기본
출력 자체가 그런 값을 포함하지 않음). 로그 쓰기 자체가 실패해도(자체
try/except로 흡수) 원래 `invalid_reason`/cleanup에 전혀 영향을 주지
않는다. 기존 `TrialResult` 스키마는 건드리지 않았다 - 경로는 이미 있는
`result.notes`에 append(다른 비핵심 진단 정보들과 동일한 관례 재사용).

**C. 분석기 attempt 대응** (`correct_followup_138.py`):
`analyze_arm_corrected(arm, rep=1, run_id_override=None)` - override가
있으면 `rep` 숫자로 표준 경로를 재조립하지 않고 그 값을 그대로 쓴다
(기본값 None이면 기존 동작과 100% 동일).

**오프라인 검증 결과(파일별로 분리 - 실행 성공 여부가 다르다)**:

| 파일 | 검증 방법 | 결과 |
|---|---|---|
| `run_once.py` | `pytest test_run_once.py` 전체 | **57 passed, 3 skipped(live_cluster) - 회귀 0건** |
| `run_load_ramp_followup_trial.py` | `pytest test_run_load_ramp_followup_trial.py`(신규 6개) | **6 passed**(1개는 테스트 fixture의 `ensure_ascii` 버그로 최초 실패 → 수정 후 통과, 프로덕션 코드 결함 아니었음) |
| `correct_followup_138.py` | `pytest test_correct_followup_138.py` | **실행 자체가 안 됨 - numpy/OpenBLAS 메모리 할당 실패로 프로세스가 출력 없이 죽음(0절)** |
| 6개 파일 전부 | `python -m py_compile` | **문법 오류 0건(가장 가벼운 확인, numpy 안 씀)** |

`correct_followup_138.py` 변경은 2줄짜리 순수 파이썬 변경(매개변수 추가
+ 삼항 재대입, 새 numpy 사용 없음)이라 코드 리뷰 수준에서는 오류
가능성이 낮다고 판단하지만, **인터프리터 실행으로 확인하지 못한 건
사실이고, 이를 "검증됐다"고 보고하지 않는다.** 재시도하지 않았다 -
같은 명령을 다시 돌려도 로컬 자원 상태가 그대로면 같은 결과가 날 뿐이고,
지시된 "무기한 폴링·자동 재시도 금지"에 해당한다고 판단했다.

**실행기·분석기가 새 attempt ID를 실제로 지원하는지 교차 확인**(지시
§2A의 핵심 우려사항): `test_run_load_ramp_followup_trial.py`가 작성기
쪽(retry run_id로 정확한 파일에 씀)을, `test_correct_followup_138.py`에
추가한 `test_run_id_override_reads_retry_file_not_hardcoded_original`이
분석기 쪽(retry run_id를 주면 정확히 그 파일을 읽고, 표준 재조립 경로로
새지 않음 - 원본 999초 vs retry 15초로 값 자체를 다르게 만들어 대조)을
검증하도록 작성했다. **후자는 위 표의 이유로 이번 턴에 실행 확인을
못 했다** - 코드는 있지만 "통과를 확인함"이라고 말하지 않는다.

## 3. 실행 여부와 이유

**실행하지 않았다.** 라이브 재시도는 애초에 §143의 조건(commit
headroom ≥4GB)이 필요했는데, 이번 턴에 다시 잰 값은 그보다 훨씬 나쁘고
계속 나빠지는 중이다. 사용자로부터 "앱을 정리했다/재부팅했다"는 확인도
이번 턴에 없었다. 지시 그대로 - 조건 미충족이면 시작하지 않는다.

---

## 4. 원본 invalid ↔새 시도 연결

**아직 아무 연결도 생성하지 않았다** - 라이브 시도 자체가 없었으므로
연결할 실제 재시도 결과가 없다. 1절에서 설명한 대로 **연결을 만들 수
있는 코드(계약 스키마 필드, 충돌 거부, 원본 해시 기록)는 구현·부분
검증됐다** - 다음에 실제로 실행할 때 `--attempt-of load_ramp-fixed_
threshold-03-post_hoc_followup-v1 --attempt-suffix retry1 --replacement-
reason "..."` 형태로 쓰면 된다. 원본 파일(`trial-load_ramp-fixed_
threshold-03-post_hoc_followup-v1.json`, §142)은 이번 턴에도 읽기만
했고 전혀 수정하지 않았다.

## 6. 로컬 자원 추이 + 중단기준 발동 여부

**추이**: 2절 표대로 급격히, 지속적으로 악화(21분 사이 1,911MB →
109MB). **중단기준(1.5GB) 발동 여부**: 엄밀히는 "실행 중인 라이브
trial"에 대한 기준이라 이번엔 적용 대상 자체가 없었지만, **그 수치
자체는 이미 훨씬 전에 하회했다** - 만약 이 상태에서 라이브를 시작했다면
중단기준을 즉시, 크게 위반한 채로 시작하는 셈이었다.

**내 자신의 기여 가능성을 숨기지 않는다**: 이번 턴에 pytest·python
subprocess를 여러 번 실행했다(비교적 가벼운 것들이지만 0은 아니다) -
이게 22:09→22:30 악화의 전부인지 일부인지 지금 시점에서 정확히 분리할
수 없다(§143과 동일한 이유 - 실시간 이전 스냅샷이 있어야 정확히
분리되는데, 그런 기록이 없다). 다만 22:27→22:30(추가 명령을 최소화한
구간)에도 계속 나빠졌다는 점은, 내 프로세스 실행만이 원인은 아니라는
근거는 된다 - 그러나 이것도 확정은 아니다.

**제안(실행 안 함, 3절 권한 범위 그대로 유지)**: 상황이 §143 때보다
뚜렷이 나빠졌으므로, 사용자가 직접 확인·정리하거나(어떤 앱이 언제부터
얼마나 쓰는지는 사용자 화면에서 보는 게 가장 빠르다) 재부팅을
고려해보는 걸 다시 한번 권한다 - 어느 쪽도 내가 실행하지 않았고, 실행
전에는 반드시 사용자의 명시적 승인이 필요하다.
