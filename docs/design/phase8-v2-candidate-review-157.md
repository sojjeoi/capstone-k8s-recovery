# Phase 8 — §156 NO-GO 범위 확정 + v2 후보 검토 (읽기전용) (§157)

§140~§156 전부 보존(수정 0건). 코드 수정 0건, 클러스터 접속 0건, 새
실험 0건. §152의 0/40, 후속 5쌍 결과는 변경하지 않는다.

**§156 NO-GO의 범위 확정**: §156의 NO-GO는 **"현재 `load_ramp` +
동일 용량(active와 같은 스펙) BlueGreen 단일 pod 전환" 설계에 한정**된
결론이다 - 다른 대응 방식(용량을 다르게 하는 전환 등) 일반에 대한
NO-GO가 아니다. 이번 문서는 그 한정된 범위 밖에 있는 v2 후보 2개를
검토한다.

**결론 먼저: 1주 내 실행 가능한 v2 없음.** 아래 두 후보 모두 (a) §156
Q1·Q2에서 이미 확인한 탐지-시점 한계(대응 방식과 무관하게 남아 있음)를
그대로 물려받고, (b) 각자 다른 이유로 **현재 2-VM 클러스터(worker
node 1개, CPU 8코어, 메모리 ~15.62GiB, system-reserved carve-out
없음)의 이미 문서화된 자원 한계**에 걸린다. 억지로 하나를 고르지
않는다.

---

## 0. 두 후보 모두에 공통되는 제약 - 대응 방식과 무관

§156에서 이미 확인한 사실은 v2가 "무엇으로 대응하는가"와 무관하게
그대로 적용된다: 19개 유효 `load_ramp` trial 중 12개는 `t_first_bad`
자체가 주입 후 2초 안이라 **어떤 대응도 물리적으로 시간이 없고**,
텔레메트리가 있는 나머지 trial 중 실제 전조+충분한 여유가 함께 확인된
건 2개뿐(둘 다 `fixed_threshold`, `proposed` 사례는 0개)이다. **v2가
"탐지 뒤 무엇을 할지"를 아무리 잘 바꿔도, "언제 알 수 있는가"라는
상한은 §156에서 이미 확정된 것과 같다.** 이 상한을 넘어서려면 탐지
민감도 자체를 바꿔야 하는데, 그건 지시대로 이번 검토 범위 밖이다.
그래서 아래 두 후보는 **"안다면 무엇을 할까"**만 다루고, "더 빨리
알 수 있는가"는 다루지 않는다 - 이 자체가 v2의 상한 개선치를 이미
제한한다.

---

## 1. 후보 A — 수평 확장(승격 시 preview를 소용량 2 replica로 기동)

동일 용량 단일 pod 대신, 승격 대상을 **더 작은 CPU limit의 pod
2개**(예: 1.5코어씩, 합쳐서 지금의 3코어와 동일)로 구성해 부하를
분산한다.

1. **막으려는 장애의 전조**: §156과 동일(CPU 상승, 7개 중 2개만
   확인됨) - 이 후보 자체가 새 전조를 만들지 않는다.
2. **인과 경로**: 부하를 두 프로세스로 나누면 단일 pod CPU 포화가
   줄 것으로 기대되나, **불확실성이 크다** - vLLM은 연속 배치
   (continuous batching)로 동시 요청을 하나의 배치로 묶어 처리하는
   구조라, 같은 총 용량(3코어)을 2개의 더 작은 pod로 쪼개면 각
   pod의 배치 효율이 떨어져 **오히려 개별 pod가 더 쉽게 자기 몫
   (1.5코어)을 다 쓸 수 있다**(§10.3, `docs/design/phase8-blue-
   green-preflight-incident.md`: vLLM이 동시 요청 처리 시 limit을
   실제로 다 쓰는 워크로드임을 실측 확인) - 총 처리량이 늘어난다는
   보장이 없다.
3. **2-VM 클러스터 용량·preview 공존 가능성**: **불가능에 가깝다.**
   `sj-worker` 메모리 capacity는 **~15.62GiB**(`16380344Ki`, 같은
   문서 §10.1)이고, `vllm-serving` 1개 pod의 request/limit은 각각
   4Gi/6Gi(`rollout.yaml`)다. 지금도 active+preview(각 1개, 총
   2개)만으로 **8Gi 요청/12Gi 제한**(노드의 51%/77%)을 쓴다. 이
   후보는 승격 순간 active(1개) + preview(2개) = **pod 3개가 동시에
   떠야** 한다 - 요청 합계 12Gi(77%)는 스케줄링은 통과할 수 있으나,
   제한 합계 18Gi는 **노드 전체 용량(15.62GiB)을 이미 초과**한다.
   §10.1이 확인한 대로 이 노드는 system-reserved carve-out이 0이라,
   이 상태에서 실사용이 제한에 가까워지면 커널 프로세스와 직접
   경쟁한다 - **이미 한 번(§10, 4코어×2=8/8코어 상태) 겪은 것과
   같은 종류의 자원 고갈 위험**이다.
4. **첫 요청 피해 전 완료에 필요한 시간**: preview는 이 프로젝트
   전체가 항상 주입 **전에** 미리 준비해 둔다(§154 §3 S0 확인) -
   그래서 모델 로딩 시간(수십~수백 초)은 원칙적으로 탐지-전환 창을
   깎아먹지 않는다. 다만 pod가 2개로 늘면 **모델 가중치를 2번
   따로 적재**해야 해 준비 단계 자체의 실패 위험(메모리 부족으로
   Ready 실패)이 커진다 - §3의 결과(용량 초과)와 직결.
5. **오승격·추가 자원 위험**: 위 §3 자체가 직접적인 자원 위험이다.
   추가로, 2-replica 구성은 Service가 두 pod에 요청을 어떻게 분배
   하는지(라운드로빈 등)에 따라 개별 pod의 순간 부하가 불균등해질
   수 있어 오탐/오승격 판단에 새 변동 요인이 생긴다 - 미검증.
6. **구현·독립 검증 시간**: `rollout.yaml`의 pod template을 단일
   Deployment형 다중 replica 구조로 바꾸는 작업 자체가 BlueGreen
   단일-전환 전제를 벗어나는 재설계다. §151 후보 C(수평 확장)가 이미
   "설계+구현 최소 1~2일, 검증 별도"로 추정한 바 있다 - 거기에 §3의
   메모리 초과 문제를 먼저 풀어야 하는 부담이 더해져, **1주 안에
   구현+독립 검증까지 마치기는 빠듯하다(확인 필요, 낙관적으로도
   여유가 거의 없음).**

## 2. 후보 B — 수직 확장(승격 시 더 큰 단일 preview로 전환)

preview를 active와 같은 3코어가 아니라 **더 큰 limit**(예: 5코어)의
단일 pod로 미리 준비해 뒀다가, 그쪽으로 전환한다.

1. **막으려는 장애의 전조**: 후보 A와 동일 - 새로 만들지 않는다.
2. **인과 경로**: 후보 A보다 **더 직접적**이다 - 같은 워크로드를
   더 큰 CPU 한도의 단일 pod가 처리하면(연속 배치 효율은 유지되면서
   한도만 늘어남) 같은 RPS에서 지연이 낮아질 것으로 기대할 수 있다 -
   §151 후보 C가 "부하 자체를 여러 pod로 분산"보다 더 단순한 형태의
   같은 논리(용량 확대)다.
3. **2-VM 클러스터 용량·preview 공존 가능성**: **이미 한 번 겪은
   사고와 같은 조건을 그대로 재현한다.** active(3코어, 기존) +
   preview(5코어, 이 후보) = **8/8코어(100%) 제한 합계** - 정확히
   `docs/design/phase8-blue-green-preflight-incident.md` §10이
   "2-vLLM=8/8코어 100%" 상태로 지목하고, 그 대응으로 vLLM limit을
   4→3코어로 낮춘(§10.6) **바로 그 상태**다. 메모리도 비례해 늘리면
   (예: preview 8~10Gi) 활성+preview 합계가 14~16Gi로 노드 총량
   (~15.62GiB)에 근접하거나 넘는다. **이 노드에서 이미 실제 사고로
   이어졌던 구성을 다시 만드는 것**이라 위험이 가장 명확하다.
4. **첫 요청 피해 전 완료에 필요한 시간**: 후보 A와 동일 논리로
   사전 준비 자체는 탐지-전환 창을 깎지 않으나, §3의 자원 위험이
   준비 단계 자체(모델 로딩 중 자원 경쟁)를 불안정하게 만들 수 있다.
5. **오승격·추가 자원 위험**: **가장 높음** - §3에서 지목한 구성이
   과거 실제 NodeNotReady류 사고와 시간적으로 연관된 것으로 이미
   기록돼 있다(`docs/design/phase8-blue-green-preflight-incident.md`
   §3, §10). 이 구성을 다시 만드는 건 v2 검증 자체를 위험에 빠뜨릴
   수 있다.
6. **구현·독립 검증 시간**: `rollout.yaml` 1줄(preview 전용 limit)
   변경만으로는 안 되고(BlueGreen이 active/preview에 같은 template을
   쓰는지 다른 template을 허용하는지부터 확인 필요 - **확인 필요**),
   §3의 위험을 감안한 신중한 단계적 검증(예: 노드 자원을 계속
   모니터링하며 낮은 부하부터)이 필요해 **1주 예산으로는 구현보다
   안전 검증에 더 많은 시간이 들 가능성이 높다.**

---

## 3. 종합 판정: 1주 내 실행 가능한 v2 없음

- **후보 A**: 인과 경로 자체가 불확실(vLLM 배치 특성상 분산이 오히려
  역효과일 수 있음) + 메모리 제한 합계가 이미 노드 총량을 초과.
- **후보 B**: 인과 경로는 더 명확하지만, **이 클러스터에서 이미 한
  번 실제로 겪은(§10) 자원 고갈 구성을 그대로 재현**한다.
- 둘 다 §0의 탐지-시점 상한(대응과 무관하게 §156에서 이미 확정)을
  넘어서지 못하며, 그 위에 각자 다른 방식으로 **이미 문서화된 이
  클러스터의 실제 자원 한계**에 부딪힌다.
- `load_ramp` 강도를 완화하거나 기존 결과를 v2 성과로 재사용하는
  방식은 검토하지 않았다(지시대로 제외).
- **판정: 1주 내 실행 가능한 v2 조치 없음.** 억지로 후보를 구현안으로
  올리지 않는다.

§152의 0/40, 후속 5쌍 결과는 이번 검토로 바뀌지 않는다 - 그대로
보존한다. 판정 보고 후 멈춘다.
