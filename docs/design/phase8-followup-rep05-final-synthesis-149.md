`outcome=recovered, state=completed`. 자원 모니터링 중 물리 free RAM이

## 8. rep03·rep05의 긴 회복시간 — 확인된 시간관계로만 보고(원인 아님)

**확인된 사실(둘 다 원자료에서 직접 읽음, 새 실험 없음)**:
- rep03 proposed: 탐지→전환 6.07초(빠름), 전환→실제 SLO회복까지
  추가 104.49초.
- rep05 proposed: 탐지→전환 4.27초(더 빠름, t_slo 겨우 1.28초 뒤
  탐지), 전환→실제 SLO회복까지 추가 **448.56초**.
- 두 사례 모두 `decision_outcome=executed_verified` - 조치 자체는

  빠르지 않은 게 아니라 오히려 매우 빨랐다(둘 다 10초 미만).
- 10개 trial 중 이 두 사례(rep03·rep05의 proposed)만 "탐지가 첫
  episode 시작과 가깝거나 이전"이었고, 동시에 이 두 사례가 recovery_
  sec 최댓값 1·2위(454.11s, 103.30s)다 - 나머지 8개는 recovery_sec이
  전부 30초 이하다.

**이걸 "전환 후 회복이 느려서"라는 사실 이상으로 원인을 특정하지
않는다.** §136(core 45건 분석)이 이미 지적한 것과 같은 성격의 공백
- "전환 후 새 pod가 실제로 SLO를 만족하기까지 걸리는 시간"의 원인
(워밍업·트래픽 전환 과도기 등)은 이번 5쌍 자료에도, core 45건에도
직접적 근거가 없다. **이번 턴에 이걸 밝히는 새 진단 실험이나 코드
변경을 하지 않았다** - 지시 그대로.

## 9. 5쌍 전체가 말해주는 것 — 일관성·변동성·추가비용

**방향 일관성 없음**: 6절 표대로 latency초과율 차이 부호가 5번 중
3번 바뀐다. **어느 쪽으로도 "매번 낫다"고 말할 수 없다.**

**변동성 자체가 크다**: fixed_threshold의 latency초과율 범위(4.78~
8.00%, 폭 3.22%p)보다 proposed의 범위(6.00~10.33%, 폭 4.33%p)가 더
넓다 - proposed가 반복 간 변동이 더 크다는 것 자체는 확인된 사실이다
(원인은 8절 그대로 미확인).

**추가 비용은 일관된다**: CPU·메모리 비용은 5쌍 전부 proposed가
fixed_threshold보다 높다(방향 100% 일관) - 이건 이번 5쌍에서 유일하게
반복마다 같은 방향으로 나온 지표다.

**n=5/arm으로 일반적 우월성·동등성을 입증했다고 말하지 않는다.**
core 45건과 마찬가지로(§136과 동일 원칙), 유의성 검정을 하지 않았고
표본이 작다 - 위 결론은 전부 "이번 5쌍에서 관측된 것"으로 한정한다.

## 10. 공식 core 45건의 회복시간 차이 ↔ 후속 900초 비교의 사용자 요청 피해 — 연결, 합산 아님

**공식 core 45건(§136, `mainexp-v2`, load_ramp)이 말해주는 것**:
`recovery_sec`(t_recovery−t_slo, streak 소급 정의) 중앙값 기준
proposed 124.57s vs fixed_threshold 226.17s(−44.9%, n=4/5 각각) -
**단, 이 수치는 `ramp.py`(원래 load_ramp 부하생성기)로 측정됐고,
§136이 이미 명시했듯 이 부하생성기에는 애초에 요청별 원자료(성공/
실패/latency)가 없다(0/15)** - 즉 core 45건의 load_ramp 결과는
"SLO 판정기가 정상으로 돌아왔다고 확정하기까지 걸린 시간"만 말해줄
뿐, **그 시간 동안 실제 사용자 요청이 몇 건 실패했고 몇 건이 지연
임계치를 넘었는지는 core 45건 자체에 없다.**

**이번 후속 5쌍(post_hoc_followup-v1)이 말해주는 것**: `probe.py`
계열 계측(`probe_followup.py`)으로 요청 ID 단위 성공/실패/latency를
직접 추적해, 고정 900초 관측창 안에서 실패율·latency초과율을 직접
잰다 - 이게 core 45건의 load_ramp가 답할 수 없었던 "실제 사용자
요청 피해"를 채우기 위해 §137부터 새로 만든 계측이다. 그 결과(5·6절)
는 반복마다 방향이 바뀌고, 특히 proposed 쪽 변동폭이 더 크다.

**연결(합산 아님)**: 두 자료는 **서로 다른 관측 조건**이다 - 서로
다른 부하생성기(`ramp.py` vs `probe_followup.py`), 서로 다른 시각에
실행된 서로 다른 trial(같은 trial을 두 번 잰 게 아니라 완전히 별개의
실행), 서로 다른 지표 정의(streak 기반 판정 시각 차이 vs 고정 900초
창 안 요청 단위 집계). **"core 45건이 44.9% 더 빠르다고 했으니
후속 5쌍도 그만큼 피해가 줄었을 것"이라고 두 수치를 합치거나
외삽하지 않는다** - 이건 방법론적으로 성립하지 않는 연산이다.

정직하게 말할 수 있는 연결은 이 정도다: **core 45건의 시간 기반
지표(recovery_sec)가 보여준 개선이, 이번에 직접 측정한 사용자 요청
단위 피해 지표에서는 일관되게 재현되지 않았다.** 이게 "core 45건이
틀렸다"는 뜻은 아니다 - 서로 다른 부하생성기·서로 다른 trial·서로
다른 지표이므로 애초에 같은 것을 잰 게 아니다. 다만 "recovery_sec이
빠르다 = 사용자 피해가 적다"는 등식이 이번 자료로는 자동 성립하지
않는다는 것 - 이게 애초에 §137에서 이 후속 비교를 시작한 이유였고,
5쌍을 다 채운 지금도 그 등식은 확인되지 않았다.

## 12. 발표에서 주장 가능한 것 vs 주장하면 안 되는 것

**주장 가능한 것(이번 5쌍 + core 45건 원자료로 직접 뒷받침됨)**:
1. 공식 core 45건(n=5/arm, load_ramp)에서 `recovery_sec` 중앙값은
   proposed가 fixed_threshold보다 낮다(124.57s vs 226.17s, −44.9%,
   기술통계, 검정 없음).
2. 이 개선은 무작위가 아니라 predictive 탐지가 실제 채택된 비율과
   대응한다(§136).
3. 후속 5쌍(고정 900초, 요청 단위 직접 계측)에서는 fixed−proposed
   latency초과율 차이의 방향이 5번 중 3번 바뀌었다 - 일관된 우열이
   관측되지 않았다.
4. 후속 5쌍에서 proposed의 detector CPU·메모리 비용은 매 반복
   fixed_threshold보다 높았다(방향 100% 일관, 약 2.6~10배 CPU,
   약 4배 메모리) - 이건 일관되게 관측된 비용이다.
5. proposed의 두 극단적 recovery_sec 사례(rep03·rep05)는 공통적으로
   "탐지·전환 자체는 빨랐으나 전환 후 실제 SLO 회복까지 추가로
   오래 걸렸다"는 시간관계를 보인다(원인은 미확인).
6. 10개 후속 trial 전부에서 detection_source=predictive,
   decision_outcome=executed_verified였고, 오승격·중복승격으로
   의심되는 감사 기록은 없다.

**주장하면 안 되는 것**:
1. proposed가 fixed_threshold보다 **일반적으로 우월하다**는 것 -
   core 45건의 시간 지표 개선과 후속 5쌍의 요청 단위 피해 지표가
   서로 다른 방향/일관성을 보였다.
2. proposed가 **동등하다**는 것도 마찬가지로 입증되지 않았다 - 5쌍
   중 3쌍은 fixed가 근소~뚜렷하게 유리했다.
3. n=5/arm(후속)이나 n=5/arm(core, 시나리오당)으로 **통계적 유의성**을
   확보했다는 것 - 두 분석 모두 검정을 하지 않았고 하지도 않는다.
4. core 45건의 recovery_sec 개선(44.9%)을 후속 5쌍의 사용자 요청
   피해 감소로 **환산·합산**하는 것 - 서로 다른 계측·조건의 자료를
   그렇게 연결할 근거가 없다(10절).
5. rep03·rep05의 긴 회복시간의 **원인**(워밍업 등)을 확정하는 것 -
   시간관계만 확인됐고 원인은 미확인이다.
6. "추가 비용(CPU·메모리)이 크므로 proposed를 쓸 가치가 없다"는
   것도 마찬가지로 과도한 결론이다 - 비용은 일관되게 크지만, core
   45건의 시간 개선과 후속 5쌍의 피해 지표가 상충하는 상황에서
   "가치 판단" 자체를 이 자료만으로 내릴 근거는 없다(비용 대 효과의
   "효과" 쪽이 이미 불확실하다).
