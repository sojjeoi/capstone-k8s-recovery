# Phase 8 — §154 판정 기준 재검토 및 정정 (읽기전용) (§155)

§140~§154 전부 보존(수정 0건, §154 원문 포함). 이번 턴도 **읽기 전용
판정 기준 재검토만** 한다 - 코드 수정 0건, 클러스터 접속 0건, 새 실험
0건, 새 분석 스크립트 0건. §153에서 **이미 계산해 저장해 둔**
`experiments/results/_precursor_timing_analysis_153.json`을 다시 읽기만
했다(새 계산 없음). **성능 GO/NO-GO나 구현 승인은 이번에도 내리지
않는다** - 판정 기준 자체의 오류만 정정하고 보고 후 멈춘다.

**결론 먼저**: **§154는 실제로 1차 목표를 완화했다.** §154 §4.3이
"성공"의 비교 시점을 `t_first_confirmed_bad`(확인된 지속 저하)로 바꾼
것은, 원래 목표("장애 관련 첫 사용자 요청 실패 또는 사전 고정된 지연
임계 초과 **전**에 전환 완료")를 조용히 더 쉬운 기준으로 바꾼 것이었다.
§153·§154가 "성공"이라고 부른 2건(`load_ramp-proposed-02/03-post_hoc_
followup-v1`)은 **원래(완화 전) 기준으로는 둘 다 실패**다 - 이미
계산된 `switch_before_firstbad` 필드가 두 건 모두 `false`임을 직접
확인했다(§2). 이 정정으로 "성공 2건"이라는 표현을 철회한다.

## 1. 이번 정정의 범위

- 다루는 것: §154의 **판정 기준**(무엇을 "성공"이라 부르는지)만.
- 안 다루는 것: §152의 0/40, §153의 시간예산·전조 탐색 원자료, §154의
  1~10절 원문 - 전부 그대로 둔다. 이 문서는 §154 §4.3(성공/실패/판정불가
  규칙)을 **대체**하는 정정 절이며, §154 파일 자체는 고치지 않는다.
- 새로 계산한 것 없음 - §153이 이미 만든 `_precursor_timing_analysis_
  153.json`을 다시 읽어 기존 필드(`switch_before_firstbad`,
  `injection_to_firstbad_sec`, `firstbad_was_isolated_singleton`,
  `injection_to_confirmedbad_sec`, `switch_before_confirmedbad`)만
  인용했다.

## 2. §154가 목표를 완화했는가 - 확인, 수치로

원래 1차 목표(사용자 재확인): "장애 관련 **첫** 사용자 요청 실패 또는
사전 고정된 지연 임계 초과 **전**에 실제 트래픽 전환이 완료됨" -
연산으로 쓰면 `t_switch < t_first_bad`(원 정의, 고립 단발 포함, 예외
없음)다.

§154 §4.3은 이걸 `t_switch < t_first_confirmed_bad`로 바꿨다.
`t_first_confirmed_bad`는 정의상 **항상 `t_first_bad` 이후이거나
같다**(고립 단발이 아니면 둘이 같은 시각, 고립 단발이면 `t_first_
confirmed_bad`가 더 늦다) - 그래서 이 대체는 **수학적으로 항상 더
느슨한(같거나 쉬운) 기준**이다. 실제로 차이가 나는 유일한 경우가
"고립 단발" trial이고, 정확히 그 경우에만 결과가 바뀐다:

| trial | `t_first_bad`까지(초) | `switch_before_firstbad`(원 기준) | `t_first_confirmed_bad`까지(초) | `switch_before_confirmedbad`(§154 기준) |
|---|---|---|---|---|
| `load_ramp-proposed-02-post_hoc_followup-v1` | 0.057 | **false** | 90.057 | true |
| `load_ramp-proposed-03-post_hoc_followup-v1` | 0.725 | **false** | 76.728 | true |

**두 건 다 원 기준으로는 `switch_before_firstbad=false`(실패)인데,
§154는 이걸 `switch_before_confirmedbad=true`(성공)로 보고했다.** 이건
"노이즈를 걸러내는 합리적 방법"이 아니라, **결과를 본 뒤 더 쉬운
비교 시점을 골라 성공으로 바꾼 것**이었다 - 이번 지시가 정확히 지적한
문제다. 이 두 사례를 "성공"이라고 부른 §153·§154의 표현을 철회한다.
§152의 0/40은 **원 기준으로 다시 봐도 그대로 0/40**이다(§6).

## 3. 세 지표의 분리 재정의 - 서로 대체 불가

앞으로 이 세 가지는 **항상 따로 계산·보고**하고, 어느 하나가 다른
하나의 대체물로 쓰이지 않는다:

| 지표 | 정의 | 용도 |
|---|---|---|
| **개별 피해(`t_first_bad`)** | 주입 이후, 개별 요청 단위로 실패 또는 지연>0.648s인 **첫 번째** 요청의 발신 시각. 정렬+첫 매치, 예외 없음(§152 방법 그대로) | **1차 목표의 유일한 공식 비교 시점.** 다른 지표로 바꿔치기하지 않는다. |
| **지속 저하 개시(`t_first_confirmed_bad`)** | §153이 만든 보조 지표("그 뒤 W초 안에 K건 더") - 사후 진단·설계 탐색용 | **독립적인 참고 통계일 뿐, 1차 목표 판정에 쓰지 않는다.** "전환이 이걸 앞섰다"는 사실은 계속 보고하되, "1차 목표 성공"이라고 부르지 않는다(§154의 원래 실수를 막기 위한 명시적 금지). |
| **사후 계산 `t_slo`(`slo_judge.find_t_slo`)** | 기존 정의(30초 지속조건 확정 후 스트릭 시작점으로 소급) | 기존 §136 이후 문서들의 "판정 확정" 기준으로만 계속 쓴다 - 1차 목표 비교 시점 아님(§152에서 이미 확정한 구분) |

## 4. 정정된 성공/실패/판정불가 규칙 (§154 §4.3을 대체)

- **성공**: `load_ramp` trial에서 `t_switch`(§7의 L2 증거 수준)가
  **`t_first_bad`(원 정의, 고립 단발 포함)보다 이전**이다. 예외 없음 -
  고립 단발로 보이더라도 이 비교 시점 자체를 바꾸지 않는다(§5).
- **실패**: `t_switch`가 `t_first_bad`와 같거나 이후, 또는 유효한
  신호/전환이 전혀 없었던 경우.
- **판정불가**: (a) `t_detection`/`t_switch` 필드 결측이나 trial 자체가
  기술적 실패인 경우, (b) §5에서 정할 사전고정 규칙으로 봤을 때
  `t_first_bad` 자체가 "장애 귀속 여부 불확실"로 분류되는 경우(단,
  이 (b) 경로는 **미래의 새 trial에만 적용** - 기존 40건에는 소급 적용
  안 함, §5·§6), (c) `pod_kill`·`network_degrade`(적용 대상 아님).
- `t_first_confirmed_bad`·`t_slo`와의 선후 관계는 **항상 함께 보고**
  하되(투명성 유지), 위 성공/실패/판정불가 결정에는 관여하지 않는다.

## 5. 고립된 느린 요청 처리 - 사전 고정 정상대조 + 판정불가 절차 (방법론만, 미실행)

**원칙**: "이 요청이 노이즈처럼 보인다"는 판단을 **결과를 본 trial
자신의 뒷부분(60초 뒤에 또 있었는지)으로 사후에 내리지 않는다** -
그건 §154가 이미 한 번 저지른 실수와 같은 종류다(다만 §154는 "성공"
쪽으로, 이 방법은 "판정불가" 쪽으로 완화한다는 차이만 있을 뿐, 여전히
같은 trial의 사후 정보로 판단한다는 문제가 남는다). 대신:

1. **사전 고정 절차(향후 실행, 이번 턴엔 미실행)**: 이미 저장된 모든
   arm·모든 trial의 **주입 전(pre-injection) 구간** 원자료(새 실험
   아님, 기존 파일만 읽음)에서 "건강한 상태의 단일 요청이 자연적으로
   0.648초를 넘는 배경 비율" `p_normal`을 잰다. 이건 §154 §9의 1단계와
   같은 작업이고, 이번에도 실행하지 않는다(코드 수정·새 실험 금지
   범위 밖 판단 - 순수 통계 집계라도 이번 지시의 "판정 기준 재검토"
   범위를 넘는 별도 분석이라 다음 승인 대상으로 남긴다).
2. **판정 절차(방법론만)**: 어떤 trial의 `t_first_bad`가 주입 후
   `n`번째 요청 이내에 나왔다면, `p_normal`과 `n`으로 "우연히 이
   시점까지 최소 1건의 자연 위반이 나올 확률"을 계산한다(예: 이항
   분포 근사). 이 확률이 사전에 정한 유의수준(예: 0.05)보다 **크면**
   -즉 노이즈로도 충분히 설명되면- 그 trial의 `t_first_bad`는 "장애
   귀속 불확실"로 표시하고, 1차 목표 판정을 **판정불가**로 낸다.
   확률이 유의수준보다 **작으면** 그 `t_first_bad`는 장애 귀속으로
   보고 §4의 성공/실패 규칙을 그대로 적용한다.
3. **소급 적용 금지(중요)**: 이 절차는 **앞으로 수집할 새 trial에만**
   적용한다. 이미 어떤 2건이 이 절차로 "판정불가"가 될지 알고 있는
   상태에서(§2) 그 2건을 지금 "판정불가"로 재분류하면, 방향만 다를 뿐
   §154와 같은 문제(결과를 안 뒤 유리한 범주로 옮기기)가 된다. 그래서
   **기존 40건은 이 문서의 §6처럼 원 기준(고립 단발 구분 없음)으로만
   재확인하고, 이 사전대조 절차로 재분류하지 않는다.**

## 6. 기존 40건 재적용 - 원 기준으로 재확인 (새 계산 없음, 기존 값 재인용)

§153이 이미 계산해 둔 `switch_before_firstbad` 필드를 그대로 다시
읽었다(§1). **원 기준(`t_switch < t_first_bad`, 고립 단발 구분 없음,
예외 없음)으로는 40개 trial 중 성공이 0건이다** - §152가 이미 확정한
0/40과 정확히 같은 결론이고, §153·§154 어디에서도 이 수치 자체를
바꾼 적은 없다(바뀐 건 "2건을 무엇이라 부를지"였을 뿐). 이번 정정으로
명확히 한다: **§153의 "확인된 저하 대비 2건 성공"은 여전히 사실(그
자체로는 정확한 관측)이지만, 1차 목표의 성공 사례로 세지 않는다.**

## 7. `t_switch`(L2 증거)만으로 "요청이 새 pod에 도달했다"고 주장할 수 있는가

**아니오 - 할 수 없다.** §154 §5에서 이미 L0~L5 단계를 나눴는데, 이번
지시대로 그 경계를 더 명확히 좁힌다.

### 7.1 지금 실제로 입증 가능한 주장 (L2까지)

> "정책이 promotion을 요청한 뒤, Service `vllm-active`의 selector가
> `vllm-preview`와 일치하는 상태를 `t_switch`(관측 오차: 폴링 간격
> 0.5초, 관측창 최대 5초, `rollouts_client.py: promote()`) 시점에
> 관측했다."

이게 전부다. 이 문장은 **Service 객체(API 수준)의 상태 변화**만
말한다.

### 7.2 이 주장이 **뒷받침하지 못하는** 것 (전부 별개의 미확인 단계)

1. **Endpoint/EndpointSlice 갱신(L3)** - Service selector 변경과
   Endpoint 컨트롤러의 실제 반영은 별도의 비동기 reconcile 루프다.
   같은 코드에 Endpoint를 직접 조회하는 부분이 없다 - 확인 필요.
2. **네트워크 경로 실반영(L4)** - kube-proxy(또는 해당 dataplane)가
   새 Endpoint를 실제 라우팅 규칙에 반영했는지도 코드로 확인된 바
   없다.
3. **기존 연결의 지속(추가로 새로 짚는 지점)** - `probe.py`가 요청마다
   새 TCP 연결을 여는지, 아니면 커넥션을 재사용(keep-alive)하는지
   확인 안 됐다 - 재사용한다면 Service/Endpoint가 전부 바뀌어도 **이미
   맺힌 연결은 한동안 계속 구 pod로 갈 수 있어**, L2~L4가 전부 끝나도
   당장 다음 요청이 새 pod로 간다는 보장이 없다. **확인 필요.**
4. **요청↔pod 매핑(L5)** - `probe.py`/`ramp.py` 원자료 어디에도 요청별
   pod 식별자가 없다(§152 §6, §154 §5와 동일 공백 - 이번에 다시
   확인해도 변함없음). 그래서 "이 요청은 새 pod가 처리했다"는 문장은
   **어떤 trial에서도 직접 증명된 적이 없다.**

**결론**: `t_switch`는 "라우팅 설정이 바뀐 시점"의 근사치를 줄 뿐,
"트래픽이 실제로 새 pod에 도달·처리됐다"는 주장의 증거가 아니다.
이번 지시대로, 이 공백을 명시하고 `t_switch`가 증명하는 범위를 §7.1의
한 문장으로 좁혀 둔다.

### 7.3 새 버전에 필요한 요청별 pod 확인 증거 (구현 안 함, 목록만)

| 방법 | 확인 대상 | 비고 |
|---|---|---|
| 응답에 서빙 pod 식별자 주입(예: `X-Served-By` 헤더, vLLM 컨테이너나 사이드카에서) | L5 직접 | 서빙 이미지/배포 변경 필요 - 코드 변경 |
| `probe.py`가 매 요청마다 이전 요청과 다른 연결을 강제(커넥션 재사용 끄기) + 응답 pod 식별자 병행 | L5, §7.2-3의 커넥션 재사용 문제 동시 해결 | 코드 변경 필요, 다만 부하 패턴이 살짝 달라질 수 있어 기존 trial과 비교 조건이 바뀜(별도 검토 필요) |
| Endpoint/EndpointSlice를 `t_switch` 전후로 직접 폴링(추가 계측) | L3만 | L5보다 약하지만 서빙 이미지 변경 없이 가능 |
| 전환 직후 저지연 "canary" 프로브를 별도로 보내 응답 특성(예: 콜드스타트로 인한 지연 변화) 관찰 | L5의 간접 정황 증거만 | 직접 증명 아님 - §150/151이 이미 관찰한 "전환 후에도 저하 지속" 현상과 정합적이라는 정황일 뿐(부하가 새 pod에서도 계속되고 있다는 간접 신호로 해석 가능하나, 확정적 증거로 격상하지 않는다) |

어느 것을 채택할지, 채택 시 §154 §9의 검증 순서 어디에 넣을지는
**미해결 결정으로 남긴다** - 이번 턴은 공백을 정확히 표시하는 데까지만
한다.

## 8. 범위 확인 - 다음 단계 없음

이번 정정은 §154의 판정 기준 오류(§2)를 고치고, 세 지표를 분리하고
(§3), 성공/실패/판정불가 규칙을 다시 쓰고(§4), 고립 단발 처리 방법론을
제시하고(§5, 미실행), `t_switch`의 증거 범위를 좁힌 것(§7)뿐이다.
**성능 GO/NO-GO나 구현 승인은 내리지 않는다.** §154 §9(검증 순서)의
1단계(정상 배경 비율 측정)는 이 문서의 §5-1과 같은 작업이며, 여전히
**사용자 승인 대기 상태**로 둔다.
