# Phase 8 — 서비스 피해·비용 재검증 + 후속 비교 계약 (§137)

> 최종 질문: 고정 임계치 대비 추가된 AI 탐지가 실제로 어떤 서비스 피해를
> 줄였고, 어떤 조건에서는 추가 가치가 없었는가?

**이 문서와 §136(`phase8-effect-cost-analysis.md`)의 관계**: §136을
대체하지 않는다. §136의 계산(중앙값·범위·산식)은 그대로 유효하다.
이 문서는 §136이 다루지 않은 것 — 두 arm의 **실행 경로 자체가 코드
수준에서 얼마나 같고 다른지**, 그리고 그 차이가 §136의 헤드라인
수치(44.9%/24.6%/2.1%)를 **어떻게 재해석해야 하는지**를 다룬다.
아래에서 §136의 특정 서술을 정정하는 곳은 명시적으로 "정정"이라고
표시한다 — 조용히 덮어쓰지 않는다. 클러스터 미접속, 기존 원자료·
모델·SLO·판정 로직 전부 미변경(읽기 전용). 재현:
`experiments/analyze_effect_cost_evidence.py`(이번 턴에 §7~§9 함수
추가, §3~§6은 무변경 + 1건 버그 수정 — 아래 0절).

### 1.3 핵심 재해석 — "실제 판단에 기여한 사례" 재확인(코드+audit-log 전수 대조)

`recovery-policy/main.py` 코드 확인 결과: `detection_source`/`detector`는
"이 trial에서 **최초로** 유효 판정된 신호"의 것으로 한 번만 기록되고
이후 절대 안 바뀐다 — 반면 **실제로 promotion을 실행시킨 신호**는
이론적으로 더 나중에 온 다른 출처의 신호일 수 있다(반응형이 먼저
관찰만 하고 예측 신호가 나중에 실제 승격하는 경우). 그래서 이번 턴에
30건 전수에 대해 TrialResult의 `detector`와 **실제 audit-log
executed_verified/unverified 레코드의 `evidence.detector`**를 별도로
대조했다(`analyze_effect_cost_evidence.py` §7).

**결과: 27건의 executed 레코드 전부에서 불일치 0건** — `detection_source`가
가리키는 detector가 실제로 그 승격을 실행시킨 detector와 항상 같았다.
단, 반응형(Alertmanager) 경로는 애초에 payload에 `detector` 필드가 없어
`evidence.detector`가 항상 `None`으로 남는다 — 이 경로는 이 방식으로
"교차검증"할 수 없고, "예측 경로가 실제로 실행시켰는가"만 이 방식으로
확정 가능하다(그리고 예측 경로 15건 전부 확정됨: 불일치 없음).

**더 중요한 재발견 — 시나리오별로 "비교의 성격 자체"가 다르다**:

반응형 fallback의 트리거(`up==0` 30초)가 **어떤 고장 유형에서 발동
가능한지**가 시나리오마다 근본적으로 다르다 — 이것이 왜 개선폭이
44.9% → 24.6% → 2.1%로 좁아지는지의 구조적 원인이다:

| 시나리오 | 반응형 발동 가능성 | fixed_threshold 실제 전환(executed_verified) | proposed 실제 전환 |
|---|---|---|---|
| load_ramp | **불가능**(pod는 살아있고 계속 스크랩됨 — `up`이 0이 될 이유가 없음) | **2/4**(유효 반복 중) — 나머지 2건은 **탐지 자체가 전혀 없었음**(반응형도 예측도 무발화, native처럼 수동적으로만 회복) | **5/5** |
| pod_kill | **높음**(pod 소멸 → `up=0` 즉시) | 5/5(전량 반응형 경유) | 5/5(전량 예측 경유, 단 SLO 판정보다 항상 늦음) |
| network_degrade | **높음**(네트워크 저하가 Prometheus 스크랩 자체도 방해할 가능성) | 5/5(전량 반응형 경유) | 5/5(4/5는 반응형, 1/5만 예측) |

**정정(§136 대비)**: §136은 load_ramp/fixed_threshold의 n=4를 전부
"기술적으로 작동한 baseline"처럼 다뤘다. 실제로는 **4건 중 2건은
아무 탐지도 없었다**(rep3: 무탐지, recovery_sec=259.56s; rep4: 무탐지,
recovery_sec=193.57s) — 이 두 건의 "회복"은 fixed_threshold 메커니즘이
아니라 **개입 없이 시간이 지나 자연적으로 SLO가 정상범위로 돌아온 것**
(native와 같은 성격)이다. 실제로 탐지+실행이 일어난 2건은 rep2
(41.0s, 빠름)와 rep5(258.8s, 느림 — 실행됐어도 항상 빠른 건 아님)이다.

**이것이 바꾸는 해석**: load_ramp의 "44.9% 감소"는 "같은 방식, 더
빠른 버전"이 아니라 **"proposed는 5/5 항상 개입하고, fixed_threshold는
4건 중 2건만 개입한다(50%) — 나머지 절반은 개입 자체가 없다"**는
가용성(engagement rate) 차이가 상당 부분을 차지한다. pod_kill·
network_degrade는 반응형이 있어 양쪽 다 5/5 개입하므로 이 문제가
없다 — 그래서 이 두 시나리오의 격차(24.6%/2.1%)가 순수하게 "메커니즘
간 시점 차이"에 더 가깝고, load_ramp의 격차는 "메커니즘의 존재/부재
차이"가 섞여 있다고 봐야 한다. 이것이 §136보다 정확한 설명이다.

## 2. Stage A — 서비스 피해 비교표 (요청 지정 9열, 정정된 수치)

정의(코드 확인, `collect_metrics.py`/`slo_judge.py`):
- **t_slo**: 60초 롤링 P95가 임계치(0.648s)를 넘는 상태가 30초간
  지속됨을 **확인한 시각**(스트릭 종료점 — 비-소급).
- **t_recovery**: 무위반이 30초간 지속됨을 확인했을 때, 그 **무위반
  스트릭이 시작된 시각**으로 소급 기록(§134 확인).
- **recovery_sec** = `t_recovery - t_slo`. "전체 SLO 위반시간"도 "사용자
  중단시간"도 아니다 — 대리 지표.
- **평가 가능 시간**: probe raw 원자료의 첫~마지막 `sent_at` 구간(요청이
  실제로 오간 구간만 — injection~run_end 전체를 쓰면 probe 시작 전
  대기시간을 "평가 가능한데 위반 없음"으로 잘못 채우게 됨).
- **timeout 처리**(코드 확인, `probe.py`): 모든 요청은 30초 하드
  timeout(`aiohttp.ClientTimeout(total=30)`). timeout이든 다른 예외든
  `except Exception`에서 **반드시 한 행을 남긴다**(`success=False`,
  `latency≈30s`, `status=None`) — 조용히 사라지지 않는다. rep3의
  30.143초 실패가 정확히 이 경로로 기록된 진짜 timeout이다.
- **관측종료 시 미완료 요청**: `probe.py`는 duration 종료 후 최대
  10초만 pending 요청을 기다리고 그 결과(`asyncio.wait`의 반환값)를
  버린다 — 그 10초 안에 안 끝난 요청은 **행 자체가 안 남는다**(직접
  관측 불가, 코드로 확인된 실제 공백). 아래 표는 마지막 30초 구간의
  기대 표본수 대비 결측을 추정치로만 제시한다.

## 3. Stage B — load_ramp/proposed 선제 전환 2건, 정밀 재조사

**결론 먼저(§136과의 차이)**: §136은 rep3·rep5를 "같은 패턴의 2개
사례"로 다뤘다. 이번 재조사로 **둘은 서로 다른 설명이 필요한 사례**
임이 드러났다 — 하나로 묶지 않는다.

| | rep3 | rep5 |
|---|---|---|
| t_switch → 심각 이벤트 | +29.3~34.3s (4건, 최악 30.14s 실패) | +30.6~35.5s (6건, 최악 5.9s 성공) |
| 전환 순간 **in-flight**(전환 전 발신, 전환 후 완료) 요청 | **0건** | **0건** |
| 심각 이벤트가 속한 stage | **stage-4 중간**(stage 시작 -47.9s, 끝까지 +14s 남음 — 경계 무관) | **stage-4 시작 직후**(stage 시작 겨우 +0.7s 뒤) |
| ramp.py 자체 stage 지표(같은 stage) | success_rate 0.963(27건 중 1실패), p95 5.5/p99 8.4 — **다른 4개 stage(모두 p95≈3.0-4.4)보다 뚜렷이 높음** | success_rate 1.0, p95 9.5/p99 12.1 — **역시 다른 stage보다 뚜렷이 높음, 게다가 stage 시작과 거의 동시** |
| 경쟁 설명 | 없음(ramp 자체 stage 경계와 무관 — mid-stage) | **있음**: stage-3(0.20RPS)→stage-4(0.30RPS) 부하 상승이 전환 후 29.9초 뒤 시작 — 심각 이벤트(+30.6s)와 사실상 동시 |

**해석(3단계 구분)**:
- **관측된 사실**: 두 사례 모두 (1) 전환 순간에 in-flight였던 요청은
  없다(즉 심각 이벤트는 "전환 전에 이미 보낸, 오래 걸린 요청"이
  아니라 전환 후 **새로 보낸** 요청이다), (2) ramp.py의 독립적인
  heavier 트래픽에서도 **같은 시간대에** 이례적으로 나쁜 stage 지표가
  동시에 나타난다(단일 probe 표본의 우연이 아니라는 방향의 corroborating
  evidence). (3) rep5의 심각 이벤트는 ramp.py의 stage-4 시작과
  0.7초 차이로 거의 동시다.
- **사실과 부합하는 가설**(미검증): (a) rep3처럼 stage 경계와 무관한
  경우, 승격 직후 이미 수립된 aiohttp 커넥션이 Kubernetes conntrack
  특성상 Service selector가 바뀌어도 **기존 연결은 계속 구(old) pod로
  갈 수 있다**(코드 확인: `probe.py`/`ramp.py` 둘 다
  `aiohttp.TCPConnector(limit=0)` + 기본 keepalive 사용, 매 요청마다
  새 연결을 강제하지 않음) — 전환 후 "신규 발신"처럼 보여도 실제로는
  구 pod로 갔을 가능성을 배제 못 한다. 이는 그럴듯한 메커니즘이지
  확인된 사실이 아니다(아래 Stage C 없이는 검증 불가). (b) rep5는
  ramp 자체의 예정된 부하 상승이 **경쟁 설명으로서 최소한 동등하게
  유력**하다 — 전환과 무관하게 일어났을 가능성을 배제할 수 없다.
- **아직 검증되지 않은 주장**: "전환이 이 저하를 유발했다"는 인과
  주장, "신규 pod가 아직 불안정했다"는 주장 — 둘 다 실제 처리 pod
  식별자가 없어 이 데이터만으로 확정 불가(사용자 지시 그대로 유보).

## 4. Stage C — 최소 후속 계측 설계 (미실행, 설계만)

우선 시나리오: **load_ramp**(§136 대비 이유 재확인 — 개선폭이 가장
크고, 선제 전환 후에도 저하가 발생한 사례가 있고, 반응형이 구조적으로
작동 못 해 순수 예측 메커니즘 평가가 가능한 유일한 시나리오). 이는
기존 결과를 본 뒤 선택한 **사후(post-hoc) 우선순위**임을 명시한다.

**필요 계측 6종과 구현 방식**:

| 계측 | 방식 | 판정/부하/라우팅 의미 변경? |
|---|---|---|
| 요청별 고유 ID, sent/complete 시각, 성공, latency | probe.py에 `uuid4()` 컬럼 추가 | 아니오(순수 추가 컬럼) |
| 요청 프로필·부하 stage | 기존 필드 그대로(변경 없음) | 아니오 |
| 실제 전환 시각·selector 변화 | 기존 `t_switch`/`rollouts_client.get_service_selector()` 폴링 추가 | 아니오(읽기 전용 폴링) |
| detector 평가/skip/신호 시각 | 기존 detector 로그 그대로(변경 없음) | 아니오 |
| active/preview/detector CPU·메모리 | **detector**: 로컬 서브프로세스이므로 `psutil`로 그 PID를 직접 샘플링(§7 — 클러스터 지표로는 못 잡음). **active/preview pod**: `kubectl top pod` 또는 기존 Prometheus 스크레이프 폴링 | 아니오(사이드카성 폴링) |
| **실제 처리 pod 식별** | 후보 A: 응답 헤더에 pod 이름 주입(vLLM 서빙 컨테이너 또는 앞단 프록시 설정 변경 필요) — **서빙 응답 경로 변경**. 후보 B: 요청 시각 기준으로 `kubectl get endpointslice`를 폴링해 그 순간의 backend 목록을 남기고 사후 대조(conntrack까지는 못 보지만 selector 변화 시점은 정밀화됨) — **판정 로직 변경 없음, 순수 관측** | **후보 A는 승인 필요**(아래 명시). 후보 B는 판정/부하/라우팅 불변, 계측만 |

> **명시적 결정 요청**: 실제 처리 pod를 확실히 알려면(위 후보 A) vLLM
> 서빙 응답에 pod 식별 헤더를 추가해야 한다 — 이는 "관측 코드 추가"를
> 넘어 **서빙 경로 자체의 변경**이다. 영향: 응답 크기/헤더 처리 오버헤드
> 극히 미미하게 추가, 두 arm에 동일 적용 시 비교 왜곡 없음, 다만 원본
> vLLM 배포 설정을 건드림. 대안(후보 B, endpointslice 폴링)은 서빙을
> 건드리지 않지만 "그 순간 selector가 가리키는 대상"만 알 뿐 "그
> 특정 요청이 실제로 그 pod에서 처리됐는지"(conntrack 수준)까지는
> 확인 못 한다. **이 turn에서는 후보 A를 구현하지 않는다** — 사용자
> 승인 없이는 서빙 경로를 바꾸지 않는다(지시 그대로). 승인 시 후보
> A를, 승인 전까지는 후보 B만 준비한다.

**계측 자체의 최소성**: 요청마다 무거운 관리 명령(`kubectl` 등)을
호출하지 않는다 — endpointslice/자원 폴링은 요청과 **독립적인 주기**
(예: 5초 간격)로 별도 실행하고, 양쪽 arm에 동일하게 적용한다.

**오프라인 검증 항목(라이브 실행 전 필수, 이번 턴엔 코드 미작성이므로
미실행)**:
- 계측 실패(폴링 예외 등)가 원 요청의 success/latency 판정에 영향을
  주지 않는지 — 별도 컬럼/파일로 완전히 분리해 확인.
- 결측·timeout·미완료 요청이 그대로 보존되는지(빈 값으로 채우지 않음).
- 요청 ID 중복, timestamp 역전(시계 오차) 자동 탐지.
- 원본 동결 artifact(모델 해시·threshold·SLO 정의)가 계측 추가 전후로
  동일한지 hash 대조.
- 두 arm에 계측 코드 경로가 100% 동일하게 적용되는지(분기 없음).

## 5. 후속 비교 계약 — 라이브 실행 전 고정 (사전등록)

결과를 보기 전에 아래를 동결한다. 이후 결과를 보고 창·지표·분모를
바꾸지 않는다 — 필요하면 원 분석과 구분한 탐색적 분석으로만 남긴다.

**주 평가 지표(동일 probe 프로필 기준)**:
1. latency threshold(0.648s) 초과 비율 — 분모: 해당 arm·rep의 평가
   가능 구간 내 전체 probe 요청 수.
2. 요청 실패 비율 — 분모: 동일.

**보조 지표**(주 지표와 이중 집계 방지 — 실패 요청은 "실패 수"에만
넣고 "지연 수"에는 안 넣는다. 둘을 합쳐 "피해 요청 수"로 묶어 쓰려면
`실패 OR 지연` 합집합으로 명시하고 절대 합산(실패+지연)으로 세지
않는다):
- 평가 가능 시간 대비 SLO 위반 누적시간·비율.
- 기존 정의의 recovery_sec.
- 탐지→판단→API요청→전환 지연.
- detector 자원 사용(§4 계측, 확보 시).
- 전환 횟수·탐지 경로(predictive/reactive, executed 레코드의
  evidence.detector 기준 — §1.3 방식 그대로).

**관측 구간·포함 기준**: probe raw 원자료의 첫~마지막 `sent_at`
구간만 "평가 가능"으로 센다(§2 정의와 동일). trial 종료 후 10초
grace 안에 완료 못 한 요청은 원천적으로 기록이 없다는 한계를 그대로
인정한다(허위로 채우지 않음).

**하니스 중립성 확인(코드 확인 완료)**: `chaos/loadgen/ramp.py`의
stage 루프는 `config["stages"]`를 정해진 `duration_sec`만큼 순서대로
도는 것으로 끝이다 — promotion/탐지 상태를 전혀 참조하지 않는다.
즉 **promotion이 load_ramp의 부하 스케줄을 종료시키거나 부하 대상을
바꾸지 않는다** — 이것은 의도된 시스템 효과가 아니라 애초에 하니스가
그런 결합을 갖고 있지 않다는 뜻이다. 후속 실험에서도 이 하니스를
그대로 재사용하며 이 동작을 바꾸지 않는다.

**부하 스케줄·관측종료 규칙**: 두 arm 모두 기존 `scenario-load-ramp.yaml`
그대로(5 stage, 동일 RPS 스케줄) — 변경 없음, 양쪽에 동일 적용.

**plan_id/네임스페이스**: 실행한다면 `plan_id=post_hoc_followup-v1`,
결과 파일은 `results/trial-*-post_hoc_followup-v1.json` 등 기존
`mainexp-v1`/`mainexp-v2`와 겹치지 않는 접두사를 쓴다. 기존 45건에
합산하지 않고, `load_authoritative()`의 core 집합에도 포함하지
않는다(별도 로더로만 읽음).

## 6. 라이브 승인 범위 평가 — 이번 턴 실행 여부

사용자가 제시한 6개 선행조건을 현재 상태와 대조한다:

| 조건 | 상태 |
|---|---|
| 기존 자료로 해결 못 하는 질문이 명확함 | **충족** — 실제 처리 pod, ramp-stage-confound 여부는 기존 45건으로 못 푼다(§3 결론) |
| 추가 계측이 판정·부하·라우팅 의미를 안 바꿈 | **부분 미충족** — 후보 B(계측만)는 충족하지만, pod 식별의 확실한 방법(후보 A)은 서빙 경로 변경이 필요하고 아직 승인받지 않음(§4) |
| 비교 계약과 코드·artifact hash가 사전 기록됨 | **미충족** — §5는 지표·창·규칙을 동결했지만, 계측 **코드 자체가 아직 작성되지 않았다**(hash를 기록할 대상이 없음) |
| 오프라인 검증 통과 | **미충족** — 계측 코드가 없으므로 검증 자체가 수행 불가 |
| 기존 클러스터 안전·연결·정리 검사 통과 | **미확인** — 이번 턴은 클러스터에 접속하지 않았다(지시 범위 - 읽기전용) |
| 2 trial + cleanup 예상시간이 90분 이내 | 예상은 가능(기존 load_ramp 1회 관측시간 참고 시 여유 있음)하나 나머지 조건 미충족으로 의미 없음 |

**결론: 이번 턴은 라이브 실행을 하지 않는다.** 6개 중 최소 3개
(계측 코드 미작성 → hash 사전기록 불가 → 오프라인 검증 불가)가
연쇄적으로 미충족이고, pod 식별 방법(후보 A vs B) 자체도 아직
사용자 결정을 기다리는 상태다(§4). 차단 사유는 "결과가 나쁠까봐"가
아니라 **"사전조건이 되는 산출물(계측 코드, 오프라인 검증, 승인)이
아직 존재하지 않기 때문"**이다 — 조건이 갖춰지면 §5의 동결된 계약
그대로 즉시 실행 가능한 상태로 설계해 뒀다.

## 7. 비용·오탐 해석

**비용 구분**:
- **공통 비용**(두 arm 동일): BlueGreen preview 유지. §136에서 이미
  측정 — 시나리오별 중앙값 136.7~235.6s 범위, arm 간 차이 미미.
- **방식별 추가 비용**(detector CPU·메모리): **미측정, 0/45**(§136·
  §2 표 재확인). 이번 코드 조사로 **왜 지금까지 측정이 어려웠는지**는
  분명해졌다 — detector(`score_server.py`/`fixed_threshold.py`)는
  **클러스터 밖 로컬 서브프로세스**로 돈다(`arm_controller.py`,
  `kubectl port-forward` 전제). **클러스터 지표(`kubectl top pod`
  등)만으로는 이 비용을 절대 측정할 수 없다** — 측정하려면 로컬
  프로세스 PID를 `psutil` 등으로 직접 샘플링해야 한다(§4 계측 항목).
  recovery-policy 서비스 자체는 클러스터 안에서 돌지만, 이건 두 arm이
  공유하는 컴포넌트라 "proposed의 추가 비용"이 아니다.
- **운영 부담**(학습·설정·배포·유지보수): 정성적으로만 언급 —
  Isolation Forest는 모델 학습·threshold 재검증(홀드아웃) 절차가
  추가로 필요하고(`anomaly-detection/v3/model_v32b/` 일체), fixed_threshold는
  임계치 값 하나만 클러스터 자원 설정과 맞춰 관리하면 된다. 정량화된
  인시(person-hour)나 금액 산정 근거는 없다 — 계산하지 않는다.

**오탐(false positive) 해석 원칙**:
- model_v32b의 사전 holdout 평가(idle/low_load 6세션, §136에서 이미
  인용)는 point-level FPR 5.78%이지만 **실신호(연속3회+cooldown)
  기준으로는 0/6 episode** — 단, 이 holdout은 load_ramp처럼 부하
  자체가 오르내리는 조건에서 측정된 게 아니다. 이 수치를 모든 부하
  수준으로 일반화하지 않는다(§136과 동일 원칙 유지).
- **장애 trial(45건)에서의 "오승격 의심 0건"과 위 정상-holdout FPR은
  서로 다른 것을 측정한 별개의 근거다** — 혼동하지 않는다(사용자
  지시 그대로).
- 실제 전환 횟수는 §2 표에 건수로만 제시했다 — 각 실행이 "불필요"
  했는지 판단할 독립적 근거(예: 그 시점에 실제로 SLO가 이미 정상이었는지
  등)가 없으므로 어떤 전환에도 "불필요"라는 라벨을 붙이지 않았다.
- 금액·산업 절감액·인력 절감시간: 계산하지 않는다(실제 근거 없음).

## 8. 최종 산출물 및 3단계 결론

**산출물 목록(요청한 7항목)**:
1. 서비스 피해 비교표 — §2.
2. 선제 전환 2건의 증거 기반 타임라인 — §3.
3. 계측 가능/불가능 항목과 한계 — §2 정의부 + §4.
4. 사전등록한 후속 비교 계약 — §5.
5. 첫 비교 1쌍 실행 결과 — **해당 없음**(§6에서 실행 안 함으로 결론).
6. 실행하지 못한 정확한 차단 사유 — §6 표.
7. 추가 반복 필요성과 근거·예상시간 — 아래.

**추가 반복에 대한 판단**: 첫 쌍조차 아직 실행하지 않았으므로 "반복
횟수"를 이번에 확정하지 않는다. 다만 §4/§5 설계를 실제 실행 단계로
넘길 때를 대비해 원칙만 미리 명시한다 — 탐지 성공/실패와 무관하게
고정된 반복 수(5회, 기존 core cell과 동일 규모 — 이 프로젝트 전체의
"n=5, 기술통계 목적" 관례를 따름)를 사전에 정하고, arm 순서를
교차(fixed→proposed, 다음 세션엔 proposed→fixed)하며, 이번 승인
범위(§6 결론: 실행 안 함)를 자동으로 확대하지 않는다 — 조건이
갖춰진 뒤 별도 승인을 받는다.

**3단계 결론**:

- **관측된 사실**: (a) core 45건 기준 세 시나리오 모두 proposed의
  recovery_sec 중앙값이 낮다(§2). (b) load_ramp에서 fixed_threshold의
  실제 개입은 4건 중 2건뿐이었고 나머지 2건은 무개입 자연회복이었다
  (§1.3, §0 정정 반영). (c) pod_kill에서 요청 실패율은 fixed 32.8%
  vs proposed 21.8%로, recovery_sec보다 더 큰 상대 격차를 보인다(§2).
  (d) network_degrade는 양쪽 arm 모두 대부분 반응형 경로로 수렴하고
  (§1.3), recovery_sec 격차는 2.1%로 사실상 미미하다. (e) rep3·rep5의
  전환 후 심각 이벤트는 둘 다 in-flight 잔류 요청이 아니라 신규 발신
  요청이었다(§3). (f) rep5의 사건은 ramp.py 자체의 예정된 부하 상승
  시점과 0.7초 차이로 거의 동시에 일어났다(§3) — rep3에는 이런
  경쟁 설명이 없다.
- **사실과 부합하는 설명/가설(미검증)**: (a) load_ramp의 개선폭은
  "메커니즘 간 속도 차이"보다 "개입 여부 자체의 신뢰성 차이"가 더
  크게 기여했을 가능성. (b) rep3의 지연된 저하는 승격 후에도 기존
  aiohttp 커넥션이 conntrack 특성상 구 pod로 계속 향했을 가능성
  (코드상 가능하지만 미확인). (c) rep5는 전환과 무관하게 ramp 자체의
  부하 상승만으로 설명될 수 있는 가능성이 rep3보다 훨씬 크다.
  (d) network_degrade의 낮은 개선폭은 두 arm 모두 네트워크/지연
  피처가 없는 예측 모델을 쓰고 실질적으로 같은 반응형 경로에 의존하기
  때문일 가능성.
- **아직 검증되지 않은 산업 적용 주장**: "Isolation Forest 기반
  탐지가 고정 임계치보다 일반적으로 우월하다", "이 결과가 다른
  서비스·다른 부하 패턴에도 적용된다", "추가 비용이 개선 효과보다
  작다"(자원 비용 자체가 미측정) — 전부 이 45건짜리, 단일 클러스터,
  단일 서비스(vLLM) 실험만으로는 주장할 수 없다.

"개선 없음"에 해당하는 정직한 결론도 하나 포함한다: **network_degrade
에서는 recovery_sec 기준으로 두 arm의 차이가 실질적으로 없다고 보는
것이 안전하다**(2.1%, n=5, 게다가 대부분 같은 반응형 메커니즘에
의존) — 이 시나리오에서 Isolation Forest를 쓸 추가 가치는 현재
근거로는 확인되지 않는다.
