# Phase 8 — §138 정정 + 계측·분석 완결성 확보 (§139)

이번 지시는 §138의 후속 비교 결과를 정정하고, 추가 반복 전에 계측·분석의
완결성을 확보하는 것이었다. **코드 수정·오프라인 테스트·기존 evidence
재분석만 수행했다 — 라이브 클러스터 접속, 부하 생성, 추가 trial, 재시도는
0건.** 기존 core 45건과 후속 첫 한 쌍의 원본 결과·state·CSV·evidence·
cost·contract 파일은 전혀 건드리지 않았다(전부 읽기만 함). 정정 산출물은
`experiments/correct_followup_138.py`(신규)로 분리했다 — §138 문서와
`analyze_followup_results.py`는 그대로 남겨 이력을 보존한다.

## 1. §138에서 정정한 주장과 수치

**A. 첫 회복과 탐지·전환의 관계 — 사용자 지적을 실측으로 확인**

| | fixed_threshold | proposed |
|---|---|---|
| t_detection − t_recovery(첫 episode) | **+329.765s**(지적값과 정확히 일치) | **+176.082s**(지적값과 정확히 일치) |
| t_switch − t_recovery(첫 episode) | +342.195s | +182.607s |

§138은 이 관계를 "회복 6분49초 뒤 탐지 - 첫 회복과 무관"이라고 썼다.
**틀리지는 않았지만 불완전했다** — 아래 §3에서 밝히듯, 탐지·전환은
실제로는 **두 번째(재위반) episode 안에서** 일어났다. "9.9초/10.0초를
탐지·전환이 만들어낸 복구시간"이라고 표현한 적은 없었지만(§138 본문은
"recovery_sec(첫 episode)"로만 불렀다), 표를 detection_source와 나란히
둔 것 자체가 오인의 소지가 있었다 - 이 문서부터는 "첫 저하 해소"와
"이후 재위반에 대한 전환의 시간적 위치"를 항상 분리해서 쓴다. "실제
기여 1/4 대 3/4"(§138 앞선 정정에서 쓴 표현)는 인과 확정으로 읽힐 수
있어 이번부터 "시간적으로 기여 가능성과 부합하는 사례"로 일괄 수정한다
(과거 45건 서술도 동일 원칙 적용 - §137/§138의 "DURING"/"BEFORE" 표는
전부 "부합", "AFTER-RECOVERY"는 "무관할 가능성"으로 이미 이렇게
썼었다 - 이번엔 "기여했다"는 확정형 표현이 남아있던 곳만 수정).

**B. 900초 cohort — analyze_followup_results.py의 오류 확인**

기존 `analyze_followup_results.py`는 evidence 전체(pre-injection baseline
포함, 904/905건)를 "고정 관측 903초"라고 잘못 불렀다. 사전등록된
`t_injection<=sent_at<t_injection+900`을 명시 적용해 재구성했다(아래 §2
표). **독립 재계산값과 정확히 일치**: fixed 900/900/1/69, proposed
900/900/0/60(사용자가 제시한 참고값과 완전히 동일 - 코드를 그 값에
맞춰 작성하지 않았다, `correct_followup_138.py`는 참고값을 보기 전에
이미 완성된 로직으로 계산했고 사후 대조만 했다).

**C. 미완료 1건의 정정** — §138은 "proposed 1건 unresolved(0.11%)"라고
보고했다. 재조사 결과 이 1건은 **900초 cohort 밖(사후 발신, +902.8초)**
이었다 - **900초 cohort 안에서는 두 arm 모두 미완료 0건**이다(§4 상세).

**D. 재위반 확인 — §138에서 아예 누락됐던 것을 발견**

최초 재분석 시도에서 재위반 탐색 로직 자체에 버그가 있어(주입 시각
이전 이력을 rolling window 계산에서 통째로 제외 - 아래 §5 투명 고지)
원본 t_slo/t_recovery와 수 분 단위로 어긋나는 결과가 나왔다 - 원인을
찾아 고친 뒤(주입 전 이력은 window 계산엔 유지하되 판정 시작 자격만
주입 시각 이후로 제한 - 원본 run_once() 판정과 동일한 방식) 재확인한
결과, **두 arm 모두 900초 안에 재위반이 실제로 있었다**(§3 상세). 이건
§138에서 완전히 놓친 사실이다.

## 3. 첫 회복·탐지·전환·이후 episode 시간선

| | fixed_threshold | proposed |
|---|---|---|
| t_injection | 09:19:01.809 | 09:43:01.551 |
| episode 1: t_slo → t_recovery | 09:19:51.036 → 09:20:00.949(**9.91초**) | 09:43:50.638 → 09:44:00.665(**10.03초**) |
| episode 2: t_slo → t_recovery | **09:23:07.247 → 09:27:26.959(4분20초)** | **09:46:52.856 → 09:51:21.651(4분29초)** |
| t_detection | 09:25:30.714 | 09:46:56.747 |
| t_switch | 09:25:43.144 | 09:47:03.272 |

**해석(3단계, 인과 유보)**:
- **관측된 사실**: 첫 저하(episode 1)는 탐지·전환이 일어나기 훨씬
  전에(각각 5분29초/3분6초 전) 자체적으로 해소됐다 - 이 첫 회복은
  탐지·전환과 무관하다. 그런데 900초 관측 구간 안에서 **두 번째
  위반(episode 2)이 실제로 발생**했고, `t_detection`과 `t_switch`
  **둘 다 episode 2의 [t_slo, t_recovery] 구간 안에 있다**(fixed:
  09:23:07~09:27:27 안에 t_detection 09:25:31, t_switch 09:25:43;
  proposed: 09:46:53~09:51:22 안에 t_detection 09:46:57, t_switch
  09:47:03). 원본 TrialResult의 `recovery_sec`(9.9초/10.0초)는 이
  두 번째 위반을 전혀 반영하지 않는다(run_once()가 첫 t_slo/t_recovery
  쌍만 기록하는 설계이기 때문 - §137에서 이미 확인한 구조적 한계).
- **사실과 부합하는 가설(인과 미확정)**: 탐지·전환의 시각이 episode 2
  구간 안에 있다는 것은 "이 전환이 그 재위반의 해소에 기여했을 가능성"
  과 시간적으로 부합한다 - 그러나 이것만으로 기여를 입증하지 않는다
  (기존 45건에 적용한 것과 동일한 원칙 - "DURING"은 항상 "부합"이지
  "증명"이 아니다).
- **아직 검증되지 않은 것**: 전환이 없었다면 episode 2가 더 오래
  갔을지, 언제 자연 해소됐을지는 이 데이터만으로 알 수 없다(대조군
  없음, n=1).

## 4. 요청 완결성 및 미완료 1건의 정확한 분류

900초 cohort 안에서는 fixed_threshold 0건, proposed 0건 미완료 - 전부
정상 완료됐다(§2 표).

**cohort 밖(사후 발신)의 그 1건**(§138이 "unresolved 1건"으로 보고했던
바로 그 요청, request_id 앞 8자리 `d688acba`, proposed, 발신 09:58:04.357
= 주입 후 +902.8초): `send_stopped` 이벤트는 evidence에 있었지만
(`reason=duration_elapsed`), `unresolved_summary` 이벤트가 없어
"grace_expired_confirmed"로 확정할 수 없었다 → **"in_flight_at_fetch_
no_grace_summary"**(회수 순간 진행 중이었을 가능성, 확정 아님)로 분류.
이 요청은 **애초에 사전등록 900초 cohort 밖**이므로, 이번 정정으로
"cohort 안 미완료 0건"이라는 결론 자체에는 영향이 없다 - 다만 §138에서
이 요청을 cohort 안 지표처럼 다뤄 "proposed 0.11% 미완료"라고 쓴 것은
정정한다.

## 5. 비용 측정의 실제 범위와 절대·상대 차이

**구간 분리 결과**(phase_marks 기준):

| 구간 | fixed_threshold | proposed |
|---|---|---|
| 준비(run_started_at~t_injection) | 표본 1개 - **경계 표본 부족, 계산 불가(추정 안 함)** | 동일 |
| **관측(injection~injection+900s)** | 표본 180개, CPU 사용 **0.64초**, 메모리 평균 **44.8MB**(최대 46.1MB) | 표본 180개, CPU 사용 **3.703초**, 메모리 평균 **189.7MB**(최대 190.5MB) |
| 정리(injection+900s~t_run_end) | 표본 0개 - **계산 불가(추정 안 함)** | 동일 |

**절대·상대 차이(관측 구간만, 유일하게 경계가 확실한 구간)**:
- CPU: 절대차이 **3.063초**, 상대배율 **5.79배**(§138의 "약 7배"는 구간
  경계를 안 나눈 전체 span 기준 근사치였다 - 관측 구간만으로 다시 내면
  5.79배).
- 메모리 평균: 절대차이 **144.9MB**, 상대배율 **4.23배**(§138의 "4.2배"와
  거의 같음 - 관측 구간 표본이 전체 span의 대부분을 차지해 차이가 작음).

**수집 실패 재분류**(§138 이후 지시 §5 - "종료 후 표본을 수집 실패로
오분류하지 않기"): 기존엔 fixed 13건/proposed 15건을 그냥 "missed"로만
셌다. 재분류 결과 **둘 다 진짜 mid-run 수집 실패는 0건** - 전부 마지막
성공 표본 이후의 "정상종료 꼬리"(detector가 trial 정리 단계에서 이미
종료된 뒤에도 내 샘플러 스레드가 잠깐 더 폴링한 것뿐)였다. 이 재분류
로직(`reclassify_missed()`)은 합성 fixture로 별도 검증했다(§6).

**여전히 확보 불가한 것**: 준비·정리 구간의 비용은 경계 표본이 없어
계산할 수 없다(관측 시작 직전/직후 표본이 각각 1개/0개뿐) - 추정치로
채우지 않고 "계산 불가"로 명시했다. 클러스터 pod 자원(active/preview)은
§138에 이미 있으나 이번엔 구간 재분리를 안 했다(로컬 detector만큼
`n_samples_total`/`missed` 이력을 따로 안 남겨 같은 재분류가 불가능
- 다음 반복 전에 `ClusterPodSampler`에도 같은 timestamp 이력을 남기는
개선이 필요, §8).

| episode 2(재위반) 존재·시간선 | **사용 가능(신규 발견)** | 완전한 cohort로 재구성한 rolling-window 판정 결과, 오프라인 테스트로 로직 검증 완료 |
| 관측(900s) 구간 detector 비용(CPU/메모리) | **사용 가능** | 경계 표본 충분(180개), 수집실패 재분류까지 마침 |
| 준비/정리 구간 비용 | **사용 불가** | 경계 표본 부족(1개/0개) - 추정으로 채우지 않음 |
| cohort 밖 미완료 1건의 정확한 원인 | **제한적**(확정 불가) | grace_expired 확정 근거(`unresolved_summary`) 없음, "회수 순간 진행중" 정도로만 서술 가능 |
| 이 결과와 core 45건(원본 `probe.py`)의 절대값 직접 비교 | **사용 불가** | 계측 오버헤드 조건이 다름(§138 E절, evidence 이벤트 추가 기록) |

## 8. 다음 반복 실행에 필요한 조건과 현실적인 시간 계획

**필요 조건**(라이브 실행 전에 전부 충족돼야 함, 이번 턴엔 미실행):
1. 이번에 고친 `probe_followup.py`/`load_ramp_followup_adapter.py`의
   stop-file+drain 절차를 **실제 클러스터에서 최소 1회 스모크 테스트**
   (기존 §138 실행 전 스모크와 같은 수준)로 확인 - 오프라인 테스트는
   로컬 서버로는 검증됐지만 실제 kubectl exec 왕복 지연까지 반영한
   확인은 아직 없음.
2. `ClusterPodSampler`에도 `LocalProcessSampler`와 같은 timestamp 이력을
   남겨 구간별(준비/관측/정리) 재분리가 가능하게 보완(§5 - 현재는 로컬
   detector만 재분리 가능).
3. 위 1·2를 마친 뒤에만 반복 실행 여부를 별도로 승인받는다.

**시간 계획 재추정**(이번 지시가 지적한 대로 - trial당 약 25분이면
4개는 약 100분이지 90분이 아니다, 게다가 이번에 stop() drain 대기가
최대 90초 늘었다):
- trial당: preview prep(최대 8분) + 고정관측(900초=15분) + **drain 대기
  (최대 90초, 이전보다 추가됨)** + 정리(~1~2분) ≈ **약 26~27분**.
- 한 쌍(fixed→proposed) ≈ **약 52~54분**.
- **세션당 1쌍만 계획한다**(2쌍=4trial을 90분에 넣는 계획은 폐기 - 준비·
  drain·cleanup·여유시간을 감안하면 1쌍도 90분 예산의 절반 이상을
  쓴다). 5회/arm(10trial, arm 순서 교차) 완성에는 **세션 10회 내외**
  (쌍마다 최소 1세션)로 재추정한다 - 기존 §138의 "약 3세션"은 "세션당
  2쌍" 가정이 잘못돼 과소추정이었다.
- 이번 승인 범위에는 포함되지 않음 - 위 1·2 선행 조치 완료 후 별도
  승인 필요.
