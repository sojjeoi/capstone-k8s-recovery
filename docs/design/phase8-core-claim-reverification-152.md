# Phase 8 — 핵심 주장("선제 복구") 엄격 재검증 (읽기전용) (§152)

§140~§151 전부 보존(수정 0건). 이번 턴도 **읽기 전용**이다 - 코드
수정 0건, 새 실험 0건. 기존 `load_authoritative()`/`cell()`/
`load_raw_trial()`/`probe_raw_path()`/`slo_judge.load_raw()`/
follow-up evidence 로더를 그대로 재사용해 새 판정 로직 없이 재계산만
했다.

**결론 먼저**: 이 프로젝트가 그동안 "선제 복구"(preemptive recovery)
라고 불러온 것은, **"실제 첫 피해 요청" 기준으로는 지금까지 확인한
40개 trial(core 45건 중 non-native 30건 + 후속 5쌍 10건) 전부에서
단 한 번도 성립하지 않는다.** 기존에 "선제"라고 부른 사례는 전부
**사후 계산된 t_slo(30초 지속조건 확정 시각) 기준으로만** 선제였다.
**정당하게 주장할 수 있는 것은 "선제"가 아니라 "실제 저하 발생 이후
더 빠른 반응"이다** - 이건 실제로, 꽤 뚜렷하게 확인된다(아래 4절).

---

## 1. 세 가지 기준 정의 (요청대로 구별)

| 기준 | 정의 | 산출 방법 |
|---|---|---|
| **장애 주입 전** | `t_injection` | 기존 trial JSON 필드, 변경 없음 |
| **첫 실제 요청 품질 저하 전** | `t_first_bad` = 주입 이후 발신된 요청 중 **개별 요청 단위로** 실패(`success=False`) 또는 latency>0.648s(threshold)인 **첫 번째 요청의 발신 시각** | **이번 턴에 신규 계산**(원자료 직접 스캔) - core는 `probe.py`의 raw CSV(`sj.load_raw()`), 후속은 evidence JSONL의 `completed` 이벤트. 판정 로직 없음 - 단순 정렬+첫 매치. |
| **사후 계산된 t_slo 전** | `t_slo` | 기존 trial JSON 필드(30초 지속조건 확정 후 스트릭 시작점으로 소급, `slo_judge.find_t_slo()`) - 변경 없음 |

**차이의 성격**: `t_slo`는 "30초 동안 계속 나빴다"는 게 사후에
확정된 다음에야 기록되는, **판정 알고리즘이 만든 시각**이다(스트릭
시작점으로 소급되긴 하지만, 그 확정 자체가 나중에 일어남). `t_first_
bad`는 그런 지속조건 없이 **딱 한 건이라도 실제로 나빴던 첫 순간**
이다 - 개념적으로 항상 `t_first_bad <= t_slo`(또는 `t_slo`가 아예
없을 수 있음, 위반이 30초를 못 채우고 끝난 경우).

## 2. 전 trial 재계산 결과 (원자료 직접 스캔, 40개 trial)

### 2.1 돌발형 - pod_kill (core 45건 중 10개, fixed_threshold+proposed 각 5)

| | fixed_threshold(5개 반복) | proposed(5개 반복) |
|---|---|---|
| 주입→첫 실제 저하(초) | 0.0~1.0 (전부 1초 이내) | 0.0~0.8 (전부 1초 이내) |
| 탐지/전환이 첫 저하보다 앞선 사례 | **0/5** | **0/5** |
| 전환 이후에도 저하 요청 존재 | 5/5(모든 반복에서 postswitch_bad>0) | 5/5 |

**10/10 전부 "탐지·전환이 첫 저하보다 앞선 사례 없음".** 코드
근거(`pod_kill_adapter.py` 2~6행, 원본 그대로 인용): "전조 없는
즉발 장애라 예측 경로 검증용이 아니라... proposed가 native보다
반드시 빨라야 한다고 가정하면 안 된다" - **이 프로젝트 자신의 코드
주석이 이미 pod_kill을 예측 대상으로 설계하지 않았다고 명시하고
있다.** Chaos Mesh PodChaos는 "순간 액션"(같은 파일 15행)이라
주입과 동시에(또는 바로 다음 요청부터) 저하가 시작된다 - **구조적으로
사전 예측이 불가능하다는 주장이 코드와 데이터 양쪽으로 뒷받침된다.**

### 2.2 점진형 - load_ramp (core 10개 + 후속 5쌍 10개 = 20개)

| | core fixed_threshold(2개 유효 반복) | core proposed(4개 유효 반복) | 후속 fixed_threshold(5개) | 후속 proposed(5개) |
|---|---|---|---|---|
| 주입→첫 실제 저하(초) | 0.3~41.7 | 0(prevented 1건 제외)~224.7 | 0.1~110.3 | 0.1~1.8 |
| 전환이 첫 저하보다 앞선 사례 | **0/2** | **0/4** | **0/5** | **0/5** |

**load_ramp 20개 중 20개 전부 "전환이 첫 저하보다 앞선 사례 없음".**
§136이 "선제 전환"(§4, `detection_lead_sec>0`)이라고 부른 두 사례
(`load_ramp-proposed-03-mainexp-v2`, `load_ramp-proposed-05-mainexp-
v2`)를 정확히 재확인: 둘 다 **`sw_before_tslo=True`**(사후 확정
t_slo보다는 앞섬, §136의 원래 주장과 일치)이지만 **`sw_before_
firstbad=False`**(실제 첫 저하 요청보다는 뒤짐) - 각각 첫 저하
후 52.8초, 14.4초 뒤에 전환됐다. **§136의 "선제"는 t_slo 기준으로는
정확했지만, 실제 피해 기준으로는 "선제"가 아니었다** - 이게 이번
재검증의 핵심 정정이다.

### 2.3 점진형 - network_degrade (core 10개)

| | fixed_threshold(5개) | proposed(5개) |
|---|---|---|
| 주입→첫 실제 저하(초) | 0.1~0.8 | 0.2~0.9 |
| 전환이 첫 저하보다 앞선 사례 | **0/5** | **0/5** |

**network_degrade도 10/10 전부 동일.**

### 2.4 종합

**40개 trial(pod_kill 10 + load_ramp 20 + network_degrade 10) 전부에서
`t_switch`가 `t_first_bad`보다 앞선 사례는 0건이다.** "탐지만 앞선
사례"(즉 `t_detection`은 `t_slo`보다 앞서지만 실제 저하보다는 뒤인
경우)를 "선제 복구 성공"으로 세지 말라는 지시를 그대로 따른 결과,
**이 정의로는 "선제 복구 성공" 사례 자체가 하나도 없다.**

**전환 이후 저하도 확인**: 전환이 실제로 일어난 모든 trial에서
`postswitch_bad`(전환 이후 발신된 요청 중 실패·초과 건수)는 0보다
컸다(예: load_ramp-proposed-05-mainexp-v2는 전환 후 297건 중 57건
초과, 후속 proposed rep05는 전환 후 848건 중 73건 초과) - 전환이
일어나도 즉시 완전히 좋아지지는 않는다(§150에서 이미 확인한
전환후 저하 현상과 일치).

## 3. "선제 복구"의 정확한 주장 범위 판정

**주장할 수 없는 것**: "proposed가 실제 피해가 발생하기 전에
막는다"는 의미의 선제 복구 - 40/40 trial에서 반증된다.

**돌발형(pod_kill) - 애초에 대상이 아님**: 구조적으로 사전 신호가
없는 순간 장애라, 어떤 탐지 메커니즘도(proposed든 fixed_threshold든
미래의 다른 방식이든) 첫 요청 저하보다 앞설 수 없다 - 이건 "이번
시스템의 한계"가 아니라 "이 시나리오 자체의 정의상 불가능"이다.
이 시나리오에서 의미 있는 비교 대상은 "탐지 방식"이 아니라 "복구
경로"(Alertmanager 반응 vs BlueGreen vs K8s 기본 self-healing)의
상대 속도뿐이다(코드 주석과 동일한 결론).

**점진형(load_ramp/network_degrade) - 원리적으로는 가능하나 현재
시스템은 달성 못 함**: 첫 저하까지 수십~수백 초의 실측 간격이 있는
반복이 실제로 존재한다(예: 최대 224.7초) - 원리적으로 그 사이에
탐지+전환이 끝날 여지가 있다는 뜻이다. 그러나 20개 load_ramp trial과
10개 network_degrade trial 전부에서 **현재 시스템은 이 여지를 한
번도 실현하지 못했다.**

## 4. 실제로 주장 가능한 것 — "선제"가 아니라 "실제 저하 이후 더 빠른 반응"

load_ramp에서 "첫 실제 저하 발생 시각 → 전환 시각"까지의 지연을
arm별로 비교하면(원자료 직접 계산, 새 지표 아님 - 기존 `t_switch`/
`t_first_bad`의 단순 차):

| | core 45건(n=2 fixed / n=4 proposed) | 후속 5쌍(n=5/n=5) |
|---|---|---|
| fixed_threshold | [449.0s, 370.5s] | [360.4, 382.7, 287.3, 411.5, 360.8]s |
| proposed | [52.8s, 276.7s, 300.1s, 14.4s] | [239.9, 60.9, 47.1, 343.5, 54.8]s |

**두 자료 모두에서 proposed의 "첫 저하→전환" 지연이 fixed_threshold
보다 뚜렷이 짧다**(대략 중앙값 기준 core 409.8s→164.8s, 후속
360.8s→60.9s - 약 2.5~6배). **이건 "선제"가 아니라 "실제 문제가
이미 시작된 뒤, fixed_threshold보다 훨씬 빨리 알아채고 반응한다"는
뜻이다** - 표본이 작고(core n=2/4) 유의성 검정은 안 했지만, 방향은
20개 load_ramp trial 양쪽 자료에서 일관된다.

**이게 이 프로젝트가 정직하게 주장할 수 있는 핵심 성과다**: "장애
발생을 예측해 피해를 막는다"가 아니라, **"장애가 실제로 사용자
요청에 영향을 주기 시작한 뒤, 단순 CPU 임계치 방식보다 훨씬 빠르게
알아채고 전환을 시작한다"**는 것 - 다만 4절 앞부분(§147~150)에서
이미 확인했듯, 이 "더 빠른 반응"이 **최종 900초 요청 피해율까지
일관되게 더 낮춘다는 것까지는 후속 5쌍에서 입증되지 않았다**(방향이
5번 중 3번 반대) - "더 빨리 반응한다"와 "결국 피해가 더 적다"는
별개의 주장이고, 전자만 확인됐다.

## 5. 추가 설계 후보 재평가 — 이 핵심 주장을 개선할 수 있는가

§151의 4개 후보(A: 구pod cutover 가속, B: 부하기반 readiness 게이트,
C: 수평확장, D: idempotency 완화)를 "탐지/전환이 t_first_bad보다
앞서게 만들 수 있는가"라는 이번에 확정한 정확한 기준으로 재평가한다.

| 후보 | t_first_bad 이전 전환에 기여? | 이유 |
|---|---|---|
| A(cutover 가속) | **아니오** | 전환 결정 **이후**의 트래픽 이관 속도만 다룬다 - 결정 자체의 타이밍(언제 이상을 탐지하는가)에는 영향 없음 |
| B(readiness 게이트) | **아니오** | 마찬가지로 전환 실행 단계 - 탐지 타이밍과 무관 |
| C(수평확장) | **아니오** | 용량 문제 완화지 탐지 타이밍과 무관 |
| D(idempotency 완화) | **아니오** | 같은 trial의 **두 번째** 신호를 살리는 것 - 첫 신호 자체의 타이밍은 그대로이므로, "첫 전환이 t_first_bad보다 앞서는가"에는 영향 없음 |

**4개 후보 전부 이 핵심 주장(선제 여부)에 기여하지 않는다** - §151의
NO-GO 결론이 유지될 뿐 아니라, 애초에 이 후보들이 겨냥한 문제(전환
후 잔존, 자원 포화, 신호 차단)와 "선제 여부" 문제는 **서로 다른
층위**라는 게 이번 재검증으로 명확해졌다. **"선제로 만들려면"
탐지 자체가 첫 저하 발생 전에 이상을 확신할 수 있어야 하는데, 이건
연속판정(`CONSECUTIVE_THRESHOLD=3`)·평가 주기·모델 자체의 민감도
조정이 필요한 문제라 "단순 임계값 조정"이나 "재학습"과 경계가
모호해진다 - 지시대로 이번 검토 범위에서 제외한다.**

## 6. 확인 못한 것 / 한계

- core-45의 `probe.py` raw CSV는 요청ID가 없어 `t_first_bad` 판정이
  "그 시각에 발신된 어떤 요청이든 나빴다"는 것만 확인하고, 그 요청이
  정확히 어떤 것인지(예: 동시에 여러 요청이 있었다면 어느 것) 특정할
  수 없다 - 다만 확인용 지표(주입 후 첫 매치)로는 충분하다.
- 표본이 작다(core는 시나리오당 n=2~4, 유효 반복만) - 4절의 "더 빠른
  반응" 방향성은 20개 load_ramp trial 양쪽에서 일관되지만 통계적
  유의성 검정은 하지 않았다(이 프로젝트 전체의 기존 원칙과 동일).
- native arm은 탐지/전환 개념이 없어 이번 재검증에서 제외했다(§136
  에서도 참고용으로만 다룸, 원칙 동일 유지).
