# 전환/무전환 비교 계약 (guarded-ab-v1-20261007) — 첫 공식 결과 전 고정

작성: 2026-10-07(KST). **실행 승인 문서가 아니다.** 이 계약은 공식 비교 쌍 `ab01`의 어떤 결과도 보기 전에 고정한다. 바꿔야 하면 실행을 멈추고, 새 버전 ID와 이유를 먼저 기록한 뒤 이미 끝난 모든 쌍에 똑같이 적용한다(결과를 보고 유리하게 바꾸지 않는다).
실행기: `experiments/run_guarded_pilot.py`(실행 ID `abNNa`/`abNNb`). 결과 폴더: `experiments/results/capstone_guarded_ab_v1/`. plan ID: `capstone-guarded-ab-v1-20261007`.

## 1. 연구 질문과 주장 범위

- **질문(고정):** 같은 CPU 압박·요청 조건에서 v3.3-c1 Isolation Forest 신호에 따른 실제 전환이 무전환보다 공식 SLO 위반시간과 사용자 요청 품질 악화를 줄이는가?
- **별도 질문(이번 계약 밖):** 정상 운전에서 불필요한 전환의 빈도·비용. 정상 3시간 경고 조건 10회는 그대로 한계로 보고하며, 실제 승격 빈도는 별도 무주입 act 계약으로 잰다.
- **주장하지 않는 것:** 모든 장애 예측, IF의 원인 진단, gap01/gap02만으로 복구 효과 입증, 고정 임계치 실제 전환 arm 대비 우월성(이 비교에는 고정 임계치 전환 arm이 없다. 고정 규칙과는 기존 같은 평가 시점 탐지 시각 비교만 있다).

## 6. 실행 순서

- **선택: 쌍마다 A→B 고정, B는 A와 같은 시작 노드(코드 강제), 노드를 되돌리는 추가 승격 없음.**
- 이유(현재 Blue-Green 구조):
  - A는 전환하지 않으므로 A 뒤 active가 그대로다 → 같은 쌍 B가 **같은 active Pod·노드**에서 시작한다(쌍 안 대상 일치).
  - BA로 바꾸면 B가 active를 다른 노드로 옮겨 같은 쌍 A의 시작 Pod·노드가 달라진다. 맞추려면 되돌리는 추가 승격이 필요하다(미검증 롤백 금지 원칙과 충돌, 비대칭 정리 추가). 그래서 AB/BA 교차는 채택하지 않는다.
  - B가 전환하면 다음 쌍의 시작 노드가 바뀌므로 노드는 쌍 사이에서 자연히 번갈아 바뀐다(B가 전환하지 않으면 그대로). 쌍별 시작 노드를 기록하고 노드별 결과를 함께 보고한다(보정·제외에 쓰지 않음).
- 한계(보고에 적음): 쌍 안 순서가 항상 A 먼저(시간대·이월 효과 가능). 완화는 기존 기준선 안정 확인과 A→B 사이 모드 전환 시간뿐이며, 순서 효과를 통계적으로 분리하지 못한다.
- 쌍 사이: 한 쌍의 A와 B 사이에 Calico 재시작 등 노드 유지보수가 필요하면 그 쌍을 중단(시도에 포함, 유효 아님)하고 다음 쌍을 A부터 새로 시작한다(V2 §6과 같음).

## 8. 유효·무효·중단(사전 고정, 분석기가 저장된 근거만으로 기계적으로 판정)

**실행 유효(모두 만족):**
1. `outcome_status=completed`, `injection_valid=true`, 탐지기 주입 전 준비 확인.
2. 주 지표 계산 가능: 관찰 구간 요청 ≥ 570건, 요청 공백(구간 양 끝 포함) ≤ 30초(`slo_episodes` 규칙).
3. 압박 전달 확인(기준 `raw-counter-v2.3-guarded-ab-20261007`): `timed_switch_verdict.evaluate_stress_delivery_raw`의 단계별 평균 ≥ 기준선+0.2코어·창 전체 간격·카운터 리셋·연속성(B는 전환 시각부터, 전환이 압박 종료 뒤면 해당 없음) 규칙 그대로. 다만 guarded 실행기에는 V2 표본기가 없어 **원래 Pod 생존은 압박 도구 기록(`end_reason=completed`, 모든 단계 completed, `target_lost=false`)과 카운터 리셋 없음으로 확인한다**(표본기 생존 검사 대체 — 이 한 가지만 V2와 다르며 결과 전 고정).
4. 모델·threshold·아티팩트 해시·`conditions`가 동결값이고 같은 쌍 A·B가 같다. probe 이미지 실행 중 확인 통과.
5. 다른 주체 개입 없음: 기존 recovery-policy 시작·끝 격리 확인. A는 실행 전후 active selector·UID 불변이고 정책 조치 없음. B의 selector 변화는 이 실행 guarded 원장 intent→result로 설명돼야 함(설명 안 되는 변화 = 무효).
6. B 시작 노드 = 같은 쌍 A 시작 노드(코드가 다르면 주입 전에 멈춤).

**정리 오류:** 관찰 종료 뒤 단계(D6 원복 보류, 압박 CR 잔존 확인 실패 등)의 정리 오류는 그 실행의 측정값을 무효로 만들지 않지만, 실행 중 표시를 남겨 다음 실행을 막는다(사람 확인 전 자동 재개 없음). 관찰 중 문제(하네스 오류, 관찰 중 격리 해제, 정리 미완료로 압박·probe 상태 불명)는 무효.

**무효(위 조건 미충족):** 압박 미전달·판정 불가, probe 공백·요청 부족, 배치 조건 불충족, 근거 누락(요약·probe CSV·탐지기 기록·CPU 카운터), 잘못된 이미지·모델·threshold, 환경 불일치, 외부 정책 개입, SSH·노드 문제로 핵심 근거 신뢰 불가.

**즉시 중단(실행기 기존 안전 감시):** Node NotReady/Pressure, 새 디스크 오류(SSH 40초 제한 포함), worker MemAvailable 1GiB 감소, 대상 Pod OOM·재시작, 예상하지 않은 selector 변화(기존 격리 해제 포함), 정책·승격 결과 불명, 서비스 확인 failed/unknown(자동 재승격·롤백 없이 기존 정리), D6 안전조건 불충족(원복 보류), PC/연결 문제로 기록 중단. 중단된 실행은 무효이고 시도에 포함한다. 중단 원인이 B 자체 메커니즘이면 "B 메커니즘 실패"로 따로 센다(§7 조기 중단, 최종 보고에 비율 공개).

**무효 사유로 쓰지 않는 것:** 결과가 나쁨, IF가 늦음, IF 신호 없음, 정책이 거부함, B에서도 SLO 위반 발생, A에서 위반 없음.

## 9. 지표와 분석

**주 지표:** 관찰 구간(주입 관측 ~ 관찰 종료)의 **공식 SLO 누적 위반시간(초)** — `experiments/slo_episodes.violation_episodes`(계약 v2 §3 정의, `slo_judge` v3 수정 없음). 실행별로 첫 `t_slo`, 누적 위반시간, 관찰 종료 시 회복 여부(`cumulative_lower_bound`)를 저장한다. 위반 없음 = 0초. 관찰 종료까지 회복하지 않은 구간은 `관찰 종료 − t_slo`로 세고 **하한** 표시. 첫 느린 요청과 공식 지속 SLO를 섞지 않는다.

**쌍 차이:** D = A 누적 − B 누적.
- 1단계(유효 5쌍): 쌍별 A·B·D, D의 중앙값·범위, B<A / B=A / B>A 쌍 수. 부호 검정 p는 참고값으로만 적는다.
- 2단계(최종: 유효 10쌍 또는 최대 시도 도달): **Wilcoxon 부호순위 검정(정확, 양측, α=0.05) 1개만 확인 검정으로 쓴다.** D=0 쌍은 검정에서 빼고 수를 보고. 효과 = D 중앙값과 Hodges–Lehmann 추정. 유효 쌍이 10 미만이면 같은 검정을 계산하되 n과 함께 보고하고, 5 미만이면 기술 통계만.
- 하한 처리: 주 분석은 값을 그대로 쓰고 하한 표시를 붙인다. 민감도 분석(주 분석을 대체하지 않음) = 하한이 있는 쌍 제외. A만 하한이면 차이를 과소평가하는 방향(보수적), B 하한은 따로 명시.

**보조 지표(기술 통계만, 사후 primary 승격 금지):** 관찰 구간 전체·성공·실패·timeout 요청 수, 지연 P50/P95/P99·최대, 느린 요청 수(지연 > 0.648초 = 2×L_BASELINE), 최대 요청 공백, 위반 구간 수·첫 구간 길이, `t_signal`(첫 조건 충족), 정책 판단 시각, 승격 명령 시각, selector 전환 확인 시각, 새 Pod 요청 처리 시작(서비스 확인 창) 시각, 서비스 verified 시각, 정리 성공/실패, 구 RS 0 확인 시각, 420→30 원복 결과, 단계별 원래 Pod 실측 CPU, 시작 노드, 첫 신호에 주입 전 평가 포함 여부.

**분석기:** `experiments/guarded_ab_analysis.py`(이 계약의 규칙만 구현, 새 파일에만 저장). **ab01a 시작 전에 구현·테스트·Ponytail 리뷰를 마치고 sha256을 이 문서에 추가 기록해 동결한다.** ab00 자료로 동작을 확인할 수 있지만 ab00은 집계하지 않는다.

## 10. 정리 규칙

- 매 실행 끝: 압박 CR·probe 정리, A는 preview를 D5 관문으로 정리, B는 D6(2026-10-07 수정본: 상한 = max(승격+유예+180초, 원복 대기 시작+171초))로 구 RS 0 실측 뒤 30 원복, guarded context 해제, 정책 상태 확인.
- 정리·원복 실패·미해결 조치 → 실행 중 표시 보존 → **비교·pilot 두 폴더의 다음 실행 모두 자동 거부**(사람 확인 후 기존 보존 절차로만 해제). B는 같은 쌍 A가 정리 오류 없이 끝나야만 시작된다(코드).
- 쌍마다 A 뒤 guarded를 act로, B 뒤 record_only로 되돌린다(gap02와 같은 확인된 절차: 초기화 설정 0, 잠금 인계, 원장 확인, identity·timing 일치). 기존 recovery-policy는 쌍 동안 격리, 세션 끝에 복원.
- 자동 재시도·자동 재승격·미검증 롤백·잠금/원장 삭제 금지. 실행은 한 번에 하나씩 수동으로 시작한다(자동 연쇄 없음).

## 12. 개발 rehearsal `ab00`(비교에 포함하지 않음)

## 13. 알려진 Low 2건(2026-10-07 Ponytail) 판단
