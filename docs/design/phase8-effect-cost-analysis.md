# Phase 8 — 효과·비용·적용조건 분석 (§136)

> 핵심 질문: 동일한 BlueGreen 복구 구조에서 고정 임계치 대신 Isolation
> Forest를 사용했을 때, 실제 서비스 피해가 얼마나 줄었으며, 추가 비용과
> 복잡성을 감수할 가치가 있는가?

**성격**: `docs/design/phase8-blue-green-preflight-incident.md`(실행
일지)와 분리된 별도 분석 문서. 클러스터 미접속, 기존 원자료(core
45건 + auxiliary 5건) 오프라인 재계산만 사용. 원본 결과 JSON·state·
hash·모델·threshold·SLO 정의·`collect_metrics.py`/`slo_judge.py`는
전혀 수정하지 않았다 - 전부 읽기 전용. 재현 스크립트:
`experiments/analyze_effect_cost_evidence.py`(신규, 기존 검증된
`load_authoritative()`/`cell()`/`slo_judge.evaluate()` 등을 그대로
재사용, 새 판정 로직 없음). 원시 출력: `results/_effect_cost_analysis.json`
(분석 전용 산출물, `.gitignore` 대상, 공식 결과 아님).

**분석 대상**: core 45건만(`load_ramp`/`pod_kill`=`mainexp-v2`,
`network_degrade`=`mainexp-v1`, §129.1 확정 매핑) - precursor/pilot
혼입 0건(§129.1과 동일 로딩 경로이므로 구조적으로 보장). auxiliary
5건(`memory_pressure_negative_control_v1`, native 단일)은 §4/§5/§6과
분리해 별도로만 언급한다. 주 비교는 **fixed_threshold vs proposed**이며,
native는 "개입 없이 뒀을 때"를 보여주는 참고 비교로만 별도 취급한다
(`load_ramp-native-01`은 "예방"이 아니라 "무개입 상태에서 SLO 위반
미관측"으로 기술 - §131과 동일 판정 유지).

**전제**: 우월성을 전제로 분석하지 않는다. 효과가 없거나 불리한 결과
(예: network_degrade의 미미한 개선폭, network_degrade/proposed의
낮은 predictive 실제 채택률)도 동일한 비중으로 보고한다.

## 1. 확인된 효과와 그 한계

**확인된 것**:
- `recovery_sec`(정의는 §2 참고) 기준, 세 시나리오 모두에서 proposed의
  중앙값이 fixed_threshold보다 낮다(더 빠르다) - load_ramp 44.9%,
  pod_kill 24.6%, network_degrade 2.1%.
- 이 개선폭은 시나리오별 detection_source의 실제 구성과 뚜렷하게
  대응한다(§2, §4).
- load_ramp/proposed의 `detection_lead_sec>0`(SLO 판정 이전 탐지)
  2개 사례(rep3, rep5) 모두, 전환 후 90초 창에서 "심각"(실패 또는
  임계치 2배 초과) 이벤트가 실제로 관측됐다 - 판정이 순수 과거
  잔류값(stale window)만으로 이뤄졌다는 반증 근거(§4).

**한계(모든 수치에 공통 적용)**:
- **n=5/arm, 시나리오당 1회 조건**. 유의성 검정을 하지 않았고
  하지도 않는다 - 아래 모든 수치는 "중앙값·범위" 기술통계이며 우열을
  통계적으로 확정하지 않는다(§131과 동일 원칙).
- 세 시나리오는 서로 다른 고장 유형·주입 강도이므로 시나리오 간
  개선율을 직접 비교해 "평균 개선율"을 만들지 않는다 - 시나리오별로만
  본다.
- `recovery_sec`는 "총 SLO 위반시간"이나 "사용자 중단시간"이 아니다
  (§2). 대리 지표로만 해석한다.
- 자원(CPU/메모리) 비용은 0/45 미측정 - "가치가 있는가"라는 질문의
  비용 쪽 절반은 이번 분석으로 답할 수 없다(§5).
- 아래는 모두 **post-hoc**(사후) 분석이다 - 사전 등록된 가설 검정이
  아니라, 기존 45+5건 원자료를 사후에 재분류·재계산한 것이다.

## 2. 시나리오별 fixed_threshold vs proposed 차이 (절대·상대)

`recovery_sec` 정의(코드 확인, `collect_metrics.py`):
`_seconds_between(ts, "t_slo", "t_recovery")` = `t_recovery - t_slo`
(`t_recovery - t_injection`이 **아님**). 즉 "SLO 위반이 30초 지속
조건으로 확정된 시각"부터 "무위반이 30초 지속 조건으로 확정된 시각"
까지의 구간이다. `t_slo`/`t_recovery` 둘 다 스트릭 시작점으로 소급
계산되므로(§134), 이 값을 "전체 SLO 위반시간"이나 "사용자 체감
중단시간"으로 자동 지칭하지 않는다 - 대리 지표로만 쓴다.

| 시나리오 | fixed_threshold 중앙값(범위, n) | proposed 중앙값(범위, n) | 중앙값 차이 | 상대 감소율 |
|---|---|---|---|---|
| load_ramp | 226.17s (40.99–259.56, n=4/5) | 124.57s (1.1–235.87, n=4/5) | 101.6s | **44.9%** |
| pod_kill | 158.15s (135.18–179.21, n=5/5) | 119.26s (117.2–157.18, n=5/5) | 38.89s | **24.6%** |
| network_degrade | 382.56s (359.66–391.59, n=5/5) | 374.56s (200.59–393.57, n=5/5) | 8.0s | **2.1%** |

산식(고정): `median_diff_sec = median(fixed.recovery_sec) - median(proposed.recovery_sec)`,
`relative_reduction_pct = median_diff_sec / median(fixed.recovery_sec) × 100`.
이는 **중앙값 기준 1회 계산**이며 "반복별 개선율의 평균"이 아니다 -
두 계산 방식은 n=5처럼 작은 표본에서 서로 다른 값을 줄 수 있으므로
혼동하지 않는다.

각 시나리오 모두 rep01(1번 반복)이 세 arm 전부에서 `prevented`
(SLO 위반 자체가 관측되지 않음)로 제외됐다 - 이는 세 arm이 rep
인덱스별로 동일한 장애 주입 강도 조건을 공유한다는 뜻이며(공정성
확인), proposed만 선택적으로 쉬운 반복을 배정받은 것이 아니다.

**참고: native 대비**(주 비교 아님, 무개입 참고용) — native 중앙값은
load_ramp 221.68s(n=4/5), pod_kill 257.27s(n=5/5), network_degrade
391.42s(n=5/5). fixed_threshold·proposed 모두와 마찬가지로 native도
"개입 없이 두면 결국 회복되긴 하는" 궤적을 보이며, 세 arm 간 서열은
시나리오마다 다르다(예: load_ramp에서는 native가 fixed_threshold보다
오히려 빠른 중앙값을 보임 - 이는 native의 회복이 "능동 복구"가 아니라
"어떤 개입도 없이 자연 변동으로 SLO가 다시 정상 범위에 든 것"이기
때문일 수 있으며, 개입 메커니즘의 우열로 해석하지 않는다).

## 3. 실제 피해 감소에 대한 찬성/반대 증거

**증거 확보 현황**(전수 확인, 요약 신뢰하지 않고 원자료·코드 직접
확인):

| 항목 | 확보 상태 |
|---|---|
| 요청별 전송·완료 시각/성공/latency (probe raw csv) | 확보됨 45/45 |
| load_ramp 부하생성기(`ramp.py`)의 요청별 원자료 | **없음**(0/15) - 단계별 요약만 존재(15/15: target_rps/actual_rps/sent/success/p95/p99) |
| pod_kill/network_degrade의 "부하생성기" | **해당없음** - 두 시나리오는 probe.py 단일 트래픽만 사용(코드 주석 확인). "probe vs load generator 구분" 자체가 성립하지 않음 |
| injection~관측종료 전 구간 타임스탬프 | 확보됨 45/45 |
| 실제 `detection_source` | 확보됨 45/45 |
| detector 판단 로그(평가/이상판정/신호발행/cooldown) | 확보됨 45/45(비-native 30건 로그 실존 확인) |
| promotion 감사 기록(`audit-log/*.jsonl`) | 확보됨 26/45(파일 존재만 - 없어도 정상, 신호 자체가 없었을 수 있음) |
| detector/serving/preview 자원 사용(CPU·메모리) | **없음**(0/45) - 68개 필드 전수 확인 + 디렉터리 전수 검색 |

**찬성 증거(개선을 지지)**:
- 세 시나리오 모두 proposed 중앙값이 낮다(§2).
- load_ramp/proposed의 SLO probe 실패율·threshold초과율은 다른
  두 arm과 같은 프로파일(probe.py, threshold=0.648s)로 측정돼
  직접 비교 가능하다(요청 프로파일이 다른 ramp.py와 절대 혼합하지
  않음, §3의 확인 사항).
- detection_source가 "predictive"(해당 arm 고유 메커니즘이 직접
  발화)로 실제 기록된 비율이 높을수록 개선폭이 크다는 일관된 대응
  관계가 관측된다(load_ramp 5/5 predictive → 44.9%, pod_kill 5/5
  predictive(단 지연 발화) → 24.6%, network_degrade 1/5 predictive
  → 2.1% - §4).

**반대/유보 증거(개선을 제한)**:
- network_degrade에서는 proposed의 IF 탐지기 자체가 30건 로그
  전수에서 확인했듯 실제로 신호를 발행한다(6회, §5) - 그러나 5개
  반복 중 4개는 최종 `detection_source`가 `reactive`로 기록된다
  (§4) - **신호가 발행됐다는 사실이 그 신호가 실제 전환을 이끌었다는
  뜻은 아니다**. 배포된 모델(model_v32b)의 피처 6종
  (`cpu_mean/cpu_slope/memory_mean/memory_slope/cache_mean/
  cache_slope`, `score_server.py` 기동 로그로 직접 확인)에는
  네트워크/지연 관련 피처가 전혀 없다 - 순수 네트워크 저하가 CPU·
  메모리·캐시 지표에 부수적으로 반영되지 않는 한 이 모델이 구조적으로
  포착하기 어렵다. network_degrade의 미미한 개선폭(2.1%)은 이
  구조적 한계와 정합적이다.
- pod_kill에서는 5/5 모두 detection_source=predictive지만
  `detection_lead_sec`는 전부 음수(-44.6~-52.6s, §4) - "고유
  메커니즘이 발화했다"는 사실이 "SLO 위반 전에 발화했다"는 뜻은
  아니다. pod_kill의 24.6% 개선은 "위반 전 예측"이 아니라 "위반
  후에도 fixed_threshold(반응형 폴백 경유, §4)보다 빠르게 고유
  메커니즘이 판단을 내렸다"는 것으로 한정해서 해석해야 한다.
- SLO 위반이 아예 관측되지 않은 반복(각 arm의 rep01, `prevented`)은
  복구 통계에서는 제외하되, 피해 평가에서는 "개입 여부와 무관하게
  위반이 없었다"는 사실 자체가 포함된다(§2) - 세 arm 모두 동일하게
  나타나므로 arm 간 비교에 유리하게 작용하지 않는다.
- 표본 수(n=5/arm)로는 개별 반복의 편차가 크다(예: load_ramp/proposed
  범위 1.1–235.87s) - 중앙값 차이가 반복별 분산보다 작을 수 있어
  "항상 더 빠르다"고 일반화하지 않는다.

## 4. load_ramp/proposed 선제 전환(위반 판정 이전 탐지) 타임라인 + 해석

대상: `detection_lead_sec > 0`인 load_ramp/proposed 2건
(`load_ramp-proposed-03-mainexp-v2`, `load_ramp-proposed-05-mainexp-v2`).
전환 전후 각 90초 창(슬라이딩 60초 판정 창을 여유 있게 덮는 폭)의
probe 원자료를 직접 대조했다(`slo_judge.load_raw()` 재사용, 새 판정
로직 없음).

| | rep3 | rep5 |
|---|---|---|
| t_switch | 19:12:56.76 | 01:46:54.90 |
| t_switch → t_slo | +59.4s | +28.0s |
| 전환 전 90s: threshold초과 / **심각**(실패 또는 threshold×2 초과) | 2건 / **0건** (최악 0.711s) | 3건 / **0건** (최악 0.809s) |
| 전환 후 90s: threshold초과 / **심각** | 19건 / **4건** (최악 30.143s, 실패, +29.25s) | 23건 / **6건** (최악 5.932s, 성공, +31.55s) |
| 증거 수준 | **B**: 전환 이후 새 요청에서 심각한 저하 발생 근거 | **B**: 동일 |

**구분 기준**: "threshold(0.648s) 단발 초과"와 "심각"(실패 또는
threshold의 2배 초과)을 분리했다 - 전자는 정상 운영에서도 꼬리
지연으로 종종 발생하는 수준(30초 지속 조건이 아니면 SLO 위반으로
집계되지 않음)이라 노이즈로 취급하고, 결론은 **심각** 이벤트 기준
으로만 내린다. 두 사례 모두 전환 전 90초 창에는 심각 이벤트가
전혀 없고, 전환 후에만 나타난다 - 이는 사용자가 요구한 4개 결론
수준(①이동창 잔류값 ②전환 후 신규 저하 ③혼재 ④구분불가) 중
**②(전환 후 신규 저하 근거)**를 지지하며, "판정이 과거 요청의
잔류값 때문에 지연됐을 뿐"이라는 설명은 이 두 사례에서 원자료로
반증된다.

**명시적으로 확정하지 않는 것**:
- 이 심각 이벤트가 발생한 요청이 실제로 신규 target(승격된 preview)
  으로 라우팅됐는지, 구 target으로 라우팅됐는지는 **probe 원자료에
  pod 식별자가 없어 시각만으로 확정할 수 없다**. `t_switch` 이후
  시각이라는 사실과 `promotion_verified`가 이후 참이 된다는 사실만
  근거이며, 이것으로 라우팅 대상을 단정하지 않는다.
- "전환 전 SLO 판정 이전"과 "사용자가 저하를 체감하기 이전"은 다른
  개념이다 - `t_slo`는 30초 지속조건 확정 시각(스트릭 종료점,
  비-소급)이므로, `detection_lead_sec>0`은 "판정 확정 전에 탐지"를
  뜻할 뿐 "사용자가 아무 저하도 겪기 전에 탐지"를 뜻하지 않는다.
  실제로 두 사례 모두 탐지·전환 자체는 판정보다 먼저 일어났지만,
  전환 후 약 29~31초 시점에 심각 이벤트가 발생했다.
- **주목할 시간적 일치**: 두 사례 모두 전환 후 약 **29~32초** 지점에
  최악 latency가 관측된다. `target_replaced=False`(구 pod가 전환
  중 종료되지 않음, 두 사례 모두 확인됨)이므로 구 pod 종료가 원인은
  아니다. 이 일치는 n=2로는 인과관계나 메커니즘을 확정할 근거가
  못 되며(우연일 가능성 배제 못 함), §6에서 "필요한 추가 실험" 1건의
  동기로만 사용한다 - 이 문서에서 원인(예: 커넥션 풀·conntrack
  타임아웃 등)을 추정해 단정하지 않는다.

## 5. 비용·오탐 증거 (측정된 것 / 미측정으로 남긴 것)

**신호 발행 규칙**(코드 확인, `anomaly-detection/score_server.py`
64–65행, 두 탐지방식 공용): `CONSECUTIVE_THRESHOLD=3`(연속 3회
이상 판정 시 발행), `COOLDOWN_SEC=60`(발행 후 60초 재발행 억제).

**detector 로그 전수 집계**(30건, 비-native 전체):

| 시나리오/arm | 로그 | 총평가 | 이상판정 | 신호발행 | cooldown스킵 |
|---|---|---|---|---|---|
| load_ramp/fixed_threshold | 5/5 | 161 | 14 | 2 | 0 |
| load_ramp/proposed | 5/5 | 147 | 69 | 15 | 27 |
| pod_kill/fixed_threshold | 5/5 | 62 | 0 | 0 | 0 |
| pod_kill/proposed | 5/5 | 48 | 45 | 11 | 24 |
| network_degrade/fixed_threshold | 5/5 | 145 | 0 | 0 | 0 |
| network_degrade/proposed | 5/5 | 122 | 26 | 6 | 6 |

pod_kill·network_degrade에서 fixed_threshold(CPU 임계치 기반)는
**단 한 번도 "이상"으로 판정하지 않았다**(0/45 평가) - 두 고장
유형이 CPU 사용량을 임계치(2.7코어) 이상으로 밀어올리지 않기
때문으로 보이며, 이 두 시나리오에서 fixed_threshold의 전환은
전량 반응형 폴백 경로에 의존한다(§4의 `detection_source=reactive`
5/5, 5/5와 정합).

**audit-log outcome 집계**(파일 존재 26/45에 한함):

| 시나리오/arm | executed_verified | no_action | skipped_duplicate |
|---|---|---|---|
| load_ramp/fixed_threshold | 1 | – | – |
| load_ramp/proposed | 5 | – | 10 |
| pod_kill/fixed_threshold | 5 | – | 3 |
| pod_kill/proposed | 5 | 4 | 6 |
| network_degrade/fixed_threshold | 5 | – | 3 |
| network_degrade/proposed | 5 | 4 | 5 |

`executed_verified`는 시나리오·arm마다 5(반복 수)에 수렴한다 -
반복당 정확히 1회 실제 승격이라는 기대와 일치하고, 중복 신호는
`skipped_duplicate`로 올바르게 걸러진다(오승격·중복승격 근거 없음).
audit-log 총 건수가 IF 자체 신호발행 수보다 많을 수 있는 것은
(예: pod_kill/proposed 신호발행 11 vs audit 15건) audit-log가 IF
신호뿐 아니라 반응형 경로의 결정도 함께 기록하기 때문이며, 두
집계는 서로 다른 것을 세므로 억지로 일치시키지 않는다.

**공통 비용 프록시 - preview 준비 소요시간**(`t_preview_prep_start`
~`t_preview_ready`, 자원량 자체는 아니고 시간만):

| 시나리오 | fixed_threshold 중앙값 | proposed 중앙값 |
|---|---|---|
| load_ramp | 220.2s | 220.3s |
| pod_kill | 158.5s | 136.7s |
| network_degrade | 235.6s | 225.7s |

두 arm 모두 동일한 BlueGreen preview 준비 절차를 쓰므로 이 값
자체는 "공통 비용"이며 proposed 고유의 추가 비용이 아니다 - arm 간
차이가 크지 않다는 것은 예상과 일치한다(같은 인프라 절차).

**proposed의 추가 비용(detector CPU/메모리, 학습·설정 비용)**:
**미측정**(0/45, §3). 이번 분석은 이 값을 추정치로 채우지 않는다.

**오프라인 재현(홀드아웃) 대표성**: 실제 배포 모델(model_v32b)의
사전 holdout 평가(`anomaly-detection/v3/model_v32b/artifacts/
holdout-evaluation.json`, 원본 그대로 인용, 재계산 없음) -
idle/low_load 6세션(전부 'clean' 라벨) 기준 point-level FPR=5.78%
(13/225점), 그러나 **실제 신호 발행 기준(연속 3회+cooldown)으로는
6세션 전체에서 0건**(세션 내 최대 연속 이상판정 2회, 발행 문턱
3회 미달). 이 홀드아웃은 idle/low_load에서만 측정됐다 - load_ramp
처럼 부하 자체가 램프업하는 조건의 정상구간 오탐율은 별도로 측정된
적이 없으므로, 이 수치를 모든 부하 수준·수명주기로 일반화하지
않는다. 또한 "오프라인 point-level 이상판정"과 "실제 배포에서의
promote_preview 실행"은 다른 사건이며, 실제 실험 중 정상구간에서의
불필요한 신호·전환 여부는 이 홀드아웃이 아니라 위 detector 로그·
audit-log 집계(위 표)로 판단해야 한다 - 45건 core 전체에서 오승격
(불필요한 실제 promotion)으로 의심되는 audit 기록은 확인되지
않았다(모든 `executed_verified`가 반복당 정확히 1회로 수렴).

## 6. 필요/선택/불필요 추가 실험 (설계만, 이번 턴 실행 없음)

### 필요 (핵심 결론의 미해결 공백을 메움)

**실험 A — 전환 직후 정밀 관측(계측 강화, post-hoc follow-up)**
- **질문/공백**: §4에서 발견한 "전환 후 약 29~32초 지점의 심각
  이벤트" 시간적 일치(n=2)가 우연인지 재현되는 패턴인지 현재
  데이터로는 답할 수 없다.
- **비교/통제**: 새 arm·새 모델·새 threshold 없음. load_ramp/proposed
  만, 기존 동결 파라미터 그대로 재실행(순수 관측 강화).
- **지표/산식**: 전환 후 0~90초를 5초 버킷으로 나눈 구간별 "심각"
  (실패 또는 threshold×2 초과) 발생률. 가능하면 요청-응답에 실제
  서빙 pod 식별자를 남기는 **계측 추가**(§4의 라우팅 미확정 한계를
  줄이기 위함 - `probe.py`에 응답 헤더나 엔드포인트 스냅샷 기록 추가
  필요, **판정 로직·threshold·SLO 정의는 미변경**).
- **반복 수/근거**: 5회(기존 셀당 반복 수와 동일 - 통계적 유의성이
  아니라 "기존 2/5 재현 여부" 확인이 목적).
- **순서/창/warmup/cooldown**: 기존 load_ramp 프로토콜과 동일.
- **안전정지·보존규칙**: 기존 Phase 8 정지 조건과 동일, 변경 없음.
- **예상 소요/서버 변경**: 반복당 기존 load_ramp 1회 소요시간과
  동일(약 15~20분/반복) × 5 ≈ 60~90분 세션 1회로 가능. **서버/계측
  코드 변경 필요**(probe pod-식별 기록 추가 - 판정 로직 변경 아님).
- **결과별 결론**: (a) 새 5회 중 ≥2회에서 유사 오프셋에 재현 →
  "전환 후가 구조적 현상일 가능성이 뒷받침됨, 메커니즘은 여전히
  별도 코드 추적 필요"; (b) 재현 안 됨 → "n=2 관측은 재현되지 않는
  개별 사례로 하향 조정, 추가 일반화 근거 없음". 두 결과 모두
  유효한 결론이며 재실행 압박 없음.
- **명시**: 이 실험은 **post-hoc follow-up**이다 - 이번 턴 분석이
  동기이며 사전 등록된 가설이 아니다.

### 선택 (있으면 비용 질문에 답할 수 있으나, 핵심 결론엔 필수 아님)

**실험 B — 자원 사용량 계측 추가(비용 정량화)**
- **질문/공백**: §5에서 "proposed의 추가 자원 비용"이 0/45로
  완전히 미측정 - "추가 비용을 감수할 가치가 있는가"의 비용 쪽을
  전혀 정량화할 수 없는 상태.
- **비교/통제**: 기존 arm(가능하면 fixed_threshold vs proposed)에
  순수 사이드카 계측(예: `kubectl top pod` 주기적 폴링 또는 기존
  모니터링 스크레이프)만 추가 - 판정 로직·모델·threshold 불변.
- **지표/산식**: detector/serving/preview pod별 CPU·메모리 시계열,
  구간 평균·최대.
- **반복 수/근거**: 최소 3회/arm(비교 검정용이 아니라 "전형적
  사용량 범위" 확인용 - n=5까지 필요하지는 않음).
- **범위**: 대표 시나리오 1개(load_ramp - 효과가 가장 크게 나타난
  시나리오라 비용 대비 효과를 함께 보고하기 적합)로 최소 범위부터
  시작, 필요시 다른 시나리오로 확장.
- **예상 소요/서버 변경**: 3회×2arm×15~20분 ≈ 90~120분(2회 세션
  분할 가능). **계측 사이드카/스크레이프 추가 필요**, 판정 경로엔
  개입하지 않음.
- **결과별 결론**: 비용이 낮게 나오면 "추가 비용 근거는 작음, §2의
  개선폭이 비용을 상회할 가능성" / 비용이 크게 나오면 "정량적
  트레이드오프 존재, §2 개선폭과 병기해 판단 필요". 어느 쪽이든
  현재의 "미측정" 상태보다 진전.
- **명시**: **post-hoc follow-up**, 선택 사항 - 미실행 시에도 §1~§4의
  효과 결론 자체는 유효하며, 다만 "비용 대비 가치"에 대한 답은
  계속 유보로 남는다.

### 이번 범위에서 하지 않음(불필요/범위 밖으로 명시)

- **network_degrade용 모델 피처 재설계·재학습**: §3에서 이미
  구조적 원인(네트워크/지연 피처 부재)을 코드로 확인했으므로,
  "왜 그런가"를 밝히는 추가 실험은 불필요 - 다만 "고치는 것"은
  모델 변경이라 이번 턴/이 실험 목록의 범위 밖이며, 향후 모델
  개발 항목으로만 남긴다.
- **proposed 단독 재실행 후 기존 fixed_threshold 원자료와 비교**:
  같은 조건의 비교군 없이 새 proposed 데이터만 늘리는 것은 비교
  타당성이 없다 - 새 비교가 필요하면 반드시 동일 조건의 비교군을
  동반한다는 원칙(사용자 지시)에 따라 설계하지 않는다.
- **유의성 검정 추가, 반복 수 확대를 통한 "확정적 우열" 시도**:
  Phase 8 전체의 "n=5, 기술통계만, 유의성 검정 없음" 원칙과 상충 -
  설계하지 않는다.
- **새 고장 유형·새 시나리오 추가**: 이번 분석의 목적(기존 3
  시나리오의 효과·비용 규명)과 무관 - 설계하지 않는다.

## 8. 현재 주장 가능한 것 vs 아직 주장할 수 없는 것

**지금 주장 가능한 것(원자료로 직접 뒷받침됨)**:
1. core 45건(n=5/arm/시나리오)에서, `recovery_sec` 중앙값 기준
   proposed가 fixed_threshold보다 세 시나리오 모두에서 낮다 -
   load_ramp 101.6s(44.9%), pod_kill 38.89s(24.6%), network_degrade
   8.0s(2.1%) 감소.
2. 이 개선폭은 무작위가 아니라 "고유 탐지 메커니즘이 실제 채택된
   비율"과 대응한다 - network_degrade에서 개선이 미미한 이유는
   배포된 모델의 피처 구성(네트워크/지연 피처 부재)으로 구조적
   설명이 가능하다.
3. load_ramp/proposed의 두 선제 탐지 사례는 "판정 전 탐지"가 최소
   일부 사례에서는 "전환 후 새로 발생한 심각한 저하"에 대한 반응
   이었다는 근거를 갖는다(순수 과거 잔류값에 의한 지연 판정이
   아님) - 다만 라우팅 대상은 확정할 수 없다.
4. 30건 비-native core 전체에서 신호 중복 승격이나 오승격으로
   의심되는 audit 기록은 없다(반복당 정확히 1회 `executed_verified`).
5. 두 arm의 공통 비용(preview 준비 시간)은 비슷한 수준이다 -
   proposed가 이 부분에서 구조적으로 더 무겁지 않다.

**아직 주장할 수 없는 것**:
1. 위 개선폭이 **통계적으로 유의**하다는 것 - n=5/arm, 검정 미실시.
2. proposed가 **모든 부하·장애 유형에서** 낫다는 것 - network_degrade
   에서는 개선이 사실상 미미하다.
3. **실제 산업 환경 적용 시의 비용 대비 효과** - 자원 사용 비용이
   0/45로 완전히 미측정이라, "추가 비용을 감수할 가치가 있는가"의
   비용 쪽 절반은 이 분석만으로 답할 수 없다.
4. 전환 후 29~32초 지점 심각 이벤트의 **재현성이나 원인** - n=2,
   추가 관측(§6 실험 A) 없이는 우연/구조적 현상 여부를 가릴 수 없다.
5. `detection_lead_sec>0` 사례에서 심각 이벤트를 겪은 요청이
   **실제로 신규/구 target 중 어디로 라우팅됐는지** - probe
   원자료에 pod 식별자가 없어 확정 불가.
6. network_degrade에서 IF가 실제로 유용한 신호를 낼 수 있는지 -
   모델을 재설계하지 않는 한 이번 분석 범위에서 검증할 수 없다.
