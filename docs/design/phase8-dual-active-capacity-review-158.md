# Phase 8 — "피해 전 용량 추가" 원칙의 적용 검토: 기존 active+preview 동시 서빙 (읽기전용) (§158)

§140~§157 전부 보존(수정 0건). §156의 NO-GO와 원본 결과, §152의
0/40, 후속 5쌍 결과 전부 그대로 보존한다. 코드 수정 0건, 클러스터
접속 0건, 새 실험 0건. 논문의 성능 수치는 인용하지 않는다 - "피해
전에 처리 용량을 추가한다"는 **원칙**만 이 아키텍처에 적용 가능한지
검토했고, 이 문서 어디에도 논문 자체의 수치는 없다.

§157이 이미 기각한 "pod 3개 동시 실행"(새 pod 추가)과 **구분**해서,
**이미 매 trial마다 공존하는 active 1개 + preview 1개**를 둘 다
사용자 요청 처리에 쓰는 방안만 검토한다 - 새 pod를 추가하지 않으므로
§157이 지적한 메모리 초과 문제는 이 방안에는 해당하지 않는다(§1).

**결론 먼저: NO-GO.** (1) 자원 여유는 실제로 있다 - 이 부분은 §157의
후보들보다 안전하다. 그러나 (2) 지금 스택(Argo Rollouts BlueGreen +
평범한 K8s Service)에는 **트래픽을 두 pod에 나누는 방법 자체가 없고**,
있을 법한 우회(Service selector를 두 pod 다 걸리게 완화)는 Argo
Rollouts 컨트롤러의 지속적 재조정과 충돌할 가능성이 높다(코드로 직접
확인된 사실 아님 - 일반적인 컨트롤러 동작에 근거한 추정, 명시함).
(4) 요청별 처리 pod를 증명할 계측도 없다(기존에 이미 확인된 공백,
재확인). 두 조건이 막혀 있어 **"안전하게 입증할 수 없으면 NO-GO"**
기준에 해당한다.

---

## 1. 두 pod 공존 중 부하 시 CPU·메모리 안전 여유

**§157과의 결정적 차이**: §157의 두 후보는 **pod를 새로 추가**(3개
동시)하거나 **preview를 키워야**(용량 확대) 해서 노드 총량(CPU
8코어, 메모리 ~15.62GiB, `docs/design/phase8-blue-green-preflight-
incident.md` §10.1)을 초과했다. 이번 방안은 **이미 존재하는 active
1개(3코어/6Gi 제한) + preview 1개(같은 스펙)를 그대로 쓴다** - pod
개수도 스펙도 안 바뀐다.

- 두 pod가 **동시에 각자의 limit(3코어)까지** 부하를 받는 최악의
  경우를 가정해도 CPU 합계는 6/8코어(75%), 메모리 합계는 12Gi/
  ~15.62GiB(약 77%) - **이건 매 trial마다 이미 벌어지는 상태와
  숫자상 동일**하다(지금도 promote 직전까지 active+preview 두 pod가
  같은 노드에 함께 떠 있다, `blue_green_prep.py` 확인·§154 §3 S0).
  차이는 "둘 다 실제로 요청을 받는가"뿐이지, **노드가 감당해야 할
  최대 자원 약정치 자체는 늘지 않는다.**
- **반대 증거로 포함하라고 지시받은 것 - `memory_pressure_negative_
  control_v1`의 preview 공존 게이트**: `memory_pressure_adapter.py`
  72·504행의 §96 게이트는 "preview가 이미 떠 있는 상태에 **추가로**
  메모리 압박을 주입"하는 시나리오에서 헤드룸 부족으로 non-native
  arm을 아예 막았다. 이번 방안은 메모리 압박을 추가하지 않고 **기존
  2-pod 자원 약정 안에서 트래픽만 옮기는** 차이가 있어 **똑같은
  실패 사유가 그대로 적용되진 않는다** - 다만 이 클러스터의 여유가
  "추가 스트레스 한 가지에도 게이트가 걸릴 만큼 이미 빠듯하다"는
  선례로서 신중함의 근거로 남긴다(직접 증거 아님, 유사 사례).

**판정**: 이 항목만 보면 안전 여유는 확인된다(§157보다 유리) - 단,
**이것만으로 GO를 내리지 않는다**(지시대로, §2·§4가 막혀 있음).

## 2. Argo Rollouts/GitOps 관리와 충돌하지 않는 트래픽 분담 방법 - 확인 불가/부재

`gitops/apps/vllm-serving/rollout.yaml` 81~87행 - `strategy.blueGreen`
블록 전체를 확인했다: `activeService`, `previewService`,
`autoPromotionEnabled: false`, `scaleDownDelaySeconds: 30`뿐이다.
Argo Rollouts BlueGreen 전략이 공식적으로 지원하는 `trafficRouting`
필드(가중치 기반 canary-style preview 트래픽에 쓰이는, Istio/SMI/
Nginx/ALB 등 provider 필요) 자체가 **이 설정에 없다.** `gitops/` 전체를
검색해도 Istio·Linkerd·SMI·TrafficSplit·VirtualService·nginx-ingress
canary·ambassador·contour 등 트래픽 분담에 쓰일 만한 provider의 흔적이
**하나도 없다.**

**있을 법한 우회와 그 위험**: `vllm-active` Service의 selector를
`rollouts-pod-template-hash` 없이 `app: vllm-serving`만 매칭하게
완화하면, 두 pod 다 label이 같으므로(`rollout.yaml` 16~17행) kube-
proxy가 표준 라운드로빈으로 둘 다에 트래픽을 보낼 수 있다 - **이론상
가능**하다. 그러나 Argo Rollouts 컨트롤러는 그 Service의 selector를
자신이 계산한 "현재 active 리비전" 해시로 **지속적으로 재조정**하는게
일반적인 컨트롤러 패턴이다 - **이 프로젝트에서 이 재조정 주기·충돌
여부를 직접 측정하거나 로그로 확인한 적은 없다**(일반적인 K8s
컨트롤러 reconcile 동작에 근거한 추정이며, 이 저장소의 실측 사실이
아님을 명시한다). 확인되지 않은 상태에서 이 우회를 "존재하는 방법"
으로 세지 않는다.

**판정**: 공식 지원 방법 부재(확인됨), 우회는 충돌 위험이 있으나
직접 검증된 적 없음(**확인 필요/증거 부족**) - 어느 쪽으로도 "지금
GitOps 관리와 충돌 안 하는 방법이 있다"고 답할 근거가 없다.

## 3. 첫 개별 피해 전 부하 신호와 라우팅 완료 시간

**§156의 즉각적인 첫 피해를 반대 증거로 포함**: §156에서 이미 확인한
대로, 19개 유효 `load_ramp` trial 중 **12개는 `t_first_bad` 자체가
주입 후 2초 안**(0.06~1.81초)에 나온다 - 이건 이번 방안이 "탐지 뒤
무엇을 할지"를 바꾸는 것과 무관하게 그대로 적용되는 상한이다(§157
§0과 동일 논리). 나머지 7개 중 텔레메트리로 확인 가능한 2개만 실제
전조(24.2초·107.6초 리드)가 있었다(§156 §1, 재인용 - 새 계산 안 함).

이번 방안 고유의 추가 질문("트래픽을 옮기는 라우팅 자체가 얼마나
걸리는가")은 **§2에서 방법 자체를 확인 못 했으므로 답할 수 없다** -
없는 메커니즘의 소요시간은 측정 대상이 아니다.

**판정**: 시간 여유는 §156과 동일한 한계 안에 있고(확인됨, 재인용),
이번 방안 고유의 라우팅 시간은 **확인 불가**(방법이 없어서).

## 4. 요청별 어느 pod가 처리했는지 입증할 계측 - 부재(재확인)

§152 §6·§155 §7에서 이미 확인한 공백을 이번 안에 다시 적용한다:
`probe.py`/`ramp.py` 원자료 어디에도 요청ID·서빙 pod 식별자가 없다.
이번 방안은 "두 pod가 실제로 트래픽을 나눠 받았다"는 것 자체를
**요청 단위로 증명할 방법이 없다** - Service 수준 라우팅 설정이
바뀌었다는 것(§155의 L2 수준 증거)과 "실제로 각 pod가 몇 건을
처리했는가"는 별개다(§155 §7.2와 동일한 간극).

**판정**: 부재(확인됨, 새 계측 없이는 증명 불가).

## 5. 기존 단일-pod 비교와 별도 버전으로 공정하게 비교할 방법

이 방안은 "1 pod가 서빙, 1 pod는 대기"라는 지금까지의 전제 자체를
바꾼다(둘 다 서빙) - 그래서 **기존 §147~152의 단일-pod 결과와 절대
풀링하면 안 되고**(사용자의 기존 원칙과 동일), 검증하려면 완전히
새로운 세션에서 이 구조로 다시 측정해야 한다. 다만 §2·§4가 막혀
있어 **"어떻게 구현할지"조차 정해지지 않은 상태**라, 비교 방법을
설계하는 것 자체가 시기상조다 - 이 항목은 §2·§4가 풀리기 전까지는
논의 대상이 아니다.

## 6. 종합 판정: NO-GO

- §1(자원 여유): **확인됨, 유리함** - §157의 후보들과 달리 이 안은
  자원 문제가 없다.
- §2(트래픽 분담 방법): **부재 확인 + 우회는 미검증 위험** - GO의
  전제 조건이 성립하지 않는다.
- §3(시간 여유): §156과 동일한 한계 - 대응 방식과 무관하게 이미
  좁다.
- §4(요청-pod 계측): **부재 확인** - 두 번째로 막힌 조건.
- §5(공정 비교): §2·§4가 안 풀려 검토 시기상조.

지시받은 기준("조건 중 하나라도 안전하게 입증할 수 없으면 증거
부족 또는 NO-GO")에서, §2와 §4는 "불확실"이 아니라 **직접 코드·설정
확인으로 "지금은 없다"가 나온 항목**이라 단순 증거 부족보다 한 단계
더 나아간 **NO-GO**로 판정한다 - 설정만 보면 그럴듯해 보인다는 이유로
GO를 내리지 않는다(지시대로). §156의 NO-GO와 §152의 0/40, 후속 5쌍
결과는 이번 검토로 바뀌지 않는다.
