## 1. WinError 1455 — 확정 사실 vs 후보 원인 vs 미확인

**확정된 사실(코드·로그로 직접 확인)**:
- 실패 위치: `run_once.py`의 최상위 `except Exception as e:` 핸들러
  (862~864행) - `result.outcome="invalid_run"`,
  `result.invalid_reason=f"예외: {type(e).__name__}: {e}"`로 저장.
- **이 핸들러는 `str(e)`만 기록한다 - `traceback.format_exc()` 등 전체
  스택트레이스를 저장하는 코드는 이 경로 어디에도 없다**(grep으로
  확인). 즉 `invalid_reason`의 한 줄 메시지(`OSError: [WinError 1455]
  이 작업을 완료하기 위한 가상 페이징 파일이 너무 작습니다`)가 이
  결과에 남을 수 있는 구조적 최댓값이다 - 내가 못 찾은 게 아니라
  애초에 더 상세한 기록이 저장되지 않는다.
- evidence jsonl의 마지막 이벤트: `send_stopped(reason=stop_file,
  elapsed_sec=524.001)` - OBSERVING 루프가 524초 지점에서 예외로
  중단됐다.

**후보 원인(미확정 - 이번 턴에 명시적으로 구분)**: "이 세션이 길게
지속되며 누적된 로컬 프로세스 부하"는 **후보일 뿐 확정된 원인이
아니다.** §142는 이를 "관련 있을 가능성이 높다"고 썼는데, 이는
과도한 확신이었다 - **이 문서에서 정정한다.** 실패 순간의 실제
commit charge를 측정한 기록이 존재하지 않으므로(2절), "누적 부하
때문"이라는 주장을 확정할 근거가 없다. 마찬가지로 "일시적 스파이크"
라는 §142의 추정도 확정 근거가 없기는 동일하다 - 둘 다 사후
추정이지 실측이 아니다.

**증거 스트림별 분리(각각 독립적으로 확인됨)**:
| 계층 | 증거 | 상태 |
|---|---|---|
| 예외/코드 계층 | `OSError: [WinError 1455]`, run_once.py 862행 generic handler | 확정 - Windows 가상메모리 할당 실패, 코드 버그 아님 |
| detector 생존 | detector 로그, 12:48:44 UTC까지 15~16초 간격 연속 정상 평가 | 확정 - crash 없음 |
| probe/연결성 | `probe_valid=True`, t_slo/t_recovery 정상 산출(15.09초 gap) | 확정 - probe 죽지 않음, SLO 판정기 정상 |
| 클러스터 상태 | postflight: quiescent=true, Rollout DESIRED=CURRENT=AVAILABLE=1 | 확정 - 클러스터 오염 없음 |

**다른 원인을 "완전히 배제"한다고 말하지 않는다** - 위 표는 "이
계측 범위 안에서 이상 징후가 발견되지 않았다"는 뜻이지, 기존
계측이 애초에 볼 수 없는 원인(예: 다른 애플리케이션의 순간적 메모리
스파이크)까지 배제한다는 뜻은 아니다.

**신규 확인(이번 턴)**: Windows 이벤트 뷰어 Application/System 로그를
실패 추정 구간(21:25~22:00 KST = 12:25~13:00 UTC)으로 조회 - **Error/
Warning/Critical 레벨 항목 0건**(`Get-WinEvent` 결과: "No events were
found"). 이 네거티브 결과의 의미를 과장하지 않는다 - 개별 프로세스의
메모리 할당 실패(`OSError`)는 보통 OS 레벨 이벤트 로그에 별도로
기록되지 않으므로, "이벤트 로그에 없다"가 "문제가 가벼웠다"를
증명하지는 않는다. 다만 Windows 자체의 시스템 전역 저메모리 감지
메커니즘(Resource-Exhaustion-Detector류)도 발동하지 않았다는 점은
사실로 기록한다.

## 2. 로컬 자원 진단

**현재 값 vs 실패 시점 값 - 명시적으로 구분한다**:

| 지표 | 실패 시점(~21:41~21:50 KST, 2026-09-25) | 이번 턴 확인값 |
|---|---|---|
| Commit headroom | **기록 없음 - 사후 확정 불가** | 1차 확인 ~511MB → 2차 확인(22:09 KST) ~1,911MB |
| 물리 free RAM | 기록 없음 | 1차 639MB → 2차 1,877MB |
| Commit limit | 기록 없음(추정상 거의 불변) | ~46,464MB |

**이 실험의 계측(cost-sampler)은 kubectl/detector 프로세스 단위
자원만 기록하고, 시스템 전역 commit charge는 애초에 수집한 적이
없다 - 그래서 "실패 시점" 칸을 현재값으로 대신 채우지 않는다**(지시
그대로 - 과거 값을 현재값으로 단정하지 않음).

**변동성 자체가 중요한 발견**: 같은 세션 안에서 단 10~20분 사이에
commit headroom이 ~511MB→~1,911MB로 약 1.4GB 진동했다 - 이건 이
실험과 무관한 다른 프로세스들의 활동에 좌우된 것이다. 즉 "지금
스냅샷이 괜찮아 보인다"는 것만으로는 40~60분짜리 라이브 세션(준비+
trial 2개+drain+정리) 전체의 안전을 보장하지 못한다.

**페이지 파일**: `Win32_PageFileUsage` = 할당 30,522MB / 사용
6,649MB(정상 범위로 보임) - 그러나 이건 WinError 1455와 직결된
지표가 아니다(commit limit/charge가 더 직접적인 지표, §요약 참고).
`Win32_PageFileSetting` 조회 결과 빈 값 - 시스템 관리형(자동 크기
조정)으로 추정, 고정 크기 설정 아님.

**디스크**: D: 드라이브 여유 120.3GB - 디스크 공간 자체는 병목이
아니다(페이지 파일이 늘어날 공간은 충분).

**메모리 상위 소비 프로세스(이름/PID/용량만, 커맨드라인 확인
안 함)**: `svchost`(PID 21940, ~13.66GB) - Windows 시스템 프로세스,
어떤 서비스인지는 특정하지 않음(범위 밖). 그 외 사용자 애플리케이션
다수 인스턴스(`claude`, `ChatGPT`, `Notion`, `chrome`, `MsMpEng`,
`SnippingTool` 등, 이름만 확인).

**Python 프로세스**: 11개, 합계 private ~6.28GB. 이 중 **이 실험
자신의 detector 프로세스로 기록된 PID 5개(각 trial의 cost-*.json
`local_detector.summary.last_known_pid`에서 추출) 전부 "실행 중
아님"으로 교차 확인됨** - 즉 지금 떠 있는 11개 python 프로세스 중
이 실험이 만든 잔존 프로세스는 0개다. 나머지 11개가 무엇인지는
커맨드라인을 보지 않고는 알 수 없고, 지시상 커맨드라인 확인은
범위 밖이라 하지 않았다 - **정직하게 "용도 특정 불가"로 남긴다.**

**구분 불가 인정(지시 §2 마지막 요구사항 그대로)**: 특정 프로세스의
누수 / 시스템 전역 pagefile-commit 여유 부족(다른 앱들의 정상적인
동시 사용 총합이 큰 것뿐) / 디스크 공간 부족 중 **무엇이 진짜
원인인지 구분할 수 없다.** 디스크 부족은 위 수치로 배제 가능하지만,
"특정 프로세스 누수"와 "여러 프로세스의 정상적 합산이 그냥 큰 것"은
실패 순간의 스냅샷이 없어 구분할 방법이 없다.

## 3. 정리 권한 — 이번 턴 조치 기록

**이번 턴에 종료한 프로세스: 0건.** 엄격한 권한 범위(이 작업이
생성·소유·용도 확인·이미 사용 끝난 것) 안에서 종료 가능한 대상 자체가
없었다 - 이 실험 자신의 detector PID 5개는 이미 스스로 종료돼 있었고
(2절), 그 외에는 소유·용도를 확인할 수 있는 게 없었다.

**명시적으로 건드리지 않은 것**: `svchost`(시스템 프로세스),
나머지 python 프로세스 11개(용도 미확인 - 이름만으로 일괄 종료
금지), 사용자 애플리케이션 전체, 활성 포트포워드(이번 턴에 상태를
바꿀 근거 있는 조작을 하지 않았으므로 §142 postflight의 quiescent
상태가 계속 유효하다고 본다). **시스템 설정 변경: 0건**(페이지
파일 크기, 시스템 관리 방식 등 전부 조회만 했다).

**제안만 하고 실행하지 않은 것(사용자 승인 필요)**:
1. 다수 인스턴스로 떠 있는 사용자 애플리케이션을 직접 정리
2. 나머지 python 프로세스 11개를 사용자가 직접 용도 확인 후 불필요한 것 종료
3. 재부팅으로 장시간 세션 누적 상태 정리(가장 확실하지만 가장 무거운 옵션)

이 중 어느 것도 이번 턴에 실행하지 않았다 - 실행하려면 사용자의
명시적 승인이 먼저 필요하다.

## 4. 재실행 준비 기준 + 최종 판단

**명시적 기준(이번에 새로 정의 - 과거 실측 피크 데이터가 없어
보수적으로 잡은 추정치임을 명시한다, 엄밀한 실측 검증값 아님)**:
- **시작 거부 기준**: commit headroom < 4GB **또는** 물리 free RAM
  < 2GB → 시작하지 않는다.
  - 근거: 이 실험 자신의 신규 프로세스(detector+probe+cost-sampler+
    kubectl port-forward)가 추가로 쓸 것으로 보이는 양(기존 detector
    프로세스들이 개별 ~550MB대였던 것 참고, 트리 합산 대략 1~1.5GB
    추정) + 이번 턴에 실측한 배경 변동성(10~20분 사이 최대 ~1.4GB
    스윙) 감안한 여유.
- **점검 주기**: 라이브 세션 중 5분 간격, 요청 경로와 분리된 저빈도
  로컬 체크, 두 arm에 동일 적용.
- **즉시 중단 기준**: 점검 중 어느 시점이든 commit headroom < 1.5GB
  로 떨어지면 진행 중인 trial을 정상 정리(quiescence 대기 포함) 후
  즉시 중단.
- 물리 메모리 단독으로 "충분하다" 판단하지 않는다 - commit headroom을
  우선 신호로 쓴다(지시 그대로).

**현재 값과 대조**: commit headroom 1,911MB(< 4,096MB 기준 미달),
물리 free RAM 1,877MB(< 2,048MB 기준에도 근접/미달) →
**시작 거부 기준에 해당한다.**

**최종 판단: 이번 턴에 라이브 재시도를 실행하지 않는다(NO-GO).**

근거: (1) 실패 시점의 실측 자원 기록이 없어 "지금 상태가 그때보다
나은지"를 검증할 방법이 원천적으로 없다, (2) 현재 헤드룸이 같은
세션 안에서도 10~20분 사이 ~1.4GB 진동할 만큼 변동성이 크고 이
실험이 통제할 수 없는 외부 프로세스에 좌우된다, (3) 이번에 정의한
보수적 시작 기준(4GB)에 현재 값(1.9GB)이 못 미친다, (4) 엄격한
정리 권한 범위 안에서 헤드룸을 늘릴 조치가 없다(3절). "증거가
불충분하면 재실행하지 않는다"는 지시를 그대로 따른다.

## 5. 기술적 실패 ↔ 새 시도 연결 메커니즘 확인

**기존 공식 메커니즘 확인 결과**: `run_all_scenarios.py`의
`link_technical_invalid_replacement()` / `sync_replacement_results()`
/ `apply_replacements()`는 **main experiment(45건, `mainexp-v1/v2`)가
쓰는 `state` 딕셔너리**(`official-experiment-state*.json`류) 위에서
동작하도록 설계됐다. `results/followup/`(이번 후속 실행이 쓰는
네임스페이스)는 `state` 딕셔너리 개념이 아예 없다 - 각 trial이
독립된 `trial-*.json`/`cost-*.json`/`contract-*.json` 파일로만
존재한다. **즉 이번 후속 실행기(`run_load_ramp_followup_trial.py`)는
이 공식 replacement 기능을 지원하지 않는다** - 과거 main experiment
절차를 그대로 적용할 수 없다(지시와 일치하는 결론).

**재사용 가능한 기존 관례**: main experiment 테스트
(`test_run_all_scenarios.py`)는 대체 trial run_id를
`...-01-retry1-mainexp-v1`처럼 **원래 run_id에 `-retry1-`을 삽입**하는
패턴을 쓴다. `analyze_effect_cost_evidence.py`(65~68행)는 이 접미사가
표준 패턴과 달라 재조립 로직을 깨뜨린 적이 있다고 이미 기록하고
있다 - 즉 이 패턴을 새 네임스페이스에 옮길 때 분석 스크립트 쪽도
같이 고려해야 한다는 근거가 기존 코드에 이미 있다.

**안전하게 보존할 공식 메커니즘이 없으므로, 수동으로 우회하지 않고
최소 수정안만 제안한다(이번 턴엔 구현하지 않음 - 실행 승인 자체가
없어 미리 만들 필요가 없다)**:
1. `run_load_ramp_followup_trial.py`에 선택 인자 `--replaces
   <original_run_id>` / `--replacement-reason <text>` 추가 - 이미 매
   trial마다 쓰는 `contract-{run_id}.json`에 `replaces_run_id` /
   `replacement_reason` / `original_result_path` /
   `original_result_sha256` 필드만 추가(새 서브시스템 없음, 기존
   계약 파일 재사용).
2. 원본 파일(`trial-load_ramp-fixed_threshold-03-post_hoc_followup-
   v1.json` 등)은 절대 수정하지 않는다 - 새 run_id
   (`load_ramp-fixed_threshold-03-retry1-post_hoc_followup-v1`)가
   완전히 별도 파일 세트를 만든다.
3. `correct_followup_138.py`의 `analyze_arm_corrected(arm, rep=1)`은
   현재 `run_id`를 `rep` 숫자로부터 고정 조립한다(161행) - retry
   파일을 가리키려면 선택 인자(예: `run_id_override=None`) 하나만
   추가하면 된다(기존 로직 재사용, 새로 만들 필요 없음).

이 세 가지 모두 기존 파일에 필드/인자 몇 개를 추가하는 최소 diff로
끝난다 - 별도 상태 관리 시스템을 새로 만들 필요는 없다.
