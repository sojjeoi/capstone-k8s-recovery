## 1. 한 줄 목표

현재 CPU 압박에서는 CPU 임계값이 선택됐다. **압박의 종류가 바뀌면(메모리) 같은 사전등록 선택 절차가 다른 감지기를 고르는가?** 를 확인한다. 결과가 어느 쪽이든 발표할 수 있게 단계마다 중단 지점과 해석을 미리 적는다.

## 2. 왜 이 계획이 "성공 가능성이 가장 높은" 모양인가

- 안전 범위 안의 메모리 압박은 지금까지 서비스 저하를 거의 만들지 못했다(§3). 그래서 "메모리 실험을 하면 IF가 이긴다/CPU가 진다"를 전제로 두지 않는다.
- 대신 **싼 단계부터 순서대로** 놓고, 앞 단계에서 환경이 질문에 답할 수 없다고 나오면 거기서 멈추고 그 사실을 결과로 보고한다. (연구 지침: 환경·지표가 질문을 검증할 수 있는지 확인하기 전에 반복 실험을 늘리지 않는다.)
- 시간(10/30)이 모자라면 세션 수나 Gate를 줄이지 않고 **미완료로 남긴다**(Phase 2 사전등록 §15와 같은 원칙).

## 4. 연구 질문과의 연결 (연구 지침 5항목)

1. **원래 질문에 답하는 이유**: "CPU 단일 지표로 구분하기 어려운 상황에서 여러 지표를 쓰는 감지기가 더 유용한 신호를 주는가"에 직접 답하려면 CPU로 분리되지 않는 저하 환경이 있어야 한다. 메모리 압박은 CPU 이외의 지표가 먼저 움직이는 후보다. 다만 우월성은 가설이며 보장하지 않는다.
2. **CPU만으로 구분 어려운 것과 추가 지표의 정보**: CPU는 평소와 비슷한데 메모리 작업량이 늘어난 상태. 단 5000MB 기록처럼 stress가 CPU까지 올릴 수 있어(§3) 이 전제가 성립하는지부터 확인한다.
3. **정상 학습·보정·독립 검증·공정 비교군**: IF는 동결된 c3-A를 쓴다(재학습 금지). 같은 지표를 쓰는 단순 규칙으로 **메모리 임계값**을 비교군에 넣는다(§8). 이게 없으면 "CPU는 메모리를 못 보니 당연히 진다"가 되어 비교가 되지 않는다.
4. **관측 가능성·성공/중단 기준**: §6의 분류 A~D, §7의 의사결정표.
5. **10/30까지의 최소 작업**: 계층 L0(문서)는 확정적이고, L1(live)은 승인과 안전 점검 통과가 필요하며, L2(선택 실험)는 L1이 CLEAN일 때만 검토한다(§5).

## 5. 단계 (싼 것부터, 각 단계 끝에서 멈추고 보고)

| 계층 | 내용 | 클러스터 | 승인 | 이 단계만으로 말할 수 있는 것 |
|---|---|---|---|---|
| **L0** | 기존 환경 후보 기록 정리: Axis 2 NO_GO, I/O feasible=false, 요청 형태 부적합, 메모리 기록(§3)을 한 장으로 | 없음 | 문서 커밋·push만 | "CPU 이외로 구분되는 저하 환경을 이 하드웨어에서 만들기 어려웠다"는 사실 기록 |
| **L1-0** | Step 0 읽기 전용: 노드별 MemAvailable, active Pod의 노드와 작업 메모리, 스로틀링 지표 수집 여부, 어댑터 사전 검사 통과 여부 | 읽기 전용 | 필요 | 안전 점검을 통과하는지 |
| **L1-1** | 기준선 세션 1회(1200 s, stress 없음): CPU 정상 범위(envelope) 확보 | live | 필요 | CPU/메모리 정상 범위 |
| **L1-2** | **Pilot A**: 1600MB × 120 s, 단일 주입, worker 1, 대상 = active vLLM Pod, 개발 반복 2회 | live | 필요 | 분류 A~D(§6) |
| **L2** | 선택 실험(§8). **L1-2가 A. CLEAN 2/2일 때만** 검토 | live | 필요 | 이 환경의 선택 결과 |

- L0은 지금 바로 할 수 있고 실패하지 않는다. L1부터는 안전 점검과 승인이 막을 수 있다.
- **Pilot B(안전 상한 5GiB 변경 또는 강도 확대)는 이 계획에 넣지 않는다.** 사용자가 승인하지 않았고, 동결된 안전 규칙 변경은 별도 결정이다.
- **안전 규칙은 그대로다**(어댑터 변경 없음): 주입 전 MemAvailable ≥ 3GiB, MemAvailable − 주입량 ≥ 4GiB, 기준 작업 메모리 + 주입량 ≤ 5GiB, active Pod 정확히 1개, 노드 Ready·pressure 없음. 주입 중 MemAvailable < 3GiB, 작업 메모리 > 5GiB, OOMKilled, 재시작 증가가 생기면 그 회차를 무효로 하고 즉시 중단한다.

### 5.1 노드 메모리 점검 문제 (막혔던 지점)

- 1600MB를 쓰려면 대상 노드의 MemAvailable이 **5.56 GiB 이상**이어야 한다. 이전에는 sj-worker가 4.197 GiB여서 막혔다.
- 풀 수 있는 길은 둘이다. 둘 다 사용자 결정이다.
  1. **sj-worker calico 정비를 승인**해 메모리를 회복시킨 뒤 같은 노드에서 시도한다(정비는 sj-worker2에서 이미 검증됐다).
  2. **active vLLM이 sj-worker2에 있는 상태**에서 시도한다. sj-worker2는 이미 정비돼 여유가 충분하다. 단 active를 옮기려면 Rollout 전환이 필요해 별도 승인이 필요하다. 현재 active의 노드는 L1-0에서 읽기 전용으로 확인한다.
- 정비 승인 없이 점검이 계속 막히면 L1은 시작하지 않고 L0 결과로 마무리한다.

## 6. 판정 규칙 (L1-2, 결과를 보기 전에 고정한 규칙)

SLO는 공식 SLO v3(60 s P95 > 0.648 s가 30 s 이어짐, 또는 60 s 성공률 < 99%)를 **수정 없이** 쓴다.

**"메모리 관련 저하"로 인정하는 조건(셋 다)**
- R1: 위반 구간의 첫 표본이 주입 관측 시각 이후다. 주입 전부터 이어진 위반은 인정하지 않는다.
- R2: 주입 후에 보낸 요청만으로 같은 판정을 다시 돌려도 같은 구간에서 지속 위반이 재현된다(성공률 위반이면 실패 요청이 모두 주입 후 요청).
- R3: 위반이 stress가 걸려 있는 동안 시작된다. stress 정리 뒤에 시작된 위반은 "정리 이후 위반"으로 따로 기록하고 인정하지 않는다.
- 재현 기준은 개발 반복 **2/2**다.

**분류**

| 분류 | 조건 |
|---|---|
| D. TOO STRONG / INVALID | 어댑터 무효 처리·중단, OOM, 재시작, eviction, 노드 이상, 계산 불가(요청 수 부족·공백) |
| C. NEGATIVE CONTROL | 메모리 증가는 확인(요청량의 80% 이상 상승)됐지만 인정된 위반 구간 없음 |

| B. CONFOUNDED | 인정된 위반 구간이 있지만 CPU 임계값을 넘었거나 CPU 정상 범위를 벗어남 |

- CPU가 임계값을 넘었다고 회차를 무효로 처리하지 않는다. 그것도 결과다.
- 한계: stress의 CPU와 vLLM의 CPU는 같은 컨테이너 지표에 합쳐져 분리할 수 없다.
- 2회 결과가 서로 다르면 feasible=false로 보고, 강도를 다시 만들거나 반복을 늘리지 않는다.

## 8. L2 선택 실험 (A. CLEAN일 때만, 구현·동결 전에는 시작하지 않음)

Phase 2 사전등록(rev6)의 Gate 구조를 그대로 쓰고, 달라지는 점만 적는다.

**후보 3개**
| 후보 | 정의 | 비고 |
|---|---|---|
| A. CPU 임계값 | `cpu_mean > 1.6842544293089357`, 3연속, 쿨다운 60 s | 동결 규칙 그대로 |
| B. **메모리 임계값 (새 비교군)** | memory_mean 상한을 정상 보정 세션에서 구하는 규칙 | 값은 **구현 전 동결**. 아래 열린 결정 참고 |
| C. c3-A IF | `decision_function < −0.1948341270493127`, 3연속 | 동결, 재학습·재보정 금지 |

- 열린 결정 1(사용자): 메모리 임계값 산정 규칙. 예) 학습·보정 정상 세션의 memory_mean 최댓값에 사전 고정 여유를 더한 값. 값과 여유는 압박 데이터를 보기 전에 정해 동결한다. 이 문서에서는 정하지 않는다.
- Gate 2(주입 뒤 평가만으로 363 s 안 3연속, 압박 5개 중 4개 이상), Gate 3(정상 불필요 신호), tie-break, 결과 상태 5개, 세션 수(정상 4·압박 5), 시도 상한은 rev6 규칙을 따른다. 압박 세션은 새 환경의 Pilot A 조건(1600MB)이어야 한다.
- 선택된 감지기로 실제 복구를 이어가는 Stage 2는 L2 결과를 본 뒤 별도로 결정한다.
- **기대에 대한 솔직한 메모**(추정): 이 환경에서는 메모리 지표 자체가 압박을 직접 드러내므로 메모리 임계값도 Gate 2를 통과할 가능성이 높다. 그래서 갈림은 Gate 3(정상 운전 불필요 신호)와 시각에서 나올 가능성이 크다. "IF만 통과"를 기대 결과로 두지 않는다. 단순 규칙이 선택되어도 "환경에 맞춰 가장 단순한 충분한 감지기를 고른다"는 같은 구조의 성공이다. IF는 정상 memory_mean의 0.2% 이동에도 이상 판정을 낸 기록이 있어(vn01), 정상 운전 불필요 신호가 나올 위험이 있다.
- 필요한 구현: Phase 2 실행기에 메모리 후보와 메모리 압박 주입을 추가하고 다시 IMPLEMENTATION FREEZE를 해야 한다. 정상 4세션(약 78분씩) + 압박 5세션 수집이 추가로 든다. 10/30 전에 끝나지 않을 가능성이 높다(추정).
