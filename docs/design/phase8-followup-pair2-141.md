# Phase 8 — 두 번째 쌍(proposed→fixed_threshold, rep02) 실행 결과 (§141)

§140에서 동결한 계약대로 실행했다. **proposed 1회 → fixed_threshold
1회**(첫 쌍과 반대 순서), 동일 부하·요청·900초 관측·cooldown·수집 규칙,
새 run_id(`...-02-post_hoc_followup-v1`, 기존 `-01-` 파일 무변경).
모델·threshold·feature·streak·cooldown·SLO·부하강도·라우팅·keepalive
전부 미변경. 세 번째 trial·자동 대체·재시도 0건.

## 1. 수정된 종료 처리의 라이브 검증 결과

**§140 기술적 통과조건 2개 — 둘 다 PASS**:

| 조건 | fixed_threshold rep02 | proposed rep02 |
|---|---|---|
| drain 정상종료(강제종료 아님) | PASS | PASS |
| cohort 원인불명 이상 0건(terminal-only/duplicate-sent/duplicate-terminal) | PASS(0건) | PASS(0건) |

**본 실행 전 스모크 테스트**(장시간 장애 pilot 아님 - stop-file 메커니즘만
짧게 확인): 실제 클러스터·실제 이미지의 별도 pod에서 stop-file을
touch한 뒤 kubectl 왕복으로 폴링 - **약 4.5초 만에 자연 종료**(`/probe.exit`
정상 기록, `send_stopped` 이벤트에 `reason=stop_file` 정확히 기록됨,
90초 예산 안에서 여유 있게 완료). 본 실행 두 trial의 콘솔 로그에도
drain-timeout이나 회수 실패로 인한 `RuntimeError`가 없음을 확인했다.

**결론**: stop-file 기반 종료 처리가 로컬 오프라인 테스트뿐 아니라
실제 클러스터에서도 의도대로 동작한다 - 이번 계측 프로토콜을 추가
반복에도 계속 쓸 수 있다.

## 3. episode별 시간선과 실제 전환의 위치

**fixed_threshold rep02** — rep01과 동일 패턴:

| | 시각 |
|---|---|
| t_injection | 12:00:50.276 |
| episode 1: t_slo→t_recovery | 12:02:54.153→12:03:24.242(**30.09초**) |
| episode 2: t_slo→t_recovery | 12:04:32.455→12:09:09.223(4분37초) |
| t_detection / t_switch | 12:07:06.273 / 12:07:13.680 |

탐지(222.0초 뒤)·전환(229.4초 뒤) 둘 다 **episode 2 구간 안**(rep01과
동일 - "시간적 대응 관계, 인과 미확정"만 기술).

**proposed rep02** — **rep01과 다른 패턴**:

| | 시각 |
|---|---|
| t_injection | 11:36:47.944 |
| episode 1: t_slo→t_recovery | 11:37:36.227→11:37:37.253(**1.03초**) |
| episode 2: t_slo→t_recovery | 11:38:48.192→11:39:22.353(34.2초) |
| episode 3: t_slo→t_recovery | 11:40:59.431→11:45:11.322(**4분12초**) |
| t_detection / t_switch | 11:37:37.987(회복+0.73초) / 11:37:48.922(회복+11.67초) |

탐지는 episode 1 회복 **0.73초 뒤**(사실상 거의 동시 - rep01의
176~330초 지연과 전혀 다른 패턴), 전환은 회복 **11.67초 뒤**로 episode
2가 시작(70.2초 뒤)하기 **전**의 빈 구간에 있다 - **세 episode 중
어느 것의 [t_slo, t_recovery] 안에도 들어가지 않는다**(계약서 §2의
분류 규칙을 그대로 적용한 결과, 임의 판단 아님).

**해석(3단계, 인과 유보)**:
- **관측된 사실**: 같은 arm(proposed)인데도 두 반복에서 탐지·전환과
  episode의 시간적 관계가 다르다 - rep01은 재위반(episode 2) **안에서**
  탐지, rep02는 첫 회복 **직후**(0.73초) 탐지 후 전환이 재위반 **이전**
  빈 구간에서 일어났다.
- **부합하는 가설**: rep02의 즉각적 탐지는 IF 모델이 episode 1을 만든
  바로 그 이상 신호를 실시간에 가깝게 포착했을 가능성과 부합한다 -
  그런데 판정기의 30초 지속조건 때문에 SLO 판정(t_recovery)은 그보다
  먼저 "회복"으로 확정된 것일 수 있다(탐지 파이프라인과 SLO 판정
  파이프라인이 서로 다른 신호·다른 지속조건을 쓰므로 독립적으로 확정
  시점이 어긋날 수 있음 - §137에서 이미 확인한 구조).
- **미검증**: 전환이 없었다면 episode 2·3이 어떻게 됐을지는 알 수 없다.

## 6. 현재 반복에서 일관된 점과 달라진 점

**반복별 결과(합산 아님, 항상 분리)**:

| | rep01 fixed | rep01 proposed | rep02 fixed | rep02 proposed |
|---|---|---|---|---|
| 실패율 | 0.11% | 0.0% | 0.11% | 0.11% |
| 지연초과율 | 7.67% | 6.67% | 5.67% | 6.00% |
| episode1 recovery_sec | 9.91s | 10.03s | 30.09s | 1.03s |
| episode 수 | 2 | 2 | 2 | **3** |

**arm 간 차이의 방향(각 반복에서 fixed−proposed)**:

| | 실패율 차이 | 지연초과율 차이 | 어느 쪽이 유리? |
|---|---|---|---|
| rep01 | +0.11%p | +1.00%p | **proposed** (둘 다) |
| rep02 | 0.00%p | **−0.33%p** | **fixed가 지연초과율에서 근소 우위**, 실패율은 동률 |

**일관된 점**:
- 두 반복 모두 첫 episode는 탐지·전환보다 먼저 자체 회복됐다.
- 두 반복 모두 fixed_threshold는 탐지·전환이 episode 2 안에 있다(같은
  패턴 재현).
- 두 반복 모두 detector 비용은 proposed가 fixed_threshold보다 뚜렷이
  크다(CPU 2.9~5.8배, 메모리 3.9~4.2배 - 배율 자체는 반복마다 다르지만
  "더 크다"는 방향은 일관됨).
- 두 반복 모두 실제 전환은 정확히 1회(idempotency로 중복 차단 확인).

**달라진 점(이점이 일관되지 않음 - 정당한 결과로 보고)**:
- **rep01에서는 proposed가 실패율·지연초과율 둘 다 낮았지만, rep02에서는
  실패율이 동률이 됐고 지연초과율은 오히려 fixed_threshold가 근소하게
  낮았다.** n=2에서 이미 방향이 바뀌었다 - "proposed가 항상 더 낫다"는
  주장은 이 시점에서 명백히 성립하지 않는다.
- proposed의 episode 구조가 반복마다 다르다(2개 vs 3개) - 그리고
  탐지·전환이 재위반 **안**(rep01)에 있는지 재위반 **전**(rep02)에
  있는지도 달라졌다.
- proposed rep02에서 처음으로 **동일 trial 안에서 detector가 6번 더
  이상 신호를 냈지만 전부 `skipped_duplicate`로 무시됐다**(idempotency_key
  가 `{run_id}:{signal_type}`이라 trial당 첫 신호만 조치로 이어질 수
  있는 구조 - §137에서 이미 코드로 확인했던 설계가 이번에 실제 반복에서
  처음 구체적으로 관측됨). episode 2·3이라는 새로운 위반이 있었는데도
  시스템은 구조적으로 더 이상 반응할 수 없었다 - 이건 proposed 쪽의
  실제 한계로 정직하게 기록한다.

## 7. 추가 반복 계획과 예상시간

**이번 승인 범위는 여기까지다 - 5회/arm 전체를 자동 실행하지 않는다.**
5회/arm은 소표본 기술통계 목적의 제안일 뿐 통계적 검정력을 보장하지
않는다(사용자 지시 재확인). 유의성·일반적 우월성·산업 적용 비용대비
효과는 아직 확정하지 않는다.

**지금까지 확보**: 2쌍(4trial) - fixed→proposed(rep01), proposed→fixed
(rep02), arm 순서 교차 완료.

**남은 순서(사전 고정, 다음 승인 대기)**: 5회/arm 목표라면 앞으로
3쌍(6trial)이 더 필요하다 - 순서는 계속 교차한다: 다음(rep03)은
fixed→proposed, 그다음(rep04)은 proposed→fixed, 마지막(rep05)은
fixed→proposed. 매 세션 1쌍만(§139/§140에서 이미 재추정 - trial당
prep(≤8분)+관측(15분)+drain(이번엔 수초~최대 90초, 이번 두 trial 다
수초 내 완료)+정리(~1~2분) ≈ 24~25분, 한 쌍 ≈ 48~50분, 90분 예산 안).

**다음 승인 전 확인할 것 없음**: 계측 프로토콜은 이번 쌍에서 기술적
통과조건 2개를 다 통과했으므로 추가 코드 수정 없이 동일 방식으로
반복 가능 - 다만 반복 수·시점은 사용자 승인을 기다린다.
