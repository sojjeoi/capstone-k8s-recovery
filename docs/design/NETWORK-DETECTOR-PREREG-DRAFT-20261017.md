## 1. 왜 이 감지기인가
- 네트워크 지연 파일럿(2026-09-19, 조치 없음 arm 1회)에서 서비스는 느려졌는데(P95 0.317 → 최대 8.3초) **vLLM CPU는 정상과 같았다**. CPU 임계값(1.684)은 정상 상태의 CPU(약 1.66)와 거의 붙어 있어 이 상황을 구분하지 못한다.
- 같은 시간대에 **Pod까지의 통신 소요 시간**(`scrape_duration_seconds`)은 0.014초 → 2.83초(500ms 단계) → 7.68초(4000ms 단계)로 크게 움직였다. vLLM 자신의 요청 처리 시간(서버 측)은 움직이지 않았다.
- **데이터 지위**: 이 지표는 위 파일럿을 본 뒤 골랐다. 파일럿은 **개발 자료**이고 독립 검증이 아니다.

## 4. 결과: 임계값 (개정 2)

**T = 0.1242326662 초** (`net_mean > T`가 3회 연속이면 신호). `calibration_failed=false`.

- 전체 정상 평가 지점의 `net_mean` 최대는 0.1351초다. 연속 3회 조건 때문에 T가 최대값보다 조금 낮다.
- 개정 1(0.0643초)은 c3 보정용 6개만 썼다. 세션을 늘리자 값이 0.0978 → 0.1242초로 올랐다. 정상 상태에서 가끔 통신 시간이 튀는 구간이 c3r01 말고도 있었기 때문이다(c1tr01에서도 0.107초).
- **세션 안 신호 0은 정의상 당연하다.** 그래서 개발 단계의 정직한 추정으로 **leave-one-session-out**을 했다(`python experiments/network_detector_gate3.py --loso`, `loso-rev2.json`): 세션 하나를 빼고 나머지 19개로 임계값을 다시 정해 빠진 세션의 신호를 센다.
  - 20개 세션 중 **19개는 신호 0**, 신호가 난 세션은 **c3r01 하나**(빼면 T=0.0978초, 신호 2건, Gate 3 분류기로 둘 다 `unnecessary`).
  - 즉 정상 세션 약 17시간(c3 70분 × 10 + c1 30분 × 10)에서 불필요 신호 2건이다. 같은 세션에서 CPU 임계값이 낸 불필요 신호와 직접 비교할 수는 없다(세션 구성이 다름).
  - 한계: 세션들이 시간상 가깝고 독립이 아니며, 같은 자료로 조정한 값이므로 낙관적일 수 있다. **최종 오경보는 동결 뒤 새 정상 세션 4개에서 처음 평가된다.**

## 6. 한계
- **측정 위치 한계**: 이 지표는 Pod 자체 네트워크에 지연을 걸었기 때문에 Prometheus 수집도 같이 느려진 것을 본다. **사용자 쪽 경로만** 느린 실제 장애에서는 정상으로 보일 수 있다.
- **정상 변동**: 개정 1에서 평가 세션 4개 중 1개(c3r01)가 약 4분간 임계값을 넘었다. 개정 2는 이를 범위에 포함해 올린 값이라, **새 세션에서도 비슷한 구간이 나오면 오경보가 날 수 있다.** c3r01 +2578~2758초(2026-10-10 약 15:56~15:59 UTC)의 원인은 읽기 전용으로 조사했으나 **확정하지 못했다**(아래).
- **원인 조사(c3r01 +2578~2758초, 직전 정상 구간과 비교)**:
  - 이 Pod의 `scrape_duration`만 올랐다(평균 0.039 → 0.104초, 최대 0.163초). 같은 시간 **다른 모든 수집 대상**(kubelet, node-exporter, apiserver, Prometheus 자신, vllm-preview)은 그대로였다 → 클러스터 전체·Prometheus 문제가 아니다.
  - Pod의 CPU(1.60 → 1.60 core), 스로틀링(0.29 → 0.22, 오히려 낮음), 메모리, vLLM 서버 측 지연(0.256 → 0.242초), 요청 수, 송신량 모두 변화 없음. **사용자 probe도 정상**(P95 0.327 → 0.342초, 실패 0).
  - 노드(sj-worker)의 디스크 쓰기·읽기·iowait·I/O PSI·D상태 프로세스는 오히려 낮았다 → I/O 원인이 아니다.
  - 노드 `load1`만 올랐다(평균 6.4 → 9.6, 최대 12.4). CPU 사용률·CPU PSI는 그대로라 원인은 **설명되지 않았다**.
  - 결론: **네트워크 경로나 서비스 저하가 아니라 vLLM의 `/metrics` 응답이 느려진 것**으로 보인다(원인은 모름).
- **지표 의미의 정정**: `scrape_duration`은 "Pod까지의 통신 시간"만이 아니라 **그 Pod의 `/metrics` 응답 시간(통신 + 처리)** 이다. 따라서 네트워크 지연이 없어도 오를 수 있고, 이것이 이 감지기의 오경보 원인이 될 수 있다.
- **두 감지기가 모두 Gate 2를 통과하는 환경에서는 CPU가 선택될 가능성이 크다**(CPU 정상 불필요 신호 1건, 이 감지기는 개정 1에서 5건). 새 감지기는 CPU가 Gate 2를 통과하지 못하는 환경에서만 선택될 수 있다.
- **파일럿 설정**: 파일럿은 readiness/liveness `timeoutSeconds`를 11초로 바꾼 `network_tolerant` 프로필에서 돌렸다. 그 프로필은 새 환경 프로필로 정의해야 한다.
- **IF·CPU와의 비교는 하지 않았다.** 이 문서는 후보 하나의 정의와 임계값까지만 다룬다.

## 8. 대안 지표 검토: kubelet readiness probe 소요 시간 (`net_probe`, 개발 단계, 2026-10-17)
`scrape_duration`이 vLLM `/metrics` 처리 시간까지 섞인다는 점(§4·§6) 때문에, **vLLM `/metrics`와 무관한 경로**의 지표를 같은 절차로 평가했다(`python experiments/network_detector_probe_metric.py`, 읽기 전용, 결과 `probe-metric/result.json`).

- 지표: kubelet이 잰 readiness probe 소요 시간(`prober_probe_duration_seconds` 합/건수의 60초 비율), active Pod만. 15초 격자 tick마다의 값이 곧 60초 창 평균.
- 같은 규칙(3연속·쿨다운 60·간격 15), 같은 보정(정상 세션 20개, `calibrate_threshold`), 같은 leave-one-session-out.
- 구현 중 격자 시각을 부동소수점으로 비교하는 버그를 발견해 격자 번호 비교로 고쳤다(처음 실행은 전부 누락으로 나와 폐기).

| | `scrape_duration` (개정 2) | `net_probe` (kubelet probe) |
|---|---|---|
| 정상 값 범위(세션별 최대) | 0.025 ~ 0.135초 | **0.004 ~ 0.019초** |
| 임계값 T | 0.1242초 | **0.0064초** |
| leave-one-out 신호가 난 세션 | c3r01 (2건, c3 분류기로 `unnecessary`) | c1ca01 (1건, c1은 분류 근거 없음) |
| c3 세션의 불필요 신호 합계 | **2** | **0** |
| 파일럿 첫 신호(주입 후) | 42.5초 | **57.5초** |
| 파일럿 첫 신호 vs SLO 확정 | +9.6초 | **+24.6초** |
| 지연 구간 값(파일럿) | 최대 약 7.7초 | 최대 약 7.7초 |

- **오경보는 `net_probe`가 적었다**(c3 불필요 신호 0). 대신 **감지가 약 15초 늦다.** 이 지표의 값이 probe 주기(수 초)마다 갱신되고, 60초 비율이 천천히 오르기 때문으로 보이지만 확인하지 않았다.
- **정상 값이 매우 작아(밀리초) 임계값이 6.4 ms로 낮다.** 노드·kubelet의 일시적 지터에 민감할 수 있다. 20개 세션에서는 leave-one-out 신호가 1건이었으나, 새 정상 세션에서의 결과는 모른다.
- **의존성**: readiness probe 설정(주기, timeout)에 묶인다. 파일럿은 `timeoutSeconds=11`의 `network_tolerant` 프로필이었다. 기본 설정(1초)에서는 지연이 1초를 넘으면 Pod가 재시작돼 이 지표가 포화·단절된다.
- **둘 다 Pod 자체 네트워크 지연을 보며, 사용자 쪽 경로만 느린 장애는 못 본다**(§6).
- **선택은 하지 않았다.** 어느 지표를 후보로 동결할지는 사용자 결정이다(두 지표를 모두 후보로 둘 수도 있다).
