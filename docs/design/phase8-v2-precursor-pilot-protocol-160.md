# Phase 8 — v2 계측 pilot 프로토콜 사전등록 (읽기전용, 문서 초안만) (§160)

§140~§159 전부 보존(수정 0건). §152의 선제 전환 0/40, 후속 5쌍 결과,
§154·§156·§158의 각 NO-GO 판정 범위 전부 그대로 보존한다. 이번 턴은
**기존 파일 읽기·읽기 전용 검증·프로토콜 초안 작성만** 한다 - 코드·
모델·SLO·임계값·연속판정 규칙 수정 0건, 클러스터 접속 0건, 새 trial·
pilot 실행 0건. 오프라인 탐색 4시간 이내로 제한했고(로컬 자원 불안정
징후는 이번 턴에 없었음 - 발생 시 즉시 중단하고 확인한 사실·남은
공백만 보고하는 방침을 그대로 따를 준비를 해 뒀다), 결론이 뚜렷해진
지점(§3의 임계값 혼동 확인, §4의 신호 가용성 확인)에서 후보나 범위를
더 늘리지 않고 마무리했다.

**이 pilot의 목적 재확인**: active+preview 동시 서빙을 **구현하는
게 아니다.** 그 구현에 투자할 근거가 있는지 판단하기 위해, 첫
개별 피해 전에 **실제로 이용 가능했을** 부하 신호와 시간 여유가
있는지만 탐색·계측한다 - 선제 복구 성공·피해 감소·arm 우월성을
입증하는 실험이 아니다.

## 3. 사전 피해 판정 규칙

### 3.1 `t_first_bad` - 그대로 유지, 단 중요한 혼동을 명시

`t_first_bad`(정렬+첫 매치, §152 방법)는 원자료 지표로 그대로
보존한다. **그러나 이번 검토에서 다음을 코드로 직접 확인했다**:

- `docs/design/slo-definition.md` 63행: `LATENCY_THRESHOLD`(=2×
  `L_baseline`, SLO v3=0.648초)는 명시적으로 **"P95 latency > 2×
  L_baseline"**, 즉 **직전 60초 슬라이딩 윈도우의 집계 P95** 기준으로
  정의돼 있다(같은 문서 68행: "P95는 직전 60초 슬라이딩 윈도우
  기준"). **개별 요청 하나의 지연에 대한 기준으로 정의된 적이
  없다.**
- 같은 문서 77행이 명시하는 유일한 개별-요청 수준 규칙은 **"단일
  요청의 timeout도 실패로 센다"**(완료 자체를 못 한 경우) - 이건
  "지연이 얼마 이상이면 개별 실패"가 아니라 "응답을 못 받으면
  실패"라는, 다른 종류의 규칙이다.
- `LATENCY_THRESHOLD`를 **개별 요청** 판정에 쓰는 코드는 전부 사후
  분석 스크립트뿐이다(`grep` 확인: `correct_followup_138.py:119`,
  `analyze_followup_results.py:61,63`) - **원 SLO 정의나 실시간
  탐지 파이프라인이 아니라, 분석 편의를 위해 같은 상수를 재사용한
  것**이다. §152부터 §159까지 이 프로젝트(그리고 이번 검토를 포함한
  나)가 계속 이렇게 써 왔다.

**사전 결정 필요(임의로 채우지 않음)**: 이 pilot의 `t_first_bad`를
계속 "개별 latency > 0.648s"로 정의할지(기존 §152~159와의 연속성은
있으나, 그 값이 개별 요청 기준으로 별도 검증된 적은 없다는 걸 알고
쓰는 것), 아니면 개별 피해를 **`success=False`(timeout/error)만**으로
좁히고 latency 초과는 오직 집계(`t_slo`) 판정에만 남길지는 **사용자가
정해야 한다.** 이 pilot은 어느 쪽이든 실행 가능하게 설계하되(§4·§6의
run_id·로그 스키마에 두 정의를 모두 계산해 남기도록), **어느 것을
"공식" `t_first_bad`로 쓸지는 결과를 보기 전에 확정**돼야 한다.

### 3.2 `t_first_confirmed_bad`·`t_slo` - 진단 전용, 대체 금지

§155 §3~4에서 이미 정한 대로: `t_first_confirmed_bad`(지속 저하
개시)와 `t_slo`(사후 30초 지속조건)는 **항상 별도로 계산·보고**하고,
어느 쪽도 `t_first_bad`의 성공 판정을 대신하지 않는다.

### 3.3 자연 발생 저속 요청 vs 장애 관련 피해 - 사전 규칙(미실행)

§155 §5가 설계했던 절차를 이 pilot의 **필수 선행 단계**로 승격한다
(이번 턴엔 미실행):

1. 기존에 이미 저장된 **모든 arm·모든 trial의 주입 전 구간** 원자료
   (core 45건 + aux 5건 + 후속 5쌍, 새 실험 아님)에서 개별 요청이
   자연적으로 §3.1에서 확정될 개별 기준을 넘는 배경 비율 `p_normal`을
   잰다.
2. 어떤 trial의 후보 `t_first_bad`가 주입 후 `n`번째 요청 이내에
   나오면, `p_normal`·`n`으로 "우연히 이 시점까지 자연 위반이 나올
   확률"을 이항분포로 근사한다. 사전에 정한 유의수준(예: 0.05)보다
   크면 - 즉 노이즈로 충분히 설명되면 - 그 trial의 개별 피해 귀속을
   **판정불가**로 남긴다. 작으면 장애 귀속으로 보고 §7의 게이트
   계산에 포함한다.
3. **소급 금지**: 이 절차는 **이 pilot의 새 trial에만** 적용한다.
   §152의 0/40, 후속 5쌍 결과에는 적용하지 않는다(§155 §5.3과 동일
   원칙).

## 4. 후보 신호와 필요한 계측

### 4.1 신호를 2개로 고정(결과를 보기 전, 사후 확장 금지)

| 신호 | 출처 | 수집 가능 여부 | 선정 이유 |
|---|---|---|---|
| **CPU**(`cpu_mean`/`cpu_slope`) | `rate(container_cpu_usage_seconds_total[30s])`, `features.py` - **이미 운영 중인 IF 모델의 실제 feature** | **확인됨 - 현재 파이프라인이 매 tick 계산** | §153·§156에서 후속 10건 중 7건 확인 가능한 전부(7/7)에서 노이즈로 설명 안 되는 크기(40~45배 베이스라인)의 상승이 실제로 관측됨(기존 결과, 재계산 아님) |
| **queue**(`vllm:num_requests_waiting`) | `features.py`의 `METRICS["queue"]` - 쿼리 자체는 정의돼 있음 | **불확실 - 검증 필요.** `model_v32/artifacts/feature-schema.json`이 이 특성을 학습 데이터에서 **"zero_variance_in_train"**(항상 0)이라며 최종 모델에서 제외했다. 이게 "vLLM 연속 배치 구조상 이 조건에서 큐가 실제로 안 쌓인다"인지 "이 지표가 애초에 제대로 스크레이프 안 되고 있다"인지 **이번 검토로 판정 못 함** - **smoke test에서 값이 0이 아닌 게 실제로 잡히는지부터 확인해야 한다(§6.1)** | 요청 적체를 latency 저하보다 먼저 반영할 가능성이 있는, 개념상 가장 직접적인 선행지표 후보이기 때문에 포함 - 단, "저장 안 됐거나 못 읽는 지표는 쓸 수 있다고 가정하지 말라"는 지시에 따라 **사용 가능 여부 자체를 smoke test의 1차 확인 항목으로 둔다** |

**의도적으로 제외**(이번 pilot 범위 밖, 결과를 늘리려 사후에 추가
안 함): `memory_mean/slope`(모델에 남아 있으나 §153에서 CPU보다
판별력이 뚜렷하지 않았음), `cache_mean/slope`(학습 통계상 절대값이
매우 작음, `feature-schema.json`: `cache_mean` 평균≈0.00033) - 이번
pilot이 유망한 결과를 내면 별도 후속 pilot의 후보로 남긴다.

### 4.2 원시 신호 변화 시각 vs 탐지기가 실제로 읽을 수 있었던 시각 - 반드시 구분

**§153의 방법론적 결함을 이번 pilot에서 고친다**: §153의 CPU 전조
탐색은 **이미 완결된 저장 시계열 전체**를 사후에 훑어 "언제 베이스
라인을 넘었는가"를 찾았다 - 이건 **"원시 신호가 언제 변했는가"**
(`t_raw_signal_change`)이지, **"살아있는 탐지기가 그 순간에 그걸
알 수 있었는가"**(`t_detector_readable`)가 아니다. 실시간 탐지기는
(a) Prometheus 스크레이프 주기(15초, `servicemonitor.yaml`)만큼
지연된 샘플만 보고, (b) 그 샘플을 30초 rate 창으로 평균해야 하며,
(c) 15초 평가 주기의 다음 tick이 와야 계산한다 - **이 세 지연을
거친 뒤에야 "탐지기가 읽을 수 있는 feature 값"이 나온다.**

**이번 pilot의 필수 계측(§2의 "추가되는 것", 코드 변경 - 별도
승인 필요)**: `score_server.py`(and `fixed_threshold.py`)의 실제
평가 루프(`while True: ... time.sleep(EVAL_INTERVAL_SEC)`)에 **매
tick마다** (tick 시각, 그 tick이 실제로 계산한 feature 값들,
anomaly score/판정, 연속판정 카운터 상태)를 로그로 남긴다 - 판정
로직·임계값은 안 바꾼다. 이 로그가 있어야 `t_detector_readable`
(=이 값이 "이상"으로 처음 반영된 tick의 시각)을 **미래 표본 없이,
그 tick 시점에 실제로 계산된 값만으로** 정의할 수 있다.

**금지 사항(지시 그대로)**: 주입 예정 시각, `load_ramp`의 미래
stage 일정, 실험 하니스 내부 정보(예: "지금이 stage-3 시작 시점")는
전조 판정의 입력으로 쓰지 않는다 - 위 로깅 설계 자체가 이걸
구조적으로 막는다(탐지기는 원래 이런 정보에 접근할 수 없다).

**전조 주장의 근거**: "전조가 첫 피해보다 앞선다"는 주장은 반드시
`t_detector_readable < t_first_bad`로만 하고, `t_raw_signal_change`
만으로 리드타임을 부풀리지 않는다. `t_raw_signal_change`는 참고
진단치로만 별도 보고한다.

## 5. 시간 예산과 실제 전환 증거

**기존 값 재인용(§154·§156, 새로 안 잼)**:

| 구간 | 상태 | 값/근거 |
|---|---|---|
| 스크레이프 지연 | 확인됨(주기만) | ≤15초(`servicemonitor.yaml`) |
| feature 창 반영 | 확인됨(창 길이만) | ≤30초(`features.py`의 `[30s]`) |
| 평가 대기 | 확인됨(주기만) | 0~15초 |
| 연속판정(3회) | 확인됨(상수) | 30초(2회 추가 tick) |
| 정책 결정 | 확인됨(파일럿 1건) | ~27.5ms |
| promotion 요청→L2 관측 | 부분 확인 | trial마다 수 초~수십 초(§153 재인용) |
| Endpoint 반영·실제 트래픽 반영 | **확인 필요 - 계측 없음** | §155 §7 |

이번 pilot이 §4.2의 로깅을 실행하면 "평가 대기+연속판정"이 실제로
순차 합산되는지 겹치는지를 **처음으로 실측**할 수 있다 - 그 전까지는
위 표의 "확인 필요" 상태를 유지한다.

**`t_switch`는 여전히 L2만 증명한다**: `rollouts_client.py: promote()`
가 Service `vllm-active`의 selector를 `vllm-preview`와 일치하는지
0.5초 간격 폴링으로 관측한 시각(§155 §7.1)일 뿐이다. 이번 pilot에서도
이걸 Endpoint 반영이나 새 pod의 실제 요청 처리를 입증한 시각으로
바꿔 부르지 않는다 - 이 pilot은 실제 전환 자체를 구현하지 않으므로
`t_switch`를 새로 만들지도 않는다(§2).

**장래 이중 서빙 계측 요구사항만(수치 없음)**: §159 §질문1에서 정리한
대로 - (a) 기존 `vllm-active`/`vllm-preview`를 안 건드리는 독립
Service, (b) 그 앞에 둘 자체 제작 프록시가 각 요청을 어느 pod로
보냈는지 자신의 로그에 남기는 방식. **이 라우터를 아직 만들지
않았으므로, 그 지연·성능 수치는 이 문서 어디에도 채우지 않는다.**

## 6. 반복·안전·분리 계획

### 6.1 Smoke test(별도, 결론 도출 안 함)

- 목적: §4.2의 새 로깅과 `queue` 지표가 **실제로 작동하는지**만
  확인한다 - 이 결과로 §7의 게이트를 판단하지 않는다.
- 범위: 각 arm 1회, 정상 부하(주입 없음) 짧은 구간에서 (a) tick별
  로그가 실제로 남는지, (b) `queue` 값이 항상 0인지 아닌지만 확인.
- 이 데이터는 본 측정 pilot과 **완전히 분리된 디렉터리**(§6.4)에
  저장하고, 본 pilot의 통계 계산에 절대 섞지 않는다.

### 6.2 본 측정 pilot - 결과를 보기 전에 고정

- **반복 횟수**: arm당 3회(`rep01~03`) - 이 프로젝트의 기존 소규모
  반복 관행과 동일. **이 반복 수는 성능 우월성 주장을 위한 표본
  크기가 아니다** - §1의 탐색·계측 목적에만 쓴다는 걸 결과 보고서
  에도 매번 명시한다.
- **순서**: `fixed_threshold`→`proposed` 교대(기존 rep03~05 패턴과
  동일), 결과를 보고 순서를 바꾸지 않는다.
- **run_id 규칙**: `load_ramp-{arm}-{rep:02d}-v2_precursor_pilot-v1`
  - 기존 `mainexp-v1/v2`·`post_hoc_followup-v1`과 접미사로 명확히
  구분.
- **기술적 무효 처리**: 기존 `run_once.py`의 `invalid_run`/
  `HarnessCorrupted` 분류를 그대로 재사용한다 - 새 범주를 만들지
  않는다.
- **중단 조건**: 기존에 이미 확립된 것을 그대로 쓰고 완화하지 않는다
  - 로컬 자원(§143~146의 commit-charge/headroom 게이트), 클러스터
  안전 게이트(`run_all_scenarios.py`의 `real_safety_checks()`,
  `_check_rollout_healthy_single_revision()`), preview 공존 메모리
  게이트(§96, `memory_pressure_adapter.py`), 잔여 Chaos/experiment
  리소스 확인(기존 cleanup 절차 재사용).

### 6.3 매 trial 전 확인 체크리스트(향후 실행 시)

1. `real_safety_checks(phase="pre")` 통과 확인.

## 7. 구현 투자 여부를 결정할 게이트

**이 게이트는 "다음에 이중 서빙 구현에 투자할 것인가"만 판단한다 -
선제 복구 성능 PASS가 아니다.**

- **투자 검토 신호**(전부 만족해야 "검토 가치 있음"): (a) §3.3 정상
  대조 절차로 장애 귀속이 확인된 trial 중 다수(가급적 `proposed`
  포함)에서 `t_detector_readable < t_first_bad`, (b) 그 순 여유시간이
  §5에서 **이번에 실측된**(추정치 아닌) 시간 예산 합계를 넘음, (c)
  `queue` 또는 `CPU` 중 최소 하나가 smoke test에서 실제로 유효한
  값을 낸다고 확인됨.
- **보류 신호**(하나라도 해당하면 보류): 전조가 확인 안 됨, 순 여유
  시간이 부족함, §5의 미측정 구간이 여전히 남아 전체 시간 예산을
  비교할 수 없음(이 경우 **성공을 가정하지 않는다** - 지시대로), 두
  후보 신호 모두 사용 불가로 판명됨.
- **명시**: 설사 이 pilot에서 유리한 관측이 나오더라도, **요청별로
  실제 전환이 일어났는지와 그로 인한 피해 감소는 이 pilot으로
  증명되지 않는다** - 별도 v2 구현(§159가 이미 설계 방향을 제시한
  독립 Service+프록시)과 독립적인 비교 실험이 반드시 있어야 한다.
