# Phase 8 — "선제적 복구" 재설계 초안 (읽기전용, 설계만) (§154)

§140~§153 전부 보존(수정 0건). 이번 턴은 **설계 문서 초안 작성만** 한다 -
코드 수정 0건, 새 분석 스크립트 0건, 재학습 0건, 임계값·연속판정 규칙
변경 0건, 클러스터 접속 0건, 새 실험 0건. §152의 0/40과 후속 5쌍
결과·모델·SLO는 그대로 보존하고, 이 설계에서는 **기존 자료를 새 버전의
성능 증거로 재사용하지 않는다** - 오직 "이 설계가 말이 되는가/무엇을
더 알아야 하는가"를 점검하는 용도로만 인용한다. 이번 초안은 **보고만
하고 다음 단계(코드·실험)는 사용자 승인 전까지 시작하지 않는다.**

핵심 목표 재확인(사용자 지시 그대로): **"점진적 장애로 인한 첫 사용자
요청 품질 저하 전에 실제 트래픽 전환을 완료하는 것"**. 사후 계산된
`t_slo` 이전 탐지나 promotion API 성공만으로는 이 목표를 달성했다고
부르지 않는다.

---

## 1. 설계 목표

- **1차 목표(필수)**: 점진적 장애 시나리오에서, **개별 요청 단위로 확인된
  지속적 저하가 시작되기 전에**, 실제 트래픽 전환이 완료된 것을
  **직접 증거로** 보인다. "탐지가 `t_slo`보다 빠르다"나 "promotion API가
  성공을 반환했다"는 이 목표의 증거로 인정하지 않는다(§4, §5).
- **2차 목표(1차 목표가 성립할 때만 의미 있음)**: 그 선제성이
  `fixed_threshold` 대비 실제 사용자 요청 실패·지연초과를 줄인다. 1차
  목표 없이 2차 목표(피해 감소)만 있는 경우를 "1차 목표 달성"으로
  재분류하지 않는다(§136 이후 이 프로젝트의 "선제 복구" 서술을 §152가
  이미 "실제 저하 이후 더 빠른 반응"으로 좁혀 정정했고, 이번 설계는 그
  좁혀진 사실 위에서 **진짜** 1차 목표를 다시 노려보는 것이다).
- **버전 분리**: 이 설계는 기존 `proposed`(Isolation Forest, 고정
  임계값·정책)와 **별도의 새 버전**이다. §152의 40개 trial, §147~150의
  5쌍, 모델 아티팩트(`model_v32` 등), SLO 정의(`slo_judge.py`)는 전부
  그대로 둔다. 이 설계 문서에서 인용하는 기존 수치는 전부 "타당성
  점검·설계 탐색용"이며, 새 버전이 실제로 이만큼 잘한다는 증거로
  쓰지 않는다.
- **적용 범위 한정**: 이번 설계는 **`load_ramp` 시나리오 하나**에만
  적용을 검토한다(§2). 새 시나리오·새 장애 유형은 만들지 않는다(기존
  "rigor over features" 원칙 유지).

## 2. 대상 장애와 제외 사유

| 시나리오 | 판정 | 근거 |
|---|---|---|
| `pod_kill` | **제외(구조적으로 대상 아님)** | 코드(`pod_kill_adapter.py` 문서화 주석) + 데이터(10/10 trial에서 주입 후 0~1초 안에 첫 피해) 둘 다 "전조 없는 즉발 장애"를 확인 - Chaos Mesh PodChaos는 "순간 액션"이다. §152·§153과 동일 결론, 이번에 다시 뒤집지 않는다. |
| `network_degrade` | **제외(구조적으로 대상 아님)** | §153에서 코드로 신규 확인: `network_degrade_adapter.py` 59행 - stage-1부터 `latency=500ms, jitter=50ms`를 **즉시 전량 적용**한다(점진적으로 올리지 않음). 베이스라인 왕복(~0.25~0.3s)에 이게 그대로 더해지면 첫 요청부터 0.648s 임계값을 넘길 수 있다 - 데이터도 10/10 고립 단발 0건·0.09~0.93초 만에 첫 피해로 일치한다. "5단계로 나뉜다"는 점에서 "점진형"으로 분류돼 있었지만 **각 단계 개시 자체는 계단함수**다 - `pod_kill`과 같은 이유로 제외한다. |
| `memory_pressure_negative_control_v1` | **기존 양성 사례로 사용 금지** | 확인 완료: (1) `official-experiment-state.json`의 `analysis_group=auxiliary_negative_control`, native 단독 5건뿐 - `fixed_threshold`/`proposed` 반복이 아예 없다. (2) `memory_pressure_adapter.py` 72행·504행 - non-native arm(preview 공존) 사전 headroom 게이트(§96)가 있고, 실패 사유로 "preview 공존 상태의 headroom 부족"이 명시돼 있다 - 즉 non-native 반복은 애초에 이 안전 게이트를 통과하지 못해 시도조차 되지 않았다. (3) native 5건 자체에 지속 SLO 위반이 없다(`docs/design/phase8-effect-cost-analysis.md` 20행, §4/§5/§6과 분리해 별도 취급). 세 가지 모두 사용자 지시와 일치 - 이 보조 실험에는 "proposed가 막았다"고 부를 대상(비교할 개입 사례)도, 막을 대상(위반)도 없다. |
| `load_ramp` | **잠정 대상(미확정)** | 코드(`chaos/scenario-load-ramp.yaml`)로 확인된 유일한 진짜 점진 개시(RPS 0.025→0.40, 5단계×90초) - stage-1 RPS(0.025)는 즉시 위반을 일으킬 만큼 높지 않다. §153에서 19개 유효 trial 중 10개(53%)가 첫 위반을 "고립 단발"로 재분류했고, 그 확인된 저하까지 76.7~380.9초의 실측 여유가 있었다(§3). **"잠정"인 이유**: 이 40개 trial은 이번에 새로 정의할 사전등록 규칙(§4) 없이 수집됐다 - 기존 자료로 "가능성이 있어 보인다"는 확인은 됐지만, 이 설계의 규칙으로 **처음부터 다시 검증된 것은 아니다.** 기존 stage·강도(`scenario-load-ramp.yaml`)는 이 설계에서 **바꾸지 않는다** - 성공 사례를 만들기 위해 완화하지 않는다(사용자 지시 그대로). |

**요약**: 새 시나리오를 만들지 않고, 기존 3개 중 `load_ramp`만 "선제
복구 검증 대상 후보"로 남긴다. 나머지 둘은 구조적으로 배제하고,
`memory_pressure_negative_control_v1`은 애초에 비교 대상이 아니므로
어느 쪽으로도 세지 않는다.

## 3. 상태 흐름

`load_ramp` 한 trial 안에서 "선제 복구"가 성립하려면 지나야 하는 단계와,
각 단계의 **증거 확인 여부**를 순서대로 나열한다(코드로 확인된 것만
"확인됨", 나머지는 "확인 필요"로 표시):

| # | 상태 | 근거/확인 수단 | 확인 상태 |
|---|---|---|---|
| S0 | 베이스라인 - preview가 이미 준비돼 paused 상태로 대기 중 | `blue_green_prep.py`: `prepare_preview()`가 trial 셋업 단계에서 injection 전에 항상 먼저 실행됨(§40 pilot 로그: preview ready 06:25:50 → injection 06:28:12, 2분 이상 먼저) | **확인됨 - 기존 trial 100%가 이 상태에서 시작** |
| S1 | 장애 주입 개시(`t_injection`) - load_ramp stage-1(RPS 0.025) 시작 | trial JSON 필드 | 확인됨 |
| S2 | 내부 자원 지표(CPU 등)가 실제로 벗어나기 시작 | 후속 10건은 cost-sampler로 확인 가능(§153), core-45는 자료 없음 | **부분 확인 - core-45는 확인 필요** |
| S3 | Prometheus가 그 변화를 스크레이프 | `servicemonitor.yaml` interval=15s | 확인됨(주기만) - 실제 스크레이프 지연(0~15초 중 어디였는지)은 tick별 로그 없음 |
| S4 | `score_server.py`가 그 구간을 포함한 feature window로 평가 | `features.py`: cpu는 `rate(...[30s])` | 확인됨(윈도우 길이만) - 이 창이 실제 판정 민감도에 준 영향은 확인 필요 |
| S5 | 3회 연속 이상 판정 → 신호 발행 | `score_server.py` 62·64행 상수 | 확인됨(상수만) - 개별 tick 원점수 로그 없음(§6) |
| S6 | 정책 결정(`decided_at`) | `decision_log.py` | 확인됨(레코드 존재) |
| S7 | promotion API 호출(`requested`) | `rollouts_client.py: promote_via_cli/_promote_via_api_patch` | 확인됨 - **API 성공 자체는 클러스터 반영을 보장 안 함**(같은 파일 docstring, direct patch가 실제로 selector를 안 바꾼 전례 있음) |
| S8 | Argo Rollouts 컨트롤러가 반영 → Service `vllm-active` selector 변경 | `promote()`가 폴링으로 확인(`t_switch`/`verified`) | 확인됨 - **이게 지금 `t_switch`가 실제로 증명하는 전부**(§5) |
| S9 | Endpoint/EndpointSlice가 새 pod IP로 갱신 | 없음 | **확인 필요 - 검증 코드 없음** |
| S10 | kube-proxy/네트워크 경로에 실제 반영(새 연결이 새 pod로 감) | 없음 | **확인 필요 - 검증 코드 없음** |
| S11 | 새 pod가 실제 요청을 처리 | 없음(요청별 pod 식별자 없음) | **확인 불가 - 계측 자체가 없음**(§5) |
| S12 | (독립 트랙) 개별 요청 첫 위반(`t_first_bad`) | 원자료 정렬+첫 매치(§152) | 확인됨 |
| S13 | (독립 트랙) 확인된 지속 저하 개시(`t_first_confirmed_bad`) | §153의 "60초 안에 후속 1건" 규칙(잠정) | 확인됨(규칙 자체는 §4에서 재검토) |
| S14 | (사후 전용) `t_slo` 확정 | `slo_judge.find_t_slo()`(30초 지속조건) | 확인됨 |

**"선제 복구 성공"이 요구하는 순서**: S1 < S8(현재 확인 가능한 최고
증거 수준, §5) ≤ S13(S12 아님 - §4) 이면서, S13이 아예 없거나(무기한
지연) S8보다 한참 늦은 경우와 구별돼야 한다. S9~S11은 지금 코드로
증명할 수 없는 구간이라, "선제 복구 성공"을 S8 기준으로 판정할지
S9~S11까지 계측을 늘려 판정할지가 **미해결 결정**(§10)으로 남는다.

## 4. 관찰 사실 / 반사실 / 성공·실패·판정불가 규칙

### 4.1 관찰 가능한 사실 (한 trial 안에서 직접 측정 가능)

`t_injection`, `t_first_bad`(개별 요청 단위, §152 방법 그대로), `t_first_
confirmed_bad`(§4.3), `t_detection`, `t_switch`(S8 수준, §5), `t_slo`
(사후, 30초 지속조건). 전부 **그 trial 자신의 기록**이다.

### 4.2 반사실 - 직접 관측 불가능, 절대 혼동하지 않는다

- **같은 trial을 "개입 있음/없음" 두 번 돌릴 수 없다** - 그래서 "이
  trial에서 전환이 없었다면 언제 첫 피해가 났을까"는 **원천적으로
  관측 불가능**하다. 이 반사실을 관측된 사실인 것처럼 쓰지 않는다.
- **다른 native trial의 `t_first_bad`는 이 proposed trial의 개별
  반사실이 아니다**(사용자 지시 그대로) - 서로 다른 실행, 다른 난수/
  타이밍/자원 상태를 가진 별개의 trial이다. native 여러 건의 분포를
  "참고 비교"로 쓰는 것(§136이 이미 하는 방식)은 유지하되, **특정
  proposed trial 하나와 1:1로 짝지어 "이 경우엔 이랬을 것"이라고
  말하지 않는다.**
- **"전환 후 나쁜 요청이 없었다"는 관측 사실이지, "전환이 막았다"는
  반사실적 결론이 아니다.** 후자를 주장하려면 위 반사실이 필요한데
  이 프로젝트의 실험 설계(각 trial 1회 실행)로는 얻을 수 없다 - 그래서
  이런 trial은 "전환 후 관측된 위반 없음"이라고만 기록하고, "첫 피해
  예방 성공"이라는 표현은 쓰지 않는다.

### 4.3 성공/실패/판정불가 규칙 (**새 데이터를 보기 전에 고정**)

**"확인된 지속 저하"의 정의(§153에서 처음 썼던 잠정 규칙을 이 설계의
공식 규칙으로 승격하되, 파라미터는 아직 미확정으로 남긴다)**:

> 개별 위반 요청 중, **그 뒤 W초 안에 위반이 최소 K건 더 있는** 첫
> 번째 위반 요청을 "확인된 지속 저하 개시"(`t_first_confirmed_bad`)로
> 본다. `W=60, K=1`은 §153에서 하나의 사례(`load_ramp-proposed-03`)를
> 직접 원자료로 검증해 합리적임을 확인했지만(고립 단발 뒤 75초간 정상
> 복귀 vs 진짜 저하 개시 뒤 연쇄 위반), **1RPS 프로브 기준 60초엔 약
> 60건의 요청이 있어 K=1은 약한 기준일 수 있다** - 건강한 상태에서
> 단일 요청이 자연적으로 0.648s를 넘는 배경 비율이 얼마인지 먼저
> 재보지 않고는 W·K를 확정하지 않는다(§9 1단계).

**판정 규칙**:

- **성공(선제 복구 성공)** = 다음을 **모두** 만족:
  1. 시나리오가 `load_ramp`다(§2 - 다른 시나리오는 이 규칙 자체를
     적용하지 않는다, "실패"로 세지도 않는다).
  2. `t_switch`(§5의 현재 증거 수준, S8)가 `t_first_confirmed_bad`보다
     **이전**이다. `t_first_bad`(고립 단발 포함 원 정의)보다 이전인지는
     **별도로 항상 같이 보고**하되(투명성), 성공 판정 자체의 필요조건은
     아니다(고립 단발까지 이겨야 한다고 요구하면 노이즈에 좌우된다).
  3. 탐지만 이르고 전환이 늦은 경우는 성공이 아니다(`t_detection` 아닌
     `t_switch` 기준).
  4. 전환 후 관측 기간(사전 지정, 예: 900초 cohort 끝까지) 동안의 위반
     여부는 **별도 필드**로 함께 보고한다("전환 후 위반 있음/없음") -
     위반이 없어도 이것만으로 "피해 예방 확정"이라고 결론 내리지 않는다
     (§4.2의 반사실 한계 때문 - 이 필드는 관측 사실 보고이지 인과 주장이
     아니다).
- **실패(선제 복구 실패)** = `load_ramp` trial에서 `t_switch`가 `t_first_
  confirmed_bad` 시점이거나 그 이후, 또는 유효한 신호/전환이 전혀
  없었던 경우.
- **판정불가** = (a) 고립 단발/확인된 저하 경계가 K·W 파라미터 확정
  전이라 애매한 경우, (b) `t_detection`/`t_switch` 등 필드가 없거나
  trial 자체가 기술적 실패(`invalid_run` 등)인 경우, (c) `pod_kill`·
  `network_degrade`(애초에 이 규칙의 적용 대상이 아님 - "실패"와
  혼동하지 않는다).

## 5. 전환의 증거 수준

`rollouts_client.py`를 코드로 직접 확인해 얻은, 현재 실제로 존재하는
증거 사슬(§3의 S6~S11과 대응):

| 수준 | 사건 | 코드 근거 | 지금 `t_switch`가 이걸 증명하는가 |
|---|---|---|---|
| L0 | API 호출이 성공을 반환(`requested=True`) | `promote_via_cli`/`_promote_via_api_patch` | 아니오 - 이 자체는 클러스터 반영을 보장 안 함(direct patch가 과거 selector를 실제로 안 바꾼 채 성공을 반환한 전례가 코드 docstring에 명시돼 있음) |
| L1 | Argo Rollout 컨트롤러가 promotion을 처리(status.phase 변화) | `get_rollout_phase()` 존재하나 `promote()`의 전환 판정에는 안 씀 | 아니오 - 이 경로로 확인 안 함 |
| **L2** | **Service `vllm-active`의 selector가 `vllm-preview`와 일치함을 폴링으로 관측** | `promote()`: poll_interval=0.5s, verify_timeout=5.0s | **예 - 이게 `t_switch`/`verified_at`가 실제로 증명하는 전부다.** 코드 자체 주석: "selector 전환의 정확한 발생 시각이 아니라 그 변화를 처음 확인한 시각(폴링 간격+API 지연만큼의 관측 오차)" |
| L3 | Endpoint/EndpointSlice가 새 pod IP로 갱신 | 없음 | **확인 필요 - 검증 코드 자체가 없다** |
| L4 | kube-proxy 등 실제 트래픽 경로에 반영 | 없음 | **확인 필요 - 검증 코드 자체가 없다** |
| L5 | 새 pod가 실제 요청을 처리(요청↔pod 매핑) | 없음(`probe.py`/`ramp.py` 원자료에 요청ID·pod 식별자 없음, §152 §6과 동일 공백) | **확인 불가 - 계측이 없다** |

**이번 설계가 실제로 받아들이는 증거 수준**: §4의 "성공" 판정은 **L2
기준**으로 정의한다(현재 계측으로 실제 확보 가능한 최고 수준). L3~L5로
올리려면 새 계측(Endpoint 조회 추가, 응답에 pod 식별자 주입 등)이
필요하고, 이는 코드 변경이라 이번 설계 범위 밖이다 - **L2보다 강한
주장("새 pod가 실제로 이 요청을 처리했다")은 하지 않는다.**

## 6. 필요 시간 예산 (예고시간 공식)

§153이 "`CONSECUTIVE_THRESHOLD=3 × EVAL_INTERVAL_SEC=15 = 45~60초`"를
사실상 확정값처럼 인용한 것은 이번 지시대로 **철회한다** - 그 상수들
(`score_server.py` 62·64행)은 코드로 확인됐지만, **개별 평가 tick의
실제 판정 시각·원점수가 로그로 남지 않아**(`decision_log.py`는 최종
판단만 기록) 그 산식이 실전에서 정말 45~60초로 끝나는지는 **검증된
적이 없다.** 아래는 공식의 각 항을 "확인됨(근거)"과 "확인 필요"로
나눠 제시한다 - 확인 필요 항목에 임의의 숫자를 채우지 않는다.

```
T_예고 = T_스크레이프지연 + T_feature창반영 + T_평가대기 + T_연속판정
         + T_결정 + T_promotion반영 + T_전환관측폴링
         (+ T_Endpoint반영 + T_트래픽실반영, L3~L4 - 미계측)
```

| 항 | 정의 | 상태 | 근거/수치 |
|---|---|---|---|
| `T_스크레이프지연` | 실제 값 변화 → Prometheus가 그 샘플을 수집 | **확인됨(주기만)** | `servicemonitor.yaml` interval=15s → 최대 15초(0~15초 사이, 위상에 따라 다름) |
| `T_feature창반영` | 계단 변화가 `rate(...[30s])` 등 창 통계에 완전히 반영 | **확인됨(창 길이만)** | `features.py`: cpu는 `[30s]` - 최대 30초. 그러나 "얼마나 반영돼야 모델이 반응하는가"는 미검증 |
| `T_평가대기` | 다음 평가 tick까지 대기(위상 어긋남) | **확인됨(주기만)** | `EVAL_INTERVAL_SEC=15` → 0~15초 |
| `T_연속판정` | 3회 연속 이상 판정 확정까지 추가 대기 | **확인됨(상수만)** | `(CONSECUTIVE_THRESHOLD-1) × EVAL_INTERVAL_SEC = 30초`(단, 위 두 항목의 위상과 독립이 아닐 수 있어 단순 합산이 맞는지 확인 필요) |
| `T_결정` | 정책 결정 로직 실행 | **확인됨(파일럿 1건)** | pilot 문서: "t_decision +27.5ms" - 무시 가능한 수준으로 보이나 n=1 |
| `T_promotion반영+T_전환관측폴링` | API 호출→컨트롤러 반영→`promote()`의 selector 폴링(0.5초 간격, 최대 5초 timeout)으로 확인 | **부분 확인** | §153에서 계산한 `t_detection→t_switch`(수 초~수십 초, trial마다 다름)가 이 전체를 뭉뚱그린 값 - API 호출 자체·컨트롤러 reconcile·폴링 관측 오차를 분리 측정한 적 없음 |
| `T_Endpoint반영`, `T_트래픽실반영` | §5의 L3·L4 | **확인 필요 - 계측 자체 없음** | 일반적인 K8s 소규모 클러스터 경험상 보통 짧다(초 단위 이하)고 알려져 있으나, 이건 **이 프로젝트의 실측이 아니라 일반 지식**이므로 이 설계의 시간 예산에 확정값으로 넣지 않는다 |

**preview 준비 상태에 따른 분리(사용자 지시)**:

- **preview 사전 준비 완료(S0, §3) - 기존 모든 trial이 이 경우**: 위
  표의 항들만 더하면 되고, 승격은 "이미 대기 중인 preview로 selector만
  바꾸는" 가벼운 작업이다. 대략 `15(스크레이프)+30(창)+15(평가대기)+
  30(연속판정)` 순서로 **최소 수십 초, 대략 60~90초대**로 추정되나 -
  각 항이 정말 순차적으로 더해지는지(겹칠 수 있는 항도 있음, 예:
  스크레이프 지연과 feature 창 반영은 같은 시간축 위에서 부분적으로
  겹칠 수 있음) **개별 tick 로그 없이는 확정 못 한다 - "확인 필요"로
  남긴다.** §153의 "45~60초"는 `T_스크레이프지연`과 `T_feature창반영`을
  아예 빠뜨린 하한이었다는 뜻이므로, 이번 재검토로 그 값 자체가
  더 커질 여지가 있다(어느 쪽이든 확정 아님).
- **preview 미준비**: 이 프로젝트의 **어떤 trial도 이 경로로 실행된 적이
  없다**(`blue_green_prep.py`가 항상 injection 전에 먼저 실행됨, §3 S0
  확인). 준비 자체의 실측 소요시간은 `blue_green_prep.py` 주석 기준
  163.7~350.3초(안전 여유를 크게 둔 `PREVIEW_PREP_TIMEOUT_SEC=480초`) -
  이 경로를 선제 복구에 쓰려면 위 시간 예산 전체에 **수 분**이 추가돼야
  한다는 뜻이고, 이 경우 필요한 전조 리드타임은 훨씬 더 커야 한다.
  **이 설계는 preview가 이미 준비된 경우만 현실적 대상으로 삼는다** -
  준비 안 된 경로는 참고로만 남기고 검증 계획(§9)에 포함하지 않는다.

## 7. 후보 탐지 방식과 필요 데이터 (특정 알고리즘을 미리 정답으로 두지 않음)

| 후보 | 데이터 요구량 | 시간상 실현 가능성 | 누출/오신호 위험 | 독립 검증 필요성 |
|---|---|---|---|---|
| **(A) 현행 IF 유지 + 계측만 강화**(모델·임계값 불변, 평가 tick별 원점수 로깅만 추가) | 추가 데이터 없음 - 기존 텔레메트리 그대로 | 불변(§6의 예고시간 그대로) - 새 능력을 만들지 않음 | 없음(행동 안 바뀜) | §6의 "확인 필요" 항목들을 실측으로 메꾸는 데 필수 - 새 능력은 없지만 현재 능력을 정확히 아는 선행 조건 |

**항상 과거~현재 구간**(`start`~`end`, 호출 시점 기준 지나간 시간창)의

(A)~(D) 중 무엇을 선택할지는 이 설계 문서가 정하지 않는다 - §10로
넘긴다.

## 8. 안전장치 - 분리된 지표로

세 가지를 **절대 하나로 합치지 않고** 별도 지표로 정의·보고한다:

1. **정상 상황 불필요 신호·승격률**: (장애 무주입 구간에서 발행된 신호
   수 + 실행된 승격 수) / (그 구간의 총 평가 tick 수). 현재는 이걸 잴
   전용 데이터셋이 없다(§7-B) - §9 1단계·3단계에서 확보 전까지는
   "미측정"으로 남긴다.
2. **실제 요청 실패·지연**: §147~152에서 이미 쓰던 지표(실패율,
   latency-threshold 초과율, union(∪) 지표) 그대로 유지한다 - 새
   대체지표를 만들지 않는다.
3. **탐지기·preview 자원 비용**: 기존 cost-sampler 기반 CPU/메모리
   계정을 그대로 쓰고, (B)/(C)/(D) 중 실제 구현하는 후보가 있다면 그
   추가 계측·평가 비용도 같은 방식으로 계정한다.

**결과 보고 규칙(사용자 지시 반영)**:
- "1차 목표 달성 여부"(§4의 성공 판정)와 "2차 목표(피해 감소) 달성
  여부"는 **항상 별도 칸으로 보고**한다 - 하나가 다른 하나를 대신하지
  않는다.
- §153의 2건(`load_ramp-proposed-02/03-post_hoc_followup-v1`)은 이
  설계 문서에서도 **정확히 같은 방식으로만** 인용한다: "확인된 지속
  저하보다 전환이 28.9~29.1초 앞선, 탐색적·같은 배치 내 미반복 사례이며,
  두 건 모두 전환 이후에도 심각한 저하가 그대로 발생했다." 이걸
  "첫 개별 피해 전 전환 성공 사례"로 격상하거나, 전환 후 저하 사실을
  빼고 인용하지 않는다.

## 9. 새 데이터로 검증할 순서 (승인 전까지 미실행)

**모든 단계는 별도 승인 필요 - 이 문서는 순서만 제시한다.**

1. **(분석 전용, 클러스터 접속 없음)** 기존에 이미 저장된 **주입 전
   구간** 데이터(모든 arm의 pre-injection 원자료, 새 실험 아님)에서
   단일 요청이 자연적으로 0.648초를 넘는 배경 비율을 재서 §4.3의
   `W`/`K`를 확정한다.
2. **(코드 변경, 행동 불변)** `score_server.py`에 평가 tick별 원점수·
   feature 벡터 로깅을 추가한다(§7-A) - 판정 로직·임계값은 그대로.
   §6의 "확인 필요" 항목을 실측으로 메꾸는 목적.
3. **(라이브, 무주입)** 로깅이 붙은 상태로 장애를 주입하지 않는 관찰
   세션을 짧게 돌려 §8-1(오탐률)의 최소 기준선을 잰다 - fault injection이
   없으므로 "새 실험"이라기보다 순수 관찰이지만, 그래도 클러스터 라이브
   세션이라 별도 승인 대상이다.
4. 1~3의 결과로 §4.3·§6·§7을 확정하고, 새 버전의 성공/실패/판정불가
   기준·반복 횟수·비교 순서(1차: 새 버전 vs `fixed_threshold`, 2차:
   새 버전 vs 동결 원본 `proposed` - 이 둘은 반드시 같은 세션의 새
   trial로만 비교하고 과거 rep01~05 자료와 섞지 않는다, §151에서 이미
   확정한 원칙 유지)·오탐/자원/안전중단 조건을 **새 결과를 보기 전에**
   전부 고정한다.
5. 그 이후에만 독립적인 새 `load_ramp` trial을 실행해 "첫 개별 피해
   전 전환"과 `fixed_threshold` 대비 실제 피해 감소를 검증한다. 라이브
   세션은 90분 이내로 나누고 승인 지점을 표시한다(이 프로젝트의 기존
   운영 방식 그대로).

## 10. 미해결 결정 (사용자 판단 필요)

1. **증거 수준 기준**: §4의 "성공"을 지금처럼 L2(Service selector 관측)
   기준으로 둘지, L3~L5(Endpoint 반영·실제 트래픽·요청-pod 매핑)까지
   계측을 늘려 더 강한 증거를 요구할지. 후자는 코드 변경(요청에 pod
   식별자 주입 등)이 필요하다.
2. **탐지 후보 선택**: §7의 (A)(계측만 강화)/(B)(더 민감한 보조 규칙)/
   (C)(새 지표)/(D)(예측 모델 전환) 중 어디까지 추진할지, 혹은 (A)에서
   멈추고 "이 이상은 안 간다"고 정할지.
3. **`W`/`K` 확정 전까지 판정불가로 묶인 경계 사례들을 어떻게 표기할지**
   (§4.3) - 재분석 우선순위 문제.
4. **자원·시간 투입 여부**: §151이 이미 "전환 후 처리" 후보 4개 전부
   NO-GO를 냈고, 이번 §153·§154는 "선제 타이밍" 자체가 `load_ramp`에서
   판정불가(C)임을 보였다 - 이 미해결 상태를 §9의 단계들(특히 3단계
   이상의 라이브 세션)에 투자해 풀 가치가 있는지는 **졸업작품의 남은
   일정·이미 투입된 비용**을 고려한 사용자의 판단 영역이다. 이 문서는
   그 판단에 필요한 사실만 제공하고, 진행 여부를 대신 결정하지 않는다.
5. **`network_degrade`의 "점진형" 분류 표기**: 이번에 코드로 확인한
   계단형 개시(§2) 사실을 기존 문서/그림의 시나리오 분류 설명에도
   반영할지(문서 일관성 문제, 데이터 재해석 아님) - 별도 확인 필요.
